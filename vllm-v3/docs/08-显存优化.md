# 09 · 显存治理：CG 的显存开销与 workspace 共享
> !!!AI 辅助，暂未修改

> **问题**：CUDA Graph 加速的代价是什么？prefill 阶段的显存开销主要花在哪？
> **答案**：最大的开销不是动态激活，而是 **CG 的静态分配**（workspace + graph pool）。本文讲清楚这些开销从哪来、为什么能省、怎么省。

## 一、显存开销全景（Qwen3-0.6B, 4090 D 实测）

### 1.1 各组件基线

| 组件 | 大小 | 说明 |
| --- | --- | --- |
| 模型权重 | 1.40 GiB | 0.6B bf16 |
| KV 池（96 块 × 256 tok） | 2.62 GiB | FlashInfer block_size=256 |
| eager 引擎总占用 | 4.90 GiB | 模型 + KV + backend workspace(512MB) |

### 1.2 叠加 CG 后的增量（优化前后对比）

| 配置 | 优化前 | 优化后 | 省了多少 |
| --- | --- | --- | --- |
| + Piece CG | ~+2.3 GiB | **+0.47 GiB** | **-1.86 GiB** |

> 早期版本的 **Cont CG** 增量 +2.73 GiB（256 个 q_len 图共享一个 graph pool），
> 因收益/成本比差已从 v3 移除，不再计入。

### 1.3 关键结论

```
CG 增量构成（优化后）：
  piece CG:  workspace 64MB + 其他静态 buffer 49MB + graph pool ≈ 0.47 GiB
  动态激活（4096-token prefill 峰值）: 仅 0.11 GiB  ← 不是瓶颈
```

**CG 的显存大头是"setup 成本"（graph pool），不是运行时激活。**

## 二、为什么 workspace 需要共享（本次优化核心）

### 2.1 什么是 FlashInfer workspace？

FlashInfer 的 `wrapper.plan()` 会在传入的 workspace 内按对齐偏移分配多个临时 buffer（`tmp_s`/`tmp_v` 等），供 attention kernel 使用。plan 必须在 CG 捕获前完成，捕获后 buffer 地址固定。

### 2.2 优化前的浪费

piece CG 有 29 个 (bs, L) 分片，**每个 piece 各自 `torch.empty(64MB)` 一个独立 workspace**：

```python
# 优化前：每个 piece 独立 workspace
for piece in self.pieces:
    bufs["workspace"] = torch.empty(ws, ...)  # 29 块 × 64MB = 1.86 GiB
```

**但 29 个 piece 从不同时运行**——它们对一次 prefill 请求是"或"关系（选中其中一个重放）。29 块 64MB 意味着 28 块完全闲置。

### 2.3 优化后的共享

```python
# 优化后：全 runner 共享一块（大小取最大 piece 的需求）
self._ws_bytes = max(64MB, max(bs*L) * 24KB)   # 一次估算
self._ws: torch.Tensor | None = None

def _make_piece_buffers(self, piece):
    if self._ws is None:
        self._ws = torch.empty(self._ws_bytes, ...)   # 只分配一次
    bufs["workspace"] = self._ws                       # 所有 piece 复用
```

溢出兜底也提升到 capture 层：某 piece plan 溢出时整块 `*2` 重建，而不是每个 piece 各自重试。

### 2.4 共享的安全性论证

**为什么共享是安全的？**
1. **时间上互斥**：一次 `step()` 只重放一个 piece，不同 piece 的 workspace 使用在时间上不重叠。
2. **plan 是幂等的**：`wrapper.plan()` 每次在 workspace 起始处重新布局，重放前不 plan 就不写 workspace。

**知识点**：共享的充分条件是"资源使用者时序互斥"。workspace 属于这类资源，因此共享是安全的。反例：decode 的多个 bs 图虽然也互斥，但它们的输入 buffer 按 bs 分片更直观——两种都是合法设计，按资源性质选。

> 早期版本的 **Cont CG** 也曾共享 workspace，但它捕获 q_len=1..256 的 256 个图，
> graph pool 线性膨胀（每个图 ~10.5 MB，256 图 +2.73 GiB），且受 `len(seqs)==1`
> 限制在并发前缀命中场景几乎不命中，收益/成本比差——已在 v3 移除。

## 四、测量方法

显存分解脚本：`bench/33_mem_prefill_breakdown.py`

```bash
CUDA_VISIBLE_DEVICES=0 python bench/33_mem_prefill_breakdown.py
```

它按 eager → +piece 逐步打印 reserved 增量，并拆解 workspace / 静态 buffer / graph pool 三部分（workspace 按 `id()` 去重统计共享效果）。graph pool 大小通过 `graphs.clear()` + `empty_cache()` 前后的 reserved 差测得。

**知识点**：`torch.cuda.memory_reserved()` 看"已向驱动申请"（含池化未用），`memory_allocated()` 看"实际使用"。CG 的静态分配会让 reserved 远大于 allocated——这也是为什么看显存要看 reserved。
