# 显存治理：CG 与 torch.compile 的显存开销

> **问题**：CUDA Graph 与 torch.compile 加速的代价是什么？显存开销主要花在哪？
> **答案**：最大的开销不是动态激活，而是 **CG 的静态分配（graph pool + 输出 buffer）** 与 **torch.compile 的编译产物缓存**。本文讲清楚这些开销从哪来、为什么能省、怎么省。

## 一、显存开销全景

### 1.1 各组件基线（Qwen3-0.6B）

| 组件 | 说明 |
| --- | --- |
| 模型权重 | 0.6B bf16 ≈ 1.4 GiB |
| KV 池 | block_size=256，按 `gpu_memory_utilization` 从剩余显存计算 |
| eager 引擎总占用 | 模型 + KV 池 |

### 1.2 叠加 CG / compile 后的增量

| 配置 | 增量来源 |
| --- | --- |
| + Decode CUDA Graph | graph pool（多个 bs 图共享一个 pool）+ 输出 buffer（`[max_bs, hidden]`）+ 复用 Batch 静态 buffer |
| + torch.compile prefill | inductor 编译产物 + autotune 缓存（`dynamic=True` 下符号形状，无按长度静态 buffer） |

> 早期 piecewise prefill CG（`core/prefill_cuda_graph.py`）需要一份 max-T 静态 buffer + 每个 piece 的 workspace，增量可达 +2.3 GiB；改用 torch.compile 后这部分不再存在，prefill 不再有独立的静态 buffer 与 workspace 管理。

### 1.3 关键结论

**CG 的显存大头是“setup 成本”（graph pool + 输出 buffer），不是运行时激活；compile 的显存大头是编译产物缓存。**

## 二、为什么 CG 显存要按“实际捕获量”预留

decode CG 的 graph pool 大小取决于最大捕获 batch size（`max_bs = min(max_num_seqs, 256)`）。`ModelExecutor` 用两阶段探针按实际捕获量预留，而不是固定预留：

```python
# compute/executor.py
def _probe_cg_footprint(self) -> int:
    probe_config = copy.copy(self.config)
    probe_config.torch_compile = False          # 只测 decode CG，不含 compile
    kv = self._make_kv(num_blocks=8)             # 最小 KV 池
    runner = ModelRunner(self.model, kv, self.sampler, config=probe_config, device=...)
    footprint = torch.cuda.memory_reserved() - self._mem_baseline
    runner.destroy()
    return int(footprint)

def init_kv(self):
    use_cg = not self.config.enforce_eager
    if self.config.num_kvcache_blocks > 0:
        num_blocks = self.config.num_kvcache_blocks
    else:
        reserve = self._probe_cg_footprint() if use_cg else 0
        num_blocks = self._resolve_num_blocks(reserve)   # 剩余显存给 KV 池
    ...
```

流程：先用最小 KV 池 + 真实模型构建一次 runner 触发 capture，测出 CG 的 reserved 增量；再把这个增量作为 `reserve_bytes` 传给 `KVManager.auto_num_blocks`，让 KV 池按“剩余显存”算块数——**CG 预留多少，KV 池就少多少**，避免固定预留浪费显存。

## 三、为什么共享是安全的（graph pool 复用）

decode CG 为多个 batch size 录制多张图，但它们共用同一个 graph pool（降序捕获，最大图分配 pool，小图复用）：

- **时间上互斥**：一次 `step()` 只重放一张图，不同 bs 的图在时间上不重叠；
- **pool 地址复用**：小图所需显存必然包含在大图的分配范围内。

共享的充分条件是“资源使用者时序互斥”。decode 的多个 bs 图满足这一点，因此共享是安全的。

## 四、测量方法

- `torch.cuda.memory_reserved()` 看“已向驱动申请”（含池化未用），`memory_allocated()` 看“实际使用”。CG 的静态分配会让 reserved 远大于 allocated——这也是为什么看显存要看 reserved。
- 启动日志会打印 `CG footprint measured: X.XXX GiB; KV pool sized to remainder (N blocks)`，直观给出 CG 预留与 KV 池规模。

## 五、其他显存优化建议

| 优化 | 省多少 | 成本 | 状态 |
| --- | --- | --- | --- |
| CG 显存按实际捕获量预留（探针两阶段） | KV 池按剩余显存满配 | 启动多一次捕获（~2s） | ✅ 已实现 |
| torch.compile 产物磁盘缓存 | 热启动免重编译 | 首次冷编译 ~25s | ✅ 已实现（inductor 默认缓存） |
