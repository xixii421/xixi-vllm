# v3 优化总览
## v2局限与v3优化方向
从 v0 到 v2，系统已经完成了从单模型自回归生成到多请求并发处理的基本框架构建。就单机推理服务而言，v2 已经具备了较为完整的功能：
- 单请求生成
- 分页式 KV Cache
- 前缀复用
- 多请求调度以及连续批处理等核心机制

但从推理服务的目标来看，功能完整性并不等同于性能高效。
推理引擎的核心任务不仅是正确生成结果，还需要在有限硬件资源下尽可能提高吞吐率、降低延迟，并提升 GPU 利用率。
因此，推理系统不仅需要考虑功能层面的完善，也要回到性能层面的优化上。

在 v0 到 v2 中，我们主要解决的是**逻辑正确性**和**调度结构**问题，例如请求如何进入系统、KV Cache 如何组织、Prefill 与 Decode 如何调度、多个请求如何并发推进等。这些问题决定了系统是否能够正确、高效地组织推理流程。

然而，v2 尚未充分处理以下性能问题：

1. **算子执行效率不足**  当前实现主要依赖通用 PyTorch 算子。这类算子更强调通用性和可组合性，但未必适配 LLM 推理中的分页 KV Cache、变长序列、连续批处理等特定执行模式。

2. **kernel 启动与调度开销较大**  在每个执行步中，如果存在大量细粒度 Python 调用和 kernel 启动，控制逻辑本身可能成为性能瓶颈。尤其在小 batch 或 Decode 阶段，GPU 计算量较小时，调度开销会更加明显。

3. **内存布局与访问路径尚未针对推理优化**  KV Cache 的存储布局、Attention 的读取方式、索引与拼接操作都可能引入额外内存拷贝和冗余访问，影响整体带宽利用率。

4. **计算路径仍偏概念化**  v2 更关注流程是否成立，而不是每一步是否足够快。因此，它可以作为正确的推理框架原型，但距离高性能推理引擎仍有明显距离。

因此，v3 的优化重点是在已有调度框架之上，对执行路径、算子实现和内存访问方式进行系统性重构。

从结构上看，LLM 推理引擎可以划分为三个层面：控制面、数据面和计算面。

| 层面 | 主要职责 | v2 状态 | v3 优化方向 |
| --- | --- | --- | --- |
| **控制面** | 请求调度、连续批处理、Chunked Prefill、Prefill 与 Decode 混合执行 | 已基本完成 | 保持整体结构不变，继续作为调度基础 |
| **数据面** | KV Cache 布局、批数据组织、内存管理、算子输入输出构造 | 执行效率较低 | 重构数据组织与执行路径 |
| **计算面** | 底层 kernel 与算子实现 | 主要依赖 PyTorch 通用算子 | 引入 FlashInfer、Triton、CUDA Graph 等高性能执行方式 |

在这一划分中，控制面决定系统如何组织请求，数据面决定数据如何进入计算，计算面决定计算如何真正执行。

v3 的目标是在不改变整体调度模型的前提下，重构数据组织方式和底层执行路径，使调度结果能够以更低开销、更高带宽利用率的方式进入 GPU 计算。
因此，v3 的主要收益并不来自控制逻辑本身的改变，而来自数据面与计算面的系统性优化。
