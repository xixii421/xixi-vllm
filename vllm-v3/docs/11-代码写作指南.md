# 11 - 代码写作指南：让读者（和未来的你）真正读懂

> 本文回答一个问题：**v3 的代码怎么写，才不是"AI 一次性写出来的一堆魔法"，而是程序员能逐行理解、能修改、能教给别人的代码。**

## 0. 核心认知：可读性 ≠ 注释多，可读性 = 结构

读者读懂代码靠三样东西，按优先级：

1. **结构**（函数拆分、调用顺序、数据流）——占 70%
2. **命名**（函数/变量名表达意图）——占 20%
3. **注释**（只写"为什么"，不写"是什么"）——占 10%

如果代码需要大量注释才能看懂，通常说明结构错了，而不是注释少了。
注释是**最后的手段**，不是主要手段。

---

## 1. 第一原则：一个函数只做一件事（单一职责）

### 反例（重构前 v3 的 `model_runner._run_batch`，150 行）

一个函数里同时做：构造输入 → 打包采样参数 → 判断 4 条执行路径 → 每条路径里
重复构造采样参数、重复包裹 forward_context → 提前 return。读者要记住 4 个出口
才能跟上。

### 正例（重构后）

```python
def _run_batch(self, seqs, *, is_prefill):
    """执行一批序列，返回采样的 token id。"""
    if not seqs:
        return []
    inputs = build_model_inputs(seqs, is_prefill, self.block_size, self.device)
    sampling = self._build_sampling_inputs(seqs)
    hidden = self._forward(seqs, inputs, is_prefill)
    if is_prefill and not self._need_sample(seqs):
        return [0] * len(seqs)
    logits = self._logits_for_sample(hidden, inputs)
    return self.sampler(...).tolist()
```

读者第一眼就知道流程：**构造输入 → 选路径 → 采样**。没有分支，没有提前 return。

### 判断标准

- 函数签名（函数名 + 参数 + 返回）能讲完整个故事 → 合格
- 需要看函数体才能回答"它做什么" → 太长，该拆

## 2. 第二原则：分派器（Dispatcher）模式——把"多路径"显式化

v3 里最难的阅读障碍是 `_run_batch` 里的 3 条执行路径（decode CG / piece CG /
eager）。好的做法是**一个显式的分派器**，让读者先看到"有几条路、
各自什么条件"，再决定看哪条路的具体实现。

```python
def _forward(self, seqs, inputs, is_prefill):
    """按优先级选执行路径，返回整批 hidden states。

    优先级设计（谁最快用谁，不可用则回退下一档）：
      decode        : decode CG → eager
      prefill 首 chunk : piece CG → eager
      prefill 续 chunk : eager（前缀命中跳过 KV 重算后剩余走 eager）
    """
    if not is_prefill:
        return self._decode_cg(seqs, inputs) or self._eager_forward(...)
    if all(s.num_cached_tokens == 0 for s in seqs):
        hidden = self._piece_cg(seqs, inputs)
        if hidden is not None:
            return hidden
    return self._eager_forward(...)
```

### 分派模式的三个约定

1. **每条路径一个私有方法**：`_decode_cg` / `_piece_cg` / `_eager_forward`
2. **路径方法返回 `hidden` 或 `None`**：`None` 表示"这条路不可用，请回退"
3. **分派器不重复采样逻辑**：所有路径统一返回 hidden，采样在 `_run_batch` 收尾

这样读者可以：
- 只看分派器 → 理解架构（有几条路、什么条件）
- 只看某条路径 → 理解一个具体优化（如 piece CG 为什么能加速）

## 3. 第三原则：方法名是"为什么"的注释

v3 里许多一次性逻辑被写成行内注释。更好的是把它们变成方法，用名字说话：

```python
# 反例：40 行的 _make_piece_buffers 同时干 4 件事
def _make_piece_buffers(self, piece):
    bufs = {...}                    # 分配 tensor
    bufs["qo_indptr"].copy_(...)    # 固定分布
    bufs["workspace"] = self._ws    # 共享 workspace
    wrapper = self._build_wrapper(...)
    self._metas[piece] = AttentionMetadata(...)

# 正例：拆成 4 个方法，名字即文档
def _make_piece_buffers(self, piece):
    bufs = self._alloc_buffers(M, bs, L)
    self._init_capture_layout(bufs, bs, L)
    bufs["workspace"] = self._shared_ws()
    wrapper = self._build_wrapper(piece, bufs)
    self._buffers[piece] = bufs
    self._metas[piece] = self._build_metadata(bufs, wrapper)
```

读者的心智负担从"跟踪 4 件事的状态"降为"读 4 个方法名"。

### 命名原则速查

| 场景 | 好的命名 | 差的命名 |
| --- | --- | --- |
| 判断是否可用 | `can_use(bs, seq_lens)` | `check(...)` |
| 共享资源 | `_shared_ws()` | `_get_ws()` |
| 初始化固定布局 | `_init_capture_layout(bufs, bs, L)` | `_setup(bufs)` |
| 返回可选路径 | `_piece_cg(...) -> Tensor \| None` | `_run_piece(...)` |

## 4. 第四原则：注释只写"为什么"，不写"是什么"

### 好注释：解释代码无法表达的意图

```python
# cu_seqlens_k 必须与 cu_seqlens_q 同为 token 粒度（kv_indptr 是页粒度，只喂给
# FlashInfer paged wrapper）。否则 FA2 varlen 把每条 K 序列当成 1 个 token。
```

这段注释价值极高：**它记录了一个曾经踩过的坑**（bs>1 CG 输出完全错乱的真实 bug）。
删除它，未来会有人再踩一遍。

### 坏注释：复述代码已经说明的事

```python
# 先跑 3 次 warmup
for _ in range(3): forward()        # ← 代码已经说了"跑 3 次"

# 把 hidden 拼起来
return torch.cat(rows, dim=0)       # ← 代码已经说了"cat"
```

### 判断标准

问自己：**如果删除这条注释，读者会失去什么？**
- 失去"为什么这样设计 / 这是个坑 / 这里有个权衡" → 保留
- 只失去"这段代码做了什么" → 删除

## 5. 第五原则：模块级 docstring 是"入口地图"

读者打开一个文件，第一眼该看到**这个模块在系统里的位置和职责**，而不是立刻
陷入代码。给每个核心类加一段"入口地图" docstring：

```python
class PrefillCUDAGraphRunner:
    """prefill piecewise CUDA Graph：按 (bs, L) 捕获固定形状的图并重放。

    设计动机与收益判据见 docs/10-Prefill-CUDA-Graph.md。
    核心矛盾：prefill 形状动态，而 CUDA Graph 要求静态形状。
    解法：用 (bs, L) 网格覆盖常见形状，L 处 padding，重放时只填真实数据。
    """
```

一个可读的 docstring 应该回答：
1. **这个类/模块是什么**（一句话）
2. **它解决什么核心矛盾**（为什么存在）
3. **指向深入文档**（哪里能学到完整原理）

## 6. 第六原则：重复代码是"信号"，不是"风格"

v3 重构前，`scheduler._pull_prefill_chunk` 和 `_schedule_prefill_first` 有大量
重复的 chunk 切分逻辑。发现重复时的正确反应是**提取公共逻辑**，而不是复制粘贴。

```python
def _chunk(seq, *, max_tokens, block_size, clamp_to_block=False):
    """公共的 chunk 切分：计算本次调度给 seq 的 token 数。"""
    ...
```

### 什么时候可以容忍重复

- 两条路径语义完全不同，只是碰巧长得像（强行合并会引入隐性耦合）
- 为了性能手写的内联代码（拆函数有调用开销的 hot path）

## 7. 面向读者的"阅读顺序"工程

代码写好后，用读者的视角走一遍：

1. **从入口开始**：`engine.py` → `scheduler.py` → `model_runner.py` → `layers/`
2. **每个文件先看 docstring 再看主方法**
3. **分派器优先**：先看 `_forward` 的分支结构，再看单条路径

如果走下来有"卡住"的地方，那就是需要改进的信号——加 docstring、拆方法、
或补一条"为什么"注释。

---

## 8. 给 AI 协作的约定（本项目的实践）

因为 v3 代码大量由 AI 生成，程序员更难读懂，所以约定：

1. **每个非平凡方法必须有 docstring**（说明意图而非实现）
2. **注释记录"坑"和"权衡"**，不记录"步骤"
3. **分派逻辑集中一处**，不要散落在多个 if 分支里
4. **改性能代码后必须验证数值一致性**（见 `bench/0*_verify_*` 系列），并把这个
   验证过程留给读者（`_calibrate`、`can_use` 的 docstring 就是在做这件事）
5. **指向文档**：每个优化点都应在 `docs/` 有对应章节，代码里用 docstring 指路

## 9. 练习：用这份指南重读一遍 v3

| 文件 | 可读性要点 |
| --- | --- |
| `engine/engine.py` | 控制面：scheduler 怎么编排 request |
| `engine/scheduler.py` | chunk 切分 + PD mix 的"为什么" |
| `engine/model_runner.py` | **分派器模式**（重构后最值得读） |
| `engine/sampler.py` | 整批采样 + Gumbel-max 的技巧 |
| `core/prefill_cuda_graph.py` | 静态形状 vs 动态形状的矛盾与解法 |
| `memory/manager.py` | 前缀缓存的三态（free/cached/used） |

读完每个文件，问自己三个问题：

1. 这个文件在系统里做什么？（入口地图）
2. 它是怎么做的？（结构 + 分派）
3. 为什么这么做？（docstring + 坑注释）
