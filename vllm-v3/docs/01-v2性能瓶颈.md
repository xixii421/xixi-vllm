# 01 · v2 的性能瓶颈

v2 已经支持 Continuous Batching、Chunked Prefill、Prefill / Decode 混合调度。但是v0-v2的性能并没有明显提升，甚至还有略微下降，之前我们提到把原本的vllm拆分为**控制、数据、计算**三个层面。

v3 版本则主要在计算侧进行性能提升。

## 2. 瓶颈总览

| 编号 | 瓶颈 | v2 | v3  |
| --- | --- | --- | --- |
| A | Attention | 先把分页 KV **gather 成连续张量**再调 SDPA；SDPA 不懂 `block_table`；decode 按序列 **for 循环**拆批 | **FlashInfer** 按页表就地算 attention；批 decode 一次合批 |
| B | Decode 启动 | 每步大量小 kernel **eager launch**，小模型 / 小 batch 上启动开销大于计算本身 | 使用**CUDA Graph**进行加速 |
| C | KV 写入 | 每层、每步用**`index_copy_`** scatter | **Triton `store_kvcache`** 按 slot 特化写入 |
| D | Norm / RoPE / MLP | 纯 PyTorch 小算子，kernel 多、难融合 | **Triton** RMSNorm / RoPE；**`torch.compile`** SiluAndMul |
| E | 输入与采样 | H2D 偏同步；采样未批处理 | **`pin_memory` + non_blocking** H2D；**批量 Sampler** |


## 3. Attention 先 gather，再 SDPA

源码位置：
> [v2-attention.py](../../vllm-v2/src/layers/attention.py) | [v2-store](../../vllm-v2/src/pagedattention/store.py)

### 3.1 完整路径
我们再回顾一下Attention模块中的计算逻辑是什么。

* 首先，模型会算出来当前这一步的K和V，它们按照映射表把数据填到显存池对应的位置。
* 其次，Attention计算的时候，需要Q、K、V是处于连续张量的状态，但是K和V在硬件的内存池是东一块西一块不连续的。所以得先把这些散落的页按照页表拷贝出来，拼成一大块连续的张量。
* 最终进行点积注意力计算。

理想的做法是：K和V老老实实呆在内存池里，写一个专门的Attention计算内核，让它直接按照页表一页一页读，然后就地算完。简单来说，原本有两页题，理想做法是边看边算，但是我们之前的做法是，先把题从各个地方抄到草稿纸上，然后统一计算。

**抄**这个动作就是gather，然后再SDPA，整体多了一次大规模搬运，这就是慢的主要原因。


---
### 3.2 回顾PagedStore
内存池的物理布局如下所示：
```
k[layer_id, block_id, offset_in_block, H_kv, D]
v[layer_id, block_id, offset_in_block, H_kv, D]
```
其中 block_id 是物理页号，offset_in_block 是页内偏移，H_kv 为 KV 头数，D 为头维度。


write负责将本次算出来的KV写入内存池：
```py
def write(self, layer_id, slot_mapping, k, v):
    # k, v: [num_tokens, H_kv, D]
    flat_k, flat_v, flat_dim = _flat_layer_views(self.pool, layer_id)
    flat_k.index_copy_(0, slot_mapping, k.reshape(n, flat_dim))
    flat_v.index_copy_(0, slot_mapping, v.reshape(n, flat_dim))
```

gather负责将离散的历史KV拼成连续张量：
```py
def gather(self, layer_id, block_table, seq_len):
    bs = self.pool.block_size
    table = torch.tensor(block_table[:need_blocks], device=..., dtype=torch.long)
    positions = torch.arange(seq_len, device=..., dtype=torch.long)
    physical = table[positions // bs]
    offsets = positions % bs
    k = self.pool.k[layer_id, physical, offsets]  # [seq_len, H_kv, D]
    v = self.pool.v[layer_id, physical, offsets]
    return k, v
```

gather操作的核心特征是：每次读取都会覆盖完整的seq_len个位置，而不是仅仅读取本步新增的token，需要返回一整块新的连续张量来供后续SDPA使用。

### 3.3 Attention 层的前向流程

```python
# vllm-v2/src/layers/attention.py

def forward(self, q, k, v):
    ctx = get_forward_context()
    q, k, v = q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2)

    # ① 先写入本步 K/V
    store.write(self.layer_id, ctx.slot_mapping, k.transpose(1, 2), v.transpose(1, 2))

    if ctx.is_prefill:
        return self._prefill(q, k, v, ctx)
    return self._decode(q, ctx)


def _prefill(self, q, k, v, ctx):
    cached = ctx.cached_lens[0] if ctx.cached_lens else 0
    if cached == 0:
        # 冷启动：本步 K/V 已经是连续的，直接 SDPA，无需 gather
        return self._sdpa(q, k, v, is_causal=True).transpose(1, 2).contiguous()

    # 有前缀命中 / chunked：必须把「整段 context」gather 出来
    k_full, v_full = ctx.store.gather(self.layer_id, ctx.block_tables[0], ctx_len)
    k_full = k_full.unsqueeze(0).transpose(1, 2)  # [1, H, L, D]
    v_full = v_full.unsqueeze(0).transpose(1, 2)
    # 再构造 causal mask，对 (q_len × ctx_len) 做 SDPA
    out = self._sdpa(q, k_full, v_full, is_causal=False, attn_mask=attn_mask)
    return out.transpose(1, 2).contiguous()


def _decode(self, q, ctx):
    outs = []
    for b in range(q.shape[0]):                      # ← 按序列拆批
        ctx_len = ctx.context_lens[b]
        k_c, v_c = ctx.store.gather(                 # ← 每条序列 gather 整段历史
            self.layer_id, ctx.block_tables[b], ctx_len
        )
        k_c = k_c.unsqueeze(0).transpose(1, 2)
        v_c = v_c.unsqueeze(0).transpose(1, 2)
        outs.append(self._sdpa(q[b : b + 1], k_c, v_c, is_causal=False))
    return torch.cat(outs, dim=0).transpose(1, 2).contiguous()
```
SDPA要求 K/V 已经是 `(B, H, S, D)`。

### 3.4 带宽分析
| 参数             | 取值            |
| -------------- | ------------- |
| batch size B   | 8             |
| 每条上下文长度 L      | 2048          |
| KV heads H\_kv | 8             |
| head dim D     | 128           |
| dtype          | bf16（2 bytes） |
| 模型层数           | 28            |


单条序列单层一次decode的gather搬运量：

首先K和V各自需要取L个位置：
```
2 (K + V) * L * H_kv * D * 2 bytes
= 2 * 2048 * 8 * 128 * 2
= 8 MiB
```
其次计算整个模型整个batch单步的总搬运量为：
```
8 MiB × B × 层数
= 8 × 8 × 28
≈ 1.75 GiB / step
```
这些字节在每一层每一步都需要搬运一遍，且搬运后仅仅是为了给SDPA，而Attention计算本身还要再次读取QKV，因此KV在热路径上被反复读取。

### 3.5 性能瓶颈
1. Gather：分页省了碎片，但是热路径又把 KV 全部读出
2. SDPA：无法直接消费分页布局
3. Decode 的 for 循环，调度层合并了批次，但是计算层面却又使用循环


## 4. Decode 没有 CUDA Graph

### 4.1 路径

一步 decode 的计算量其实很小。通常每条序列只有一个 query token。

但它仍然要串起一整条 Transformer 路径：

```text
embedding
→ RMSNorm
→ QKV projection
→ RoPE
→ Attention
→ O projection
→ RMSNorm
→ MLP
→ lm_head
```

v2 的 decode 没有 CUDA Graph，每一步都按 eager 模式逐个 launch kernel。

---

### 4.2 慢在哪里

GPU 上一步的时间可以粗略拆成：

```text
总时间 = 计算时间 + kernel launch 时间 + 同步等待时间
```

Decode 的特点是计算量小，kernel 数量多。

当模型较小、batch 较小时，GPU 计算时间很短，CPU 的 launch 开销反而会占主导。

这就是 launch-bound：

> GPU 不是算不过来，而是等 CPU 把下一个 kernel 发过来。

CUDA Graph 的作用不是改变数学结果，而是把一步 decode 的 kernel 序列录成一张图，之后一次 replay。

它可以显著减少：

```text
CPU launch 次数、Python 调度开销、kernel 之间的空隙时间。
```

---

### 4.3 和 Continuous Batching 的区别

这里容易混淆：

| 机制 | 解决的问题 |
| --- | --- |
| Continuous Batching | 多请求之间如何共享 GPU 时间片 |
| CUDA Graph | 单步内部如何减少 kernel launch 开销 |

Continuous Batching 提高的是请求之间的 GPU 占用率。

它不消除单步内部的 launch 税。

所以会出现这种情况：

```text
调度已经是 Continuous Batching，
但 decode 仍然很慢。
```

原因就在于，单步执行路径本身仍然很重。

---

### 4.4 什么时候最明显

| 场景 | 主导因素 |
| --- | --- |
| 小模型、B=1 decode | launch-bound 最明显 |
| 大模型、大 batch prefill | 计算和带宽更主要 |
| 长上下文 decode | attention gather 和 KV 带宽更主要 |

因此 A 和 B 都是第一优先级，但它们打中的场景不同：

```text
A 更伤长上下文、大 batch decode。
B 更伤小模型、小 batch decode。
```

---

## 5. 瓶颈 C：KV 写入是通用 `index_copy_`

### 5.1 路径

v2 的 KV 写入通过 `PagedStore.write` 完成。

它根据 `slot_mapping` 把当前步的 K/V 写入分页 KV cache，底层是：

```python
index_copy_
```

代码锚点：

```text
vllm-v2/src/pagedattention/store.py
```

---

### 5.2 慢在哪里

`index_copy_` 是一个通用索引写算子。它不是专门为 KV cache 布局设计的 fused scatter。

问题在于它的调用频率太高：

```text
每个 Transformer 层都要写一次。
每个 step 都要写一次。
prefill 和 decode 都要写。
```

单独测量时，它通常不如 attention 和 CUDA Graph 那么显眼。

但它是每层固定开销。模型层数越多，累计越明显。

更重要的是，它和瓶颈 A 会叠加：

```text
写入时用通用 scatter，
读取时又要 gather 成连续张量。
```

同一份 KV，在热路径上被两次低效对待。

---

## 6. 瓶颈 D：Norm、RoPE、MLP 未融合

### 6.1 路径

v2 中这些模块大多是 PyTorch eager 小算子：

| 模块 | v2 实现 |
| --- | --- |
| RMSNorm | 转 float、平方均值、rsqrt、乘 weight |
| RoPE | PyTorch 旋转 Q/K |
| SiluAndMul | chunk、silu、mul 分开执行 |

这些算子单个都不大，算术强度也不高。

---

### 6.2 慢在哪里

它们的问题不是单个算子很重，而是数量太多。

每一层都会产生一串小 kernel：

```text
norm
→ residual
→ rope
→ silu
→ mul
→ ...
```

在 eager 模式下，这些小算子会带来：

1. 更多 kernel launch。
2. 更多中间张量。
3. 更多显存读写。

如果 decode 路径打开了 CUDA Graph，一部分 launch 开销会被图吸收。

但在 prefill，或者没有 CUDA Graph 的路径下，这些未融合算子仍然会暴露出来。

---

## 7. 瓶颈 E：H2D 与采样

这一类属于第二梯队。

单流 decode 下通常不明显，但在高并发服务负载下会被放大。

典型问题包括：

| 环节 | 问题 |
| --- | --- |
| Host to Device | 拷贝偏同步，容易落在关键路径上 |
| pin memory | 使用不充分 |
| Sampler | 功能正确，但批量化和 kernel 化不够 |
| CPU 侧小操作 | 大 batch 时变多 |

它们不是 v2 相对 v3 慢的主因，但在真实 serving 场景下仍然值得优化。

---

## 8. 瓶颈 F：前缀缓存残缺，不是算子慢

前缀缓存影响的是有效性能：

> 同样一块 GPU，本来可以复用 KV，现在却重新做 prefill。

这不是“算子算得慢”，而是“系统没有省掉该省的计算”。

v2 中可能出现的问题包括：

| 问题 | 后果 |
| --- | --- |
| radix invalidate 不可靠 | 页回收后树索引仍可能指向旧页 |
| 缺少合理驱逐策略 | 热前缀被挤掉，命中率下降 |
| full-hit 时没有正确 promote | 请求可能卡在 waiting，表现为挂死或极慢 |
| hash 成本偏高 | 通常不是主要矛盾，但 CPU 侧会多花钱 |

这类问题在单流、无 KV 压力的 decode 下几乎看不出来。

但在以下场景会很明显：

```text
多请求共享长 system prompt；
KV cache 压力较大；
大量请求命中相同前缀。
```

此时它抬高的是有效 TTFT，而不是单 token decode 延迟。

---

## 9. 瓶颈 G：双次 forward

v2 和 v3 在当前教学合同里都还是：

```text
run(prefills, decodes)
= 一次 decode forward + 一次 prefill forward
```

也就是说，调度层已经可以混排 prefill 和 decode，但计算层仍然把它们拆成两次 forward。

生产系统可以进一步做 fused prefill / decode，在同一次 forward 里处理两类 token。

这是和更高生产上限的差距。

但它不是 v2 相对 v3 慢的主要原因，所以单独列为 G，避免和 A 到 F 混淆。

---

## 10. 小结

可以把这些瓶颈按性质分成三类。

### 10.1 算子本身慢

包括：

```text
A：gather + SDPA
C：index_copy_ 写 KV
D：未融合的小算子
E：部分 H2D 和采样路径
```

它们的问题是 GPU 执行路径不够高效。

---

### 10.2 该合批却没合批

典型是：

```text
A：decode attention 按 batch 循环
B：decode 没有 CUDA Graph
```

调度层已经把请求合起来了，但执行层又把它们拆开。

---

### 10.3 该复用却没复用

典型是：

```text
F：前缀缓存残缺
```

它不是 GPU 算得慢，而是系统没有省掉重复 prefill。

---

## 11. 最终结论

| 瓶颈 | 慢在什么机制 | 主要影响 |
| --- | --- | --- |
| A | gather KV + 非分页 SDPA + decode 拆批 | decode 吞吐、长上下文延迟 |
| B | decode 无 CUDA Graph | 小模型、小 batch decode |
| C | 每层通用 `index_copy_` | 每层固定开销 |
| D | Norm / RoPE / MLP 未融合 | eager 路径和 prefill |
| E | H2D 与采样不够批量化 | 高并发 |
| F | 前缀缓存命中率不可靠 | 有效 TTFT |
| G | prefill / decode 两次 forward | 混跑上限 |

三句话总结：

1. v2 相对 v3 慢，主因不是调度，而是数据面。
2. 最大的两个点是 Attention 的 gather + SDPA，以及 decode 没有 CUDA Graph。
3. KV 写入和小算子融合是稳定的第二梯队开销；前缀缓存影响的是“能不能少算”，不是“算得快不快”。
