# v2 的性能瓶颈

> [!NOTE]
> 此前我们将推理引擎划分为三个层面：控制面、数据面和计算面。v2 主要完成了控制面的建设，而 v3 的优化重点则放在计算执行路径上，即在不改变整体调度逻辑的前提下，降低每一步的算子启动开销、内存拷贝开销和 kernel 执行开销。

## 2. 瓶颈总览


| 编号  | 瓶颈 | v2 现状 | v3 优化方向 |
| --- | --- | --- | --- |
| A   | Attention         | v2 需要先将分页 KV Cache 聚合成连续张量，再调用 SDPA；SDPA 无法直接基于 `block_table` 访问分页 KV；Decode 阶段还需要按序列循环处理，无法充分利用批处理能力。 | 使用 FlashAttention（`flash_attn_varlen_func(block_table)` + `flash_attn_with_kvcache`）直接基于分页 KV Cache 和 `block_table` 计算 Attention；Decode 请求可以合并为一次批量 Attention 执行。 |
| B   | Kernel启动开销        | Prefill和Decode阶段启动开销。Prefill和Decode每一步都会启动大量细粒度kernel。在小模型或小 batch 场景下，kernel 启动和主机侧调度开销可能超过 GPU 计算本身。 | Decode 使用 CUDA Graph 捕获重放；Prefill 首 chunk 使用 torch.compile 全图编译（`attention`/`silu_and_mul`/`rotary_embedding` 注册为 custom op 算子），减少重复的 kernel 启动和 CPU 调度开销。        |
| C   | KV Cache 写入       | 每步都通过 `index_copy_` 等通用算子写入 KV Cache。该方式实现简单，但索引和访存路径较为通用，难以贴合分页 KV Cache 的写入模式。                       | 使用 Triton 实现 `store_kvcache`，按照分页 KV Cache 的 slot 布局进行特化写入，减少冗余索引和访存开销。                                                                                           |
| D   | Norm / RoPE / MLP | RMSNorm、RoPE、MLP 等模块主要由多个 PyTorch 小算子组成，kernel 数量较多，算子之间难以充分融合，容易产生额外的访存和调度开销。                         | RMSNorm 经实测对比后保持 PyTorch官方算子；RoPE 使用 FlashInfer 单核；SiluAndMul 使用 FlashInfer 融合算子；MLP 的 gate/up 投影合并为单个 GEMM                                                       |
| E   | 输入传输与采样           | 输入数据的 Host-to-Device 传输存在较多同步等待；采样过程未充分批量化，容易产生多次算子调用和主机-设备同步。                                         | 使用 `pin_memory` 配合 `non_blocking` 传输，使输入数据拷贝尽可能与 GPU 计算重叠；同时将采样合并为批量操作，减少同步和重复启动。                                                                                 |




## 3. Attention性能瓶颈

> [v2-attention.py](../../vllm-v2/src/layers/attention.py) | [v2-store](../../vllm-v2/src/pagedattention/store.py)

### 3.1 完整路径
我们再回顾一下Attention模块中的计算逻辑是什么。
- 首先，模型会算出来当前这一步的K和V，它们按照映射表把数据填到显存池对应的位置。
- 其次，Attention计算的时候，需要Q、K、V是处于连续张量的状态，但是K和V在硬件的内存池是东一块西一块不连续的。所以得先把这些散落的页按照页表拷贝出来，拼成一大块连续的张量。
- 最后，得到连续的 K/V 后，再与当前 Q 一起送入 SDPA，完成点积注意力计算。

理想的做法是：K和V老老实实呆在分页显存池里，由专门支持分页KV的Kernel根据页表读取对应的页，并且在读取的过程中完成Attention计算。举个例子来说，原本有两页题，理想做法是边看边算，但是我们v2版本的做法是先把题从各个地方抄到草稿纸上，然后统一计算。

> [!IMPORTANT]
> **抄**这个动作就是gather，然后再SDPA，整体多了一次大规模搬运。因此，v2 中每次计算Attention之前，系统需要先执行一次 `gather`，将分页保存的历史 K/V 复制成连续张量。这次复制会引入额外的显存带宽开销，也成为 Decode 阶段的重要性能瓶颈。

### 3.2 回顾PagedStore

内存池的物理布局如下所示：

```
k[layer_id, block_id, offset_in_block, H_kv, D]
v[layer_id, block_id, offset_in_block, H_kv, D]
```

其中 block_id 是物理页号，offset_in_block 是页内偏移，H_kv 为 KV 头数，D 为头维度。

write负责将本次算出来的KV写入内存池、gather负责将离散的历史KV拼成连续张量。需要注意的是，write 是增量写入，它只写入当前步新增的 token，而不会重写整段历史 K/V。这一点与 gather 的全量读取形成对比。

从实现上看，gather 有两个重要特征。

**第一**，它是全量读取。在 Decode 阶段，每一步真正新增的 token 只有一个，但 Attention 计算需要看到完整历史上下文。因此，gather 每次都需要读取从位置 0 到 seq_len - 1 的全部历史 K/V。

**第二**，它的目标是生成连续张量。页池中的 K/V 本身是分页保存的，物理上并不连续。gather 的作用就是将这些分散在不同 block 中的 K/V 按逻辑顺序重新拼接出来，形成一段连续的 [seq_len, H_kv, D] 张量。

因此，write 与 gather 在访问模式上并不对称。这种不对称性导致写入阶段只处理增量数据，但读取阶段都要把整段历史 K/V 重新组织一遍。分页机制虽然解决了 KV Cache 的存储管理问题，却没有消除 Attention 计算前的连续化成本。

### 3.3 Attention 层的前向流程

```python
# vllm-v2/src/layers/attention.py

def forward(self, q, k, v):
    ctx = get_forward_context()
    q, k, v = q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2)

    # 先写入本步 K/V
    store.write(self.layer_id, ctx.slot_mapping, k.transpose(1, 2), v.transpose(1, 2))

    if ctx.is_prefill:
        return self._prefill(q, k, v, ctx)
    return self._decode(q, ctx)


def _prefill(self, q, k, v, ctx):
    cached = ctx.cached_lens[0] if ctx.cached_lens else 0
    if cached == 0:
        # 冷启动：本步 K/V 已经是连续的，直接 SDPA，无需 gather
        return self._sdpa(q, k, v, is_causal=True).transpose(1, 2).contiguous()

    # 有前缀命中 / chunked：必须把整段 context gather 出来
    k_full, v_full = ctx.store.gather(self.layer_id, ctx.block_tables[0], ctx_len)
    k_full = k_full.unsqueeze(0).transpose(1, 2)  # [1, H, L, D]
    v_full = v_full.unsqueeze(0).transpose(1, 2)
    # 再构造 causal mask，对 (q_len × ctx_len) 做 SDPA
    out = self._sdpa(q, k_full, v_full, is_causal=False, attn_mask=attn_mask)
    return out.transpose(1, 2).contiguous()


def _decode(self, q, ctx):
    outs = []
    for b in range(q.shape[0]):                      # ← 按序列拆批
        ctx_len = ctx.context_lens[b]
        k_c, v_c = ctx.store.gather(                 # ← 每条序列 gather 整段历史
            self.layer_id, ctx.block_tables[b], ctx_len
        )
        k_c = k_c.unsqueeze(0).transpose(1, 2)
        v_c = v_c.unsqueeze(0).transpose(1, 2)
        outs.append(self._sdpa(q[b : b + 1], k_c, v_c, is_causal=False))
    return torch.cat(outs, dim=0).transpose(1, 2).contiguous()
```



### 3.4 带宽分析


| 参数           | 取值            |
| ------------ | ------------- |
| batch size B | 8             |
| 每条上下文长度 L    | 2048          |
| KV heads Hkv | 8             |
| head dim D   | 128           |
| dtype        | bf16（2 bytes） |
| 模型层数         | 28            |


单条序列单层一次 decode 需要消费的 K/V 数据量为（Attention 的有效访存）：

```
2 (K + V) * L * H_kv * D * 2 bytes
= 2 * 2048 * 8 * 128 * 2
= 8 MiB
```

但 v2 的 decode 路径上，这份 K/V 被反复搬动了 3 次：
| 阶段 | 访存 | 说明 |
| --------- | ---------- | ----------------- |
| gather 读  | 8 MiB      | 从分页池读 K/V         |
| gather 写  | 8 MiB      | 写进连续 buffer       |
| SDPA 再读   | 8 MiB      | 又从连续 buffer 读 K/V |
| **v2 合计** | **24 MiB** | 是有效访存的 3×         |


而 v3（FlashAttention paged）直接基于 `block_table` 读分页池，只读一次：8 MiB。

放大到整个模型来看：
| 方案 | 单步访存 | 换算 |
| ---------------- | -------------------------- | ------- |
| v2 gather 往返     | 16 MiB × 8 × 28 = 3.5 GiB  | ~3.7 ms |
| v2 attention 总访存 | 24 MiB × 8 × 28 = 5.25 GiB | ~5.6 ms |
| v3 attention 访存  | 8 MiB × 8 × 28 = 1.75 GiB  | ~1.9 ms |
> （按 4090 D ~1 TB/s、可持续 ~900 GB/s 估算；纯访存下界，不含计算时间。）

> [!IMPORTANT]
> 这 3× 的访存里，有 2×（gather 读写往返）是零计算开销。gather 成本随 L 线性增长。L=4096 时 v2 单步 attention 访存翻倍到 ~10.5 GiB。这正是 v3 改用 paged attention 要消除的核心浪费。

### 3.5 实测验证

上面的带宽分析是**访存下界**。用 `torch.profiler` + 细粒度 L 扫描，隔离测量单层 decode attention。

 **耗时随 L 增长**（B=8、单层、bf16，us）：
| L    | v2 gather | v2 decode | v3 decode | v2/v3 加速比 |
| ---- | --------- | --------- | --------- | --------- |
| 256  | 212       | 578       | 26        | 22.6x     |
| 512  | 208       | 576       | 24        | 23.6x     |
| 1024 | 208       | 575       | 32        | 18.2x     |
| 2048 | 221       | 583       | 52        | 11.3x     |
| 4096 | 378       | 598       | 154       | 3.9x      |
| 8192 | 704       | 975       | 297       | 3.3x      |


**breakdown**（L=2048, B=8，50 次迭代聚合）：


| 路径  | kernel 数 | 总 GPU 时间 | 最大单项                     |
| --- | -------- | -------- | ------------------------ |
| v2  | **1650** | 15394 us | gather 9211 us，占 60%     |
| v3  | **100**  | 2684 us  | flash_attn 2551 us，占 95% |


- v2 的 kernel 数是 v3 的 **16.5 倍**；其中 gather 占 60% GPU 时间。
- v3 单 kernel 完成，GPU 时间与 wall time 几乎相等；v2 的 GPU 时间只占 wall time 的一半，另一半被 1650 个 kernel 的 CPU launch 间隙吃掉。

这正是 decode 批量成为 v3 最大单点收益（见 [02-实测证据](./02-实测证据.md) decode 6.7~20x）的根源。

## 4. Decode
### 4.1 Decode 的计算特征

Decode 阶段，模型每次只为每条序列生成一个 token。以单条序列为例，一步 decode 需要依次经过 embedding、RMSNorm、QKV projection、RoPE、Attention、O projection、RMSNorm、MLP、lm_head 等模块。

每个模块内部又包含若干 CUDA kernel。例如一个 Linear 层可能涉及权重加载、矩阵乘法、偏置加法等多个 kernel；Attention 内部还有 write、gather、SDPA 等操作。因此，单步 decode 虽然总计算量不大，但要串行执行的 kernel 数量很多，通常有数十个甚至上百个。

### 4.2 执行模式

在深入 eager 的执行流程之前，需要在这里提到两个概念：静态图和动态图，后面几节都建立在这个背景上。

深度学习框架执行算子，历史上分化出两条路线。

一条是**静态图**（define-and-run）。TensorFlow 1.x 是典型代表。使用者先声明一张完整的计算图，框架对整张图做一遍优化，再交给后端统一执行。好处是框架看得见全貌，可以做算子融合、内存复用、并行调度这类全局优化；代价是写起来和调起来都别扭，Debug非常困难。

另一条是**动态图**（define-by-run），PyTorch 的 eager 模式走的就是这条路。写完代码后框架立刻在当前设备上把它执行掉。所见即所得，打断点、打印中间结果都顺手。这套体验让 PyTorch 在研究和调试场景里迅速占了上风，也成了今天深度学习框架的默认形态。

> [!NOTE]
> 严格说，eager 的正向执行本身并不构建图，动态图这个称呼源自 PyTorch autograd 在反向传播时每次 forward 都当场重建计算图（算完即弃）的机制。社区借此泛指**边定义边执行、无预编译图**的执行风格。

eager 的代价藏在它的灵活性背后。因为框架对接下来还要跑什么一无所知，每写一行算子，都要当场走一遍从 Python 解释器到 CUDA 驱动的完整提交链路。

CUDA Graph 的出发点就是为了给 eager 补上全局视图，但是又不逼使用者退回静态图的写法。它源自 NVIDIA 在 2019 年前后为 CUDA 引入的 Graph API。

即在某个时机，把一段 eager 代码实际提交的 kernel 序列原样录下来，形成一张有向图；以后再执行这段逻辑，就不再逐个 launch，而是把整张图一次提交给 GPU 回放。

也就是说，CUDA Graph 是在**eager 的开发体验**和**静态图的批量提交**之间做了Trade-off。平时照常写 eager 代码，只有结构固定、反复执行的热路径才把它录成图。

而 decode 恰好就是这样的热路径。一步 decode 里的 kernel 顺序和形状每次都一样，天然适合录制一次、反复回放。

### 4.3 Eager 模式的执行方式

在 PyTorch 的 eager 模式下，每个 CUDA 操作都由 CPU 端发起。具体流程如下：

CPU 执行到某一行代码，例如 `torch.matmul(a, b)`，它会调用 PyTorch 的 C++ 后端，后端再调用 CUDA driver API，把 kernel 的启动参数、网格维度、块维度、输入输出指针等信息打包，通过系统调用提交给 GPU。GPU 收到命令后，把 kernel 放入执行队列，待前面的 kernel 完成后开始执行。

这个过程中，CPU 和 GPU 之间存在多次交互。每个 kernel 都要走一遍完整的 launch 流程。
Kernel launch 本身需要消耗固定的时间。它包括：

1. CPU 端参数校验和准备；
2. CUDA Runtime / Driver 的软件提交开销，包括驱动交互、命令入队、参数封装等。
3. CUDA driver 对命令的编码和入队；
4. CPU 与 GPU 之间的命令传输。

在现代 GPU 上，单个 kernel 的 launch 时间通常在几微秒到几十微秒之间。这个开销与 kernel 内部的算术计算量基本无关，主要取决于 launch 路径本身。

当模型较大、batch 较大、计算密集时，每个 kernel 的执行时间很长，launch 开销被淹没在计算时间中，占比很小。

> [!IMPORTANT]
> 但 decode 阶段恰恰相反。每次Decode的batch通常不大，每个kernel处理的数据量很小，执行时间很短。此时 launch 开销在总时间中的占比急剧上升。这种状态称为 launch-bound。

### 4.4 CUDA Graph 的基本原理

CUDA Graph 是 NVIDIA 提供的一种执行机制，其核心思想是**预先录制、批量回放**。

> 参考资料: [浅谈CUDA Graph在llm推理的作用](https://zhuanlan.zhihu.com/p/715863693) | [CUDA Graph优化的底层原理分析](https://developer.aliyun.com/article/1392808) | [Nvidia CUDA Graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)

**录制阶段**。CPU 按正常流程依次 launch 各个 kernel，但 CUDA runtime 会把这些 launch 操作记录下来，构建一张有向图。图中的节点代表 kernel 或内存操作，边代表依赖关系。这张图完整描述了一步 decode 中所有 GPU 操作的执行顺序和数据依赖。

**回放阶段**。CPU 只需向 GPU 提交一次命令，整幅图就被一次性送入 GPU 的执行队列。GPU 按照图中记录的依赖关系自主调度各个节点，无需 CPU 再逐个介入。

> [!NOTE]
> 需要强调的是，CUDA Graph 不改变任何计算结果。图中每个 kernel 的输入输出、执行逻辑与 eager 模式完全一致。它优化的只是执行路径上的调度开销。



## 5. KV 写入
### 5.1 KV Cache 的写入路径

模型每生成一个新 token，都要把这个 token 对应的 K 和 V 写入分页 KV cache。在 v2 中，这一操作由 `PagedStore.write` 完成，底层调用的是 PyTorch 的 `index_copy_`。

### 5.2 index_copy_ 的工作方式

`index_copy_` 是 PyTorch 提供的一个通用索引写算子。它的语义是给定一个目标张量、一组索引和一个源张量，把源张量中的元素按索引写入目标张量的指定位置。

在 v2 的代码中，调用方式如下：

```python
flat_k.index_copy_(0, slot_mapping, k.reshape(n, flat_dim))
flat_v.index_copy_(0, slot_mapping, v.reshape(n, flat_dim))
```

这里，`flat_k` 和 `flat_v` 是页池的扁平化视图，`slot_mapping` 记录了当前 token 应该写入的物理位置，`k` 和 `v` 是当前步算出的 KV 张量。

### 5.3 为什么通用算子不够高效

`index_copy_` 的设计目标是通用性，它需要处理任意形状的输入和任意的索引模式。这种通用性带来了几个性能代价。

第一，**缺乏针对 KV cache 布局的优化**。`index_copy_` 不知道目标内存是分页池，也不知道写入模式通常是连续的块级写入。它按照通用的索引分散逻辑执行，无法利用分页内存的局部性特征做优化。

第二，**没有融合**。一个理想的 KV cache 写入内核应该把数据从计算结果直接搬运到分页池的对应位置，中间不需要额外的中间表示或多次内存访问。但 `index_copy_` 作为独立算子，它的执行路径中包含了参数校验、索引边界检查、线程调度等通用逻辑，这些在 KV cache 场景下都是不必要的开销。

第三，**调用频率高**。每个 Transformer 层都要执行一次 `index_copy_`，每一步 decode 都要执行，prefill 阶段同样如此。对于 28 层的模型，每步就要执行 28 次 KV 写入。单独一次 `index_copy_` 的耗时可能只有几十微秒，但乘以层数和步数后，累计开销相当可观。

### 5.4 与读取瓶颈的叠加

> [!IMPORTANT]
> 这个**写入瓶颈**和上边讨论的 **gather** 瓶颈使得效率进一步变低。

在 v2 的实现中，同一份 KV 数据在热路径上经历了两次低效操作。写入时，`index_copy_` 以通用的分散方式把数据写入分页池的各个位置；读取时，gather 又以通用的索引方式把这些分散的数据重新拷贝出来，拼成连续张量。

理想情况下，写入和读取都应该由专门设计的内核完成。写入时，数据应该直接从计算结果搬运到分页池。读取时，Attention 内核应该直接按页表索引分页池，不需要显式的 gather。

## 6. Norm、RoPE、MLP 未算子融合
### 6.1 小算子的执行特征

v2 在 eager 模式下被拆成了多个独立的 PyTorch 算子。这些算子单个来看计算量都不大，但数量很多，分布在每一层 Transformer 的多个位置。主要包括 RMSNorm、RoPE 和 MLP 中的激活与门控计算。

这些模块的共同特点是算术强度低。它们更适合与相邻操作融合执行，而不是作为独立算子逐个 launch。

### 6.2 RMSNorm 的拆分

RMSNorm 的计算公式为：

```
output = x / sqrt(mean(x^2) + eps) * weight
```

在 v2 的 eager 实现中，这个公式被拆成多个步骤，每一步对应一个独立的 CUDA kernel：

```
第一步，把输入从低精度（如 bf16）转成 float32，用于数值稳定性。

第二步，对转完精度的张量做逐元素平方。

第三步，在指定维度上求均值，得到均方根值。

第四步，加上 epsilon 后取平方根的倒数（rsqrt）。

第五步，把输入与 rsqrt 的结果逐元素相乘，完成归一化。

第六步，乘上可学习的 weight 参数。

第七步，把结果转回 bf16。
```

这七个步骤中，除了第三步的 reduce 操作外，其余都是逐元素变换。每个步骤执行完后，结果都要写回显存，下一步再从显存读取。一个本来可以用一次遍历完成的计算，被拆成了多次显存读写。

### 6.3 RoPE 的拆分

RoPE（Rotary Position Embedding）的作用是给 Q 和 K 注入位置信息。它的核心操作是对 Q/K 张量中相邻的两个维度做旋转变换，旋转角度由位置编码决定。

在 eager 模式下，RoPE 通常按以下步骤执行：

```
第一步，根据序列长度和头维度，预计算旋转角度（sin 和 cos 值）。

第二步，把 Q 或 K 张量按最后一个维度拆成两半。

第三步，对两半分别做逐元素的 sin 和 cos 加权。

第四步，把加权后的两半重新组合。
```

这些步骤同样涉及多次张量拆分、逐元素运算和拼接。每一步都是独立的 kernel launch，中间结果都要经过显存。

### 6.4 SiluAndMul 的拆分

MLP 模块中的门控计算通常采用 SwiGLU 结构，即：

```
gate = silu(x @ W_gate)
up = x @ W_up
output = gate * up
```

在 v2 中，这个流程被进一步拆分：

```
第一步，对输入 x 分别做 gate 投影和 up 投影，得到两个独立的线性输出。这是两个独立的矩阵乘法 kernel。

第二步，对 gate 输出做 silu 激活函数，这是一个独立的逐元素 kernel。

第三步，把 silu 的结果与 up 的结果逐元素相乘，这又是一个独立的 kernel。
```

理想情况下，gate 投影和 up 投影可以在同一个 kernel 中完成，silu 和逐元素乘法也可以紧跟其后融合执行。但在 eager 模式下，它们被拆成了独立的算子，中间结果都要落盘到显存。

### 6.5 未融合的根本问题

上述拆分带来的性能损失可以从三个维度来理解。

第一，**kernel launch 开销**。每个独立算子都要走一次完整的 launch 流程。RMSNorm 拆成七个步骤，就是七次 launch；RoPE 拆成四步，就是四次 launch；SiluAndMul 拆成三步，就是三次 launch。一层 Transformer 中这些算子累加起来，单步的 launch 次数相当可观。

第二，**中间张量占用显存**。每个步骤的输出都需要分配显存空间来保存。例如 RMSNorm 的平方结果、均值结果、rsqrt 结果，都需要临时张量。这些中间张量不仅占用显存，还增加了内存分配和释放的开销。

第三，**显存带宽的重复消耗**。每个步骤都要从显存读取输入，计算后再写回显存。以 RMSNorm 为例，输入数据被读取了多次，中间结果被写回多次。而融合内核只需要读取一次输入，在寄存器或共享内存中完成所有中间计算，最后写回一次结果。对于算术强度低的操作，显存带宽往往是瓶颈，重复读写直接放大了这个问题。

### 6.6 融合的原理

融合的核心思想是：把多个计算步骤合并到一个 CUDA kernel 中执行，避免中间结果写回显存。

以 RMSNorm 为例，融合后的内核只需要启动一次。每个线程块读取输入数据到共享内存或寄存器，依次完成转精度、平方、求和、rsqrt、乘 weight 等操作，最后把结果一次性写回显存。中间结果始终留在片上内存，不需要经过显存。

RoPE 的融合类似。融合内核可以直接在读取 Q/K 的同时计算旋转角度，就地完成旋转变换，然后直接输出到下一层需要的格式。

SiluAndMul 的融合则可以把 gate 和 up 的线性投影、silu 激活、逐元素乘法全部串在一个 kernel 中。甚至更进一步，可以把前面的 RMSNorm 和后面的线性投影也融合进来，形成更大的融合块。

> [!IMPORTANT]
> 融合带来的收益不是来自计算量的减少，而是来自显存读写次数的减少和 kernel launch 次数的降低。对于 decode 这种计算量小、带宽敏感的场景，这种减少尤为关键。


### 6.7 与 CUDA Graph 的关系

CUDA Graph 把多个 kernel 的 launch 过程录制成一张图，回放时只需一次提交。这消除了回放阶段的 CPU launch 开销和 kernel 间隙时间。但图内部每个 kernel 仍然是独立执行的，它们之间的中间张量仍然要写回显存，显存带宽的重复消耗依然存在。

> [!NOTE]
> 换句话说，CUDA Graph 解决的是调度层面的开销，而融合解决的是计算层面的内存效率。两者可以叠加：先用融合减少 kernel 数量和显存读写，再用 CUDA Graph 进一步压缩 launch 开销。



### 6.8 适用场景

未融合算子的影响在不同场景下表现不同。

在 decode 阶段，如果已经启用了 CUDA Graph，部分 launch 开销被图吸收，但未融合带来的显存带宽浪费仍然存在。对于小模型、小 batch 的 decode，计算量极小，显存带宽的重复消耗可能成为主导因素。

在 prefill 阶段，通常没有 CUDA Graph（因为 prefill 的序列长度变化大，难以录制固定图），此时未融合算子的 launch 开销和显存带宽浪费都会完全暴露出来。Prefill 阶段的计算量虽然比 decode 大，但 kernel 数量多、中间张量大，仍然会受到明显影响。

在长上下文 prefill 中，RMSNorm 和 RoPE 需要处理很长的序列，未融合导致的重复显存读写会被进一步放大。

因此，算子融合的收益在 prefill 阶段通常比在 decode 阶段更直接；在 decode 阶段，它与 CUDA Graph 形成互补，共同优化单步执行效率。

## 7. 输入 H2D 与采样

> [!NOTE]
> 这一节讨论的内容在整体性能差距中属于第二梯队。在单流、小 batch 的 decode 场景下，这些开销通常被 Attention gather 和 CUDA Graph 的差距覆盖。只有在高并发的 Continuous Batching 场景下，大 batch、多参数传递、多次采样时，这些瓶颈才会明显暴露出来。

### 7.1 v2 的输入上 GPU 方式

v2 中把主机数据搬上 GPU 的统一入口位于 `engine/model_runner.py`：

```python
def _tensor(self, data, dtype=torch.long) -> torch.Tensor:
    return torch.tensor(data, device=self.device, dtype=dtype)
```

Decode 的每一步中，多处调用这个函数来创建 GPU 张量：

```python
ids = self._tensor(input_ids).unsqueeze(-1)
pos = self._tensor(positions).unsqueeze(-1)
slot_mapping = self._tensor(slots)
```

此外，前缀 gather 中的 `block_table` 等数据也采用类似方式直接上设备。

这种写法的核心问题在于拷贝的同步性。`torch.tensor(..., device=cuda)` 从 pageable 主机内存创建张量并直接指定 CUDA 设备，其执行特征如下：

> [!NOTE]
> 第一，源内存位于 pageable host 内存，未使用 pinned memory。CUDA 的 H2D 拷贝对 pageable 内存通常需要经过额外的 bounce buffer，拷贝路径更长，且更难与 GPU 计算重叠。
>
> 第二，默认行为是同步拷贝。调用返回时，数据已经完整到达设备内存，CPU 线程在此期间被阻塞。


单就一次拷贝而言，数据量很小。`input_ids` 只有 B 个整数，`positions` 和 `slots` 数量级相当。单次拷贝的耗时在微秒级别，并不显眼。
但问题在于频率和路径位置。一步 decode 中要执行多次这样的小拷贝，包括输入 ID、位置编码、slot 映射，有时还包括采样参数。这些拷贝散落在模型执行的关键路径上，每次拷贝都会阻塞 CPU，使其无法继续准备下一步的数据或发射后续 kernel。当 batch 变大、prefill 变长时，`input_ids`、`slot_mapping`、`block_tables` 的数据量随之增长，同步拷贝的阻塞效应更加明显。

### 7.2 v2 的采样方式

Decode 阶段模型输出 logits 后，v2 的采样逻辑如下：

```python
logits = self.model.compute_logits(h[:, -1:]).squeeze(1)
return [self._sample_one(logits[i : i + 1], seq) for i, seq in enumerate(seqs)]
```

`_sample_one` 对每条序列单独执行：

```python
def _sample_one(self, logits, seq):
    if seq.temperature is not None and seq.temperature <= 0:
        return int(torch.argmax(logits, dim=-1).item())

    def opt(v, dtype):
        return None if v is None else torch.tensor([v], device=self.device, dtype=dtype)

    token = self.sampler(
        logits,
        opt(seq.temperature, ...),
        opt(seq.min_p, ...),
        opt(seq.top_p, ...),
        opt(seq.top_k, ...),
    )
    return int(token.item())
```

这段代码存在几个层面的低效。

> [!NOTE]
> 第一，Python 循环遍历 batch 中的每条序列。宿主机开销与 batch 大小成正比。
>
> 第二，每条序列的采样参数都要临时构造 `torch.tensor([v], device=...)`。这意味着每处理一条序列，就要为 temperature、top_p、top_k、min_p 等参数分别创建小张量并执行 H2D 拷贝。一个 batch 有 B 条序列，参数有多个维度，总的小张量创建次数为 B 乘以参数个数。
>
> 第三，每次调用 `.item()` 都会触发 CPU 与 GPU 之间的硬同步。GPU 必须完成该张量的所有计算，把结果传回主机，CPU 才能继续执行。在 `_sample_one` 中，greedy 路径有一次 `.item()`，sampling 路径又有一次 `.item()`。batch 中每条序列都要经历这样的同步。

Prefill 阶段的情况更为严重。v2 的外层逻辑是逐条序列执行 `run_prefill_one`，每条序列单独组张量、单独 forward、单独采样。多条 prefill 请求之间完全串行，无法享受 batching 的收益。

Sampler 本身的算法实现，包括 softmax、top-p 裁剪、multinomial 采样等，功能是正确的。问题出在它的调用方式上。Sampler 被包裹在逐条处理加同步取回的外壳中，Continuous Batching 在 Attention 和 MLP 层面实现的合批收益，无法延伸到采样这一段。

### 7.3 v3 的优化

v3 针对输入管线和采样做了两处关键改进。

#### 7.4.1 H2D
v3 的输入构造改为：

```python
input_ids = torch.tensor(input_ids_list, dtype=torch.int64, pin_memory=True).to(
    device, non_blocking=True
)
positions = torch.tensor(..., pin_memory=True).to(device, non_blocking=True)
slot_mapping = torch.tensor(..., pin_memory=True).to(device, non_blocking=True)
```

采样参数同样如此处理，一次构造长度为 B 的向量。

> [!TIP]
> `pin_memory=True` 把主机内存分配在 pinned 区域，CUDA 可以直接通过 DMA 从 pinned 内存向设备传输数据，不需要经过 bounce buffer。
>
> `non_blocking=True` 让拷贝操作异步提交。CPU 在提交拷贝命令后立即返回，可以继续执行后续代码，有机会与 GPU 上已有的工作重叠。需要说明的是，这并非万能优化。如果 GPU 当时处于空闲状态，异步拷贝仍可能很快变成实际上的同步等待。但在 GPU 负载饱满的场景下，异步提交可以让 CPU 提前完成调度准备，减少整体空闲。



#### 7.4.2 采样：整 batch 一次执行

v3 的采样逻辑改为：

```python
temperatures = torch.tensor([s.temperature for s in seqs], ..., pin_memory=True).to(...)
# top_ps、top_ks、min_ps 同样一次构造

return self.sampler(
    logits, temperatures, top_ps=top_ps, top_ks=top_ks, min_ps=min_ps
).tolist()
```

Sampler 被实现为 `nn.Module`，对 `[B, vocab]` 的 logits 做温度缩放、top-k、top-p、min-p 处理，然后一次产出 B 个 token。具体地，启用 top-k 时先用 `topk` 把候选集从 vocab 归约到 `max_k`，top-p / min-p 在这个有序小空间内共用同一次 `softmax` 与 `cumsum` 完成过滤，再用 `multinomial` 采样、按有序索引 `gather` 回原 token id。greedy 解码和采样解码可以在同一个 batch 内通过 mask 混合处理。

> [!TIP]
> 与 v2 相比，改进包括：
>
> 第一，采样参数从每条序列临时构造改为整 batch 一次构造，减少了小分配和小拷贝的次数。
>
> 第二，采样计算从 B 次独立的 Sampler 调用改为一次 batched forward，消除了 Python 循环开销和多次 kernel launch。
>
> 第三，结果取回从 B 次 `.item()` 改为一次 `.tolist()`，CPU-GPU 同步次数从 B 次降为 1 次。
>
> 第四，chunked prefill 中未完成的 chunk 可以跳过 LM-head 投影和采样，避免无用计算。
