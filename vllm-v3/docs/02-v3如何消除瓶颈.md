# 02 · v3 如何消除 v2 的瓶颈

> 承接 [01-v2性能瓶颈](./01-v2性能瓶颈.md)，对每个瓶颈给出 v3 的具体改法。
> 代码路径均为 `vllm-v3/src/`。

## 瓶颈 A → FlashInfer 分页注意力（eliminate gather）

**v2 的问题**：K/V 先 gather 成连续张量再 SDPA，热路径上 KV 被反复搬运（单步最多 ~1.75 GiB）。

**v3 的改法**：

1. **KV 布局对齐 FlashInfer NHD**：
   ```python
   # memory/kv_ops.py — pool: [2(KV), num_layers, num_blocks, block_size, n_kv, head_dim]
   self.kv_cache = torch.empty(...)  # 一次大池分配
   ```
2. **写入用 Triton 特化 kernel**（不再 `index_copy_`）：
   ```python
   # layers/attention.py forward 里，按 slot_mapping 就地写入
   store_kvcache(k, v, k_4d_2d, v_4d_2d, meta.slot_mapping)
   ```
3. **读取交给 FlashInfer**：`BatchDecodeWithPagedKVCacheWrapper` / `BatchPrefillWithPagedKVCacheWrapper` 直接消费 `block_table`，**不再 gather**。

**知识点**：PagedAttention 的 CSR 格式（`indptr`/`indices`/`last_page_len`）；分页 KV 省碎片 vs 连续 KV 省搬运的权衡。

## 瓶颈 B → CUDA Graph 消除发射地板

**v2 的问题**：decode 每步数十次 kernel 发射，CPU 下发速度 < GPU 执行速度，GPU 空转。

**v3 的改法**：

```python
# core/cuda_graph.py — 捕获固定 bs 的 decode 图，重放时只更新静态 buffer
with torch.cuda.graph(graph, pool=graph_pool):
    self.outputs[:bs] = self.model(input_ids=..., positions=...)
# 每步：copy_ 覆盖 input/positions/slot_mapping → wrapper.plan() → graph.replay()
```

**知识点**：CUDA Graph 只消除调度开销，不改变计算；静态内存约束要求所有输入输出预分配；graph pool 复用减少碎片。详见 [04](./04-CUDA-Graph.md)。

**v3 更进一步**：把 CG 推广到 prefill 首 chunk：**piece CG**——按 (bs, L) 分片捕获固定形状图，短 prompt 从 20ms 压到 3.4ms。前缀命中续 chunk 走 eager（radix 已跳过 KV 重算，剩余 token 较少）。

> 早期曾实现 **Continuation CG**（续 chunk 的 q_len 网格图，利用 FlashInfer kernel grid
> 只依赖 q_len 的特性固定图 + 动态 replan KV 元数据），因 `len(seqs)==1` 限制在并发
> 前缀命中场景几乎不命中，收益/成本比差，已移除。

详见 [10](./10-Prefill-CUDA-Graph.md)。

## 瓶颈 C → Triton KV 写入

**v2 的问题**：`index_copy_` 通用 scatter，28 层每步 28 次。

**v3 的改法**：Triton `store_kvcache` 特化 kernel，按 `[num_tokens, n_kv, head_dim]` 直接 scatter 到 NHD 布局：

```python
# memory/kv_ops.py
@triton.jit
def _store_kvcache_kernel(k, v, k_4d, v_4d, slot_mapping, ...):
    # 一个 program 处理一个 token 的 KV，直接写入 slot 对应位置
```

**知识点**：通用 scatter vs 特化 scatter；Triton 的 `tl.store` 按 index 写入；kernel 按 token 数并行。

## 瓶颈 D → Triton RMSNorm / RoPE 融合

**v2 的问题**：RMSNorm 拆 7 步、RoPE 拆 4 步、SiluAndMul 拆 3 步，中间张量反复写 HBM。

**v3 的改法**：全部单 kernel 融合，中间量留在寄存器/SRAM：

```python
# layers/layernorm.py — Triton RMSNorm：一次读入，算 rms，乘 weight，一次写出
# layers/rotary.py — Triton RoPE：一次读入，旋转，一次写出
```

**知识点**：算子融合消除的是一次次 HBM 读写而非计算量；算术强度低的算子对带宽更敏感。详见 [08](./08-RMSNorm.md)。

## 瓶颈 E → pin_memory 异步管线 + 整批采样

**v2 的问题**：`torch.tensor(..., device=cuda)` 同步小拷贝；采样逐序列 `.item()` 同步。

**v3 的改法**：

```python
# engine/input_builder.py — pinned host → 异步 H2D
torch.tensor(input_ids_list, dtype=torch.int64, pin_memory=True).to(device, non_blocking=True)

# engine/sampler.py — 整 batch 一次采样，一次 .tolist() 取回
return self.sampler(logits, temperatures, top_ps=..., top_ks=..., min_ps=...).tolist()
```

**知识点**：`pin_memory` 让 DMA 绕过 bounce buffer；`non_blocking` 让拷贝与计算重叠；`.item()` 是 CPU-GPU 硬同步，按批次聚合为一次 `.tolist()`。详见 [05](./05-Input.md) 和 [06](./06-Sampler.md)。
