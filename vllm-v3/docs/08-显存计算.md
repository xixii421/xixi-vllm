# 显存计算
> 面试经常会给出一个配置，计算相关的显存情况。

## 1. 公式
```text
总显存 = 权重 + KV Cache + 余量(约 1~2 GiB)
```

权重和 KV 是两块大头，我们在面试过程中只需要计算这两块即可。

这里要提一嘴的是，模型名字里的 B 是 Billion（十亿参数），0.6B 就是 6 亿个参数，8B 就是 80 亿。

## 2. 权重

```text
权重(GiB) = 参数量(B) × 每参数字节
```

| 精度 | 每参数 | 口算 |
| --- | ---: | --- |
| bf16 / fp16 | 2 字节 | 参数量(B) × 2 |
| fp8 | 1 字节 | 参数量(B) × 1 |
| fp32 | 4 字节 | 参数量(B) × 4 |

例子：Qwen3-0.6B 用 bf16 是 `0.6 × 2 = 1.2 GiB`；Llama-3-8B 是 `8 × 2 = 16 GiB`；Llama-70B 是 `70 × 2 = 140 GiB`。

## 3. KV Cache

KV 里存的是每一层、每个 token 的 K 和 V，所以公式就是把这几样乘起来：

```text
KV = 2 × L × H_kv × d × T × B × b
```

| 符号 | 含义 | 注意 |
| --- | --- | --- |
| 2 | K 和 V 两份 | 漏乘 2 是最高频错误 |
| L | 层数 | 配置直接给 |
| H_kv | KV 头数 | GQA 用 `num_key_value_heads`，不是 query 头 |
| d | 每头维度 | 没给就用 `hidden_size / num_attention_heads` |
| T | 缓存长度 | prompt 加已生成，不是只算 prompt |
| B | 并发条数 | beam 再乘 beam 数 |
| b | 每元素字节 | bf16/fp16 = 2 |

直接算上边这个公式很难记下来，可以分开来思考：

**第一步，每 token 多少字节。** 把 T 和 B 拿掉，假设精度是 bf16，则系数为 4（2 × b），这里要乘以2，是因为K和V都要存储。

```text
每 token = 4 × L × H_kv × d   (单位字节)
```

**第二步，一条请求多少。** 乘上下文 T。口算把 4K 当成 4：

```text
单条请求 = 每 token(KB) × (T / 1024)   (MB 量级)
```

**第三步，全部并发多少。** 乘 B，就是 KV 总占用。



## 4. 三套模型走一遍

以下都是 bf16、B=1。第一行 Qwen3-0.6B 是 v3 用的模型，后面两行是面试高频。

| 模型 | L | H_kv | d | 每 token | 4K 一条 | 32K 一条 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | 28 | 8 | 128 | 112 KB | 0.44 GiB | 3.5 GiB |
| Llama-3-8B | 32 | 8 | 128 | 128 KB | 0.50 GiB | 4.0 GiB |
| Llama-70B | 80 | 8 | 128 | 320 KB | 1.25 GiB | 10.0 GiB |

Qwen3-0.6B 是 `4 × 28 × 8 × 128 = 114688` 字节约 112 KB；Llama-8B 把 28 换成 32 就是 128 KB；Llama-70B 换成 80 就是 320 KB。

完整的口算示范，以 Llama-3-8B、4K 上下文、32 并发、bf16 为例：

```text
权重     = 8 × 2 = 16 GiB
每 token = 4 × 32 × 8 × 128 = 128 KB
单条请求 = 128 KB × 4 = 512 MB
KV 总量  = 512 MB × 32 = 16 GiB
总显存   = 16 + 16 + 2(余量) ≈ 34 GiB
```

一块 80 GiB 的 H100，权重 16 加余量 2，剩 62 GiB 给 KV，单条 0.5 GiB，约 `62 / 0.5 ≈ 124` 路并发。KV 换成 fp8，单条腰斩到 0.25 GiB，并发翻倍到约 240 路。

面试官想听的因果链就是这三步：权重固定，KV 随上下文和并发变化，精度和并发也是会变化的。

## 5. 真题

**题 1：KV Cache 怎么算，哪些参数决定占用？** 写 `2 × L × H_kv × d × T × B × b`，逐个解释符号：2 是 K/V 两份，H_kv 在 GQA 里小于 query 头，T 含已生成 token，b 由精度定。KV 线性涨，长上下文服务里 KV 才是瓶颈。追问 GQA 为什么省显存：多个 query 头共享 KV 头，H_kv 变小，公式线性下降。Qwen3-0.6B 的 8 头对 16 头就是省一半。

**题 2：Llama-70B 走一遍。** 80 层、8 头、128 维、fp16。每 token `4 × 80 × 8 × 128 = 320 KB`，4K 一条约 1.25 GiB。4 张 H100 跑 TP=4，权重每卡约 35 GiB，剩约 40 GiB，能塞 `40 / 1.25 ≈ 32` 条 4K 请求。

**题 3：Llama-8B 在 80 GiB 的 H100 上能跑多少并发？** 权重 16 GiB 扣 2 余量，剩 62 GiB；单条 4K 的 KV 0.5 GiB，`62 / 0.5 ≈ 124` 路。fp8 KV 约 248 路。

**题 4：GQA / MHA / MQA 对比。** 32 层、128 维、fp16，每 token 是 `4 × 32 × H_kv × 128 = 16 KB × H_kv`。MHA 32 头 512 KB/token，GQA 8 头 128 KB/token，MQA 1 头 16 KB/token。4K 下分别是 2 GiB、0.5 GiB、0.06 GiB。GQA 相对 MHA 正好除以 4。
