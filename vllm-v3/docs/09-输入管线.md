# 输入管线：Batch 的数据准备与封装

> 对应 [01-v2性能瓶颈](./01-v2性能瓶颈.md) — **瓶颈 E（输入传输）**。

在 vllm-v3 中，调度器负责管理变长的请求序列，而模型执行器（Model Runner）需要高度规整的 GPU 张量来执行并行计算。`data/batch.py` 里的 `Batch` 就是连接这两者的核心桥梁——它把参差不齐的 Python 列表高效、紧凑地转换为 GPU 算子（如 FlashAttention）能直接消费的张量格式。

> [batch.py](../src/data/batch.py)（`Batch.build_decode` / `Batch.build_prefill`；`ScheduledBatch` 作为 compute 层的显式接口）

## 一、为什么需要这个模块？

1. **调和“变长业务”与“定长计算”的矛盾**：GPU 擅长固定形状的密集矩阵运算，但批次由长度各异的序列组成。必须把参差不齐的 Python 列表紧凑地打包成特定张量格式。
2. **常驻 buffer 复用**：前向需要十余个元数据（`cu_seqlens`、`slot_mapping`、`block_tables` 等）。`Batch` 一次性预分配这些常驻 GPU 张量，每步只 `copy_` 实际数据，避免反复分配。
3. **隐藏底层复杂性**：上层调度逻辑不应关心 `slot_mapping` 是如何通过 `block_size` 算出来的，`Batch` 内聚了这些计算。

## 二、Prefill 阶段：紧凑打包

Prefill 需要一次性处理用户输入的完整 Prompt（或一个 chunk）。`build_prefill` 采用**紧凑打包**而非 padding：

```python
# data/batch.py build_prefill —— 逐序列累加 cu_seqlens
cu_q = [0]; cu_k = [0]
for s in seqs:
    start = s.num_cached_tokens
    n = s.num_scheduled_tokens
    end = start + n
    ids.extend(s.token_ids[start:end])
    positions.extend(range(start, end))
    slots.extend(slots_for_range(s.block_table, start, end, block_size))
    cu_q.append(cu_q[-1] + n)
    cu_k.append(cu_k[-1] + end)     # 含缓存前缀的累计长度
    ...
has_cache = cu_k[-1] > cu_q[-1]     # 是否命中前缀（续 chunk）
```

- **累积序列长度 `cu_seqlens_q` / `cu_seqlens_k`**：`cu_q` 标记每个序列的 Q 边界、`cu_k` 标记 K（含缓存前缀）的边界。这是 FlashAttention varlen 接口处理变长 batch 的标准 CSR 输入，算子借此在单次 kernel 中并行处理所有序列，不跨序列交叉计算。
- **细粒度 `slot_mapping`**：`slots_for_range` 为每个待写 token 生成物理槽位索引——序列 token 分散在非连续物理块中，这里用纯 CPU 整数运算提前算好映射，避免 GPU 端动态寻址。

> 与 padding 相比：padding 会算 `[B, max_len]` 的无效零；紧凑打包只算真实 token，有效计算量可削减 40%~90%，且 SRAM 不被 padding 数据占据。

## 三、Decode 阶段：极简输入提取

Decode 每步只接收上一 token，计算量极小，数据准备延迟必须压到极致：

```python
# data/batch.py build_decode
self._cp(self.input_ids[:bs],    [s.last_token for s in seqs], torch.int64)
self._cp(self.positions[:bs],    [len(s) - 1 for s in seqs], torch.int64)
self._cp(self.slot_mapping[:bs], [self._decode_slot(s, block_size) for s in seqs], torch.int32)
self._cp(self.cache_seqlens[:bs], [len(s) for s in seqs], torch.int32)
self._fill_block_tables(seqs)
```

- `input_ids` 直接取 `last_token`、`positions` 取 `len(seq) - 1`；
- `cache_seqlens` 给出每条序列的当前总长度，配合 `block_table` 让 FlashAttention 定位历史 KV 的读取边界。

## 四、变长到定长：block_table 的 -1 padding

GPU 要求规整的二维张量，`_fill_block_tables` 把参差的 `block_table` 补齐：

```python
def _fill_block_tables(self, seqs):
    width = self.max_blocks
    flat = []
    for s in seqs:
        flat.extend(s.block_table)
        flat.extend([-1] * (width - len(s.block_table)))   # -1 padding
    self._cp(self.block_tables[:len(seqs)].reshape(-1), flat, torch.int32)
```

`-1` 是无效页标识，paged attention 内核遇到 `-1` 会安全忽略，不会显存越界。

## 五、异步 H2D：pin_memory + non_blocking

所有列表先转 pinned CPU 张量，再 `copy_` 进常驻 GPU buffer：

```python
@staticmethod
def _cp(dst, data, dtype):
    cpu = torch.tensor(data, dtype=dtype, pin_memory=True)
    dst.copy_(cpu, non_blocking=True)
```

- `pin_memory=True`：主机内存锁页，CUDA 的 DMA 直接搬运，不经过 bounce buffer；
- `non_blocking=True`：异步提交拷贝，CPU 立即返回继续调度，与 GPU 已有工作重叠。

**采样结果异步 D2H**：`model_runner._stage_samples` 用独立 copy stream + pinned buffer 把采样结果异步拷回 CPU，采样 kernel 与拷贝解耦，随后 `read_samples` 一次 `.synchronize()` 读回，把 v2 的「逐序列 `.item()` 硬同步」从 O(batch) 降为 O(1)。

## 六、小结

| 关注点 | 手段 | 收益 |
| --- | --- | --- |
| 变长序列 | `cu_seqlens` 紧凑打包 | 免 padding 无效计算 |
| 分页寻址 | `slot_mapping` / `block_table`（-1 padding） | CPU 端整数预计算 |
| H2D 延迟 | `pin_memory` + `non_blocking` | 拷贝与计算重叠 |
| 采样回传 | 独立 stream + pinned buffer + 一次 sync | O(batch) → O(1) 同步 |
