# 输入管线：从变长请求到定长张量

> 对应 [01-v2性能瓶颈](./01-v2性能瓶颈.md) — 瓶颈 E（输入传输）。

推理服务面对的是一批长度各异的请求，GPU 需要的却是形状规整、连续排布的张量。这两者之间需要一个转换层：把参差不齐的 Python 列表，高效、紧凑地打包成 FlashAttention 这类算子能直接消费的格式。v3 里干这件事的是数据面的 Batch（`src/data/batch.py`），它是调度器与计算层之间的桥。

## 1.为什么需要它

第一，调和变长与定长的矛盾。GPU 擅长固定形状的密集计算，而一个批次里每条序列长度都不一样。必须把列表压成张量，同时不能靠粗暴 padding 浪费算力。

第二，复用常驻缓冲区。前向计算要消费十来个元数据张量，包括序列边界、槽位映射、页表等。Batch 在构造时一次性把整套常驻 GPU 张量分配好，之后每一步只拷贝实际数据进去，避免反复分配释放。

第三，隔离复杂度。调度器只关心哪些序列本轮被调度，不需要知道槽位是怎么按块大小换算出来的。Batch 把这些换算内聚起来，上层拿到的是一步就能消费的现成张量。

## 2. 常驻缓冲区长什么样

Batch 分配的上限由三个配置决定：最大序列数（max_bs）、单步最大 token 数、最长序列需要的页数。整套张量按上限一次性预分配，prefill、decode、CUDA Graph 三种路径共用这一份，互不冲突。

```python
# batch.py 构造：一套常驻 GPU 张量
self.input_ids    = torch.zeros(max_tokens, dtype=int64)     # token id
self.positions    = torch.zeros(max_tokens, dtype=int64)     # 位置编码
self.slot_mapping = torch.full((max_tokens,), -1, dtype=int32)  # 槽位映射
self.cache_seqlens = torch.zeros(max_bs, dtype=int32)        # decode 每条当前长度
self.cu_seqlens_q  = torch.zeros(max_bs + 1, dtype=int32)    # prefill 序列边界
self.cu_seqlens_k  = torch.zeros(max_bs + 1, dtype=int32)
self.block_tables  = torch.zeros(max_bs, max_blocks, dtype=int32)  # 页表
self.temperatures  = torch.zeros(max_bs, dtype=float32)      # 采样参数
self.top_ps        = torch.zeros(max_bs, dtype=float32)
self.top_ks        = torch.zeros(max_bs, dtype=int32)
self.min_ps        = torch.zeros(max_bs, dtype=float32)
```

张量都按上限建好，没填到的位置保持安全值。槽位映射初始为 -1，页表初始为 0，CUDA Graph 重放时不需要额外清理这些 padding 区域。

## 3. Prefill 紧凑打包

Prefill 一次要处理每条请求的一段 prompt（可能带前缀命中）。它用紧凑打包而不是 padding，把真实 token 按序列顺序首尾相接塞进同一段缓冲区，同时记录每条序列的边界。

```python
# build_prefill —— 逐序列累加边界
cu_q, cu_k = [0], [0]
for s in seqs:
    start = s.num_cached_tokens       # 已缓存前缀长度
    n     = s.num_scheduled_tokens    # 本轮要算的 token 数
    end   = start + n
    ids.extend(s.token_ids[start:end])
    positions.extend(range(start, end))
    slots.extend(slots_for_range(s.block_table, start, end, block_size))
    cu_q.append(cu_q[-1] + n)
    cu_k.append(cu_k[-1] + end)       # K 边界含缓存前缀
has_cache = cu_k[-1] > cu_q[-1]       # 有前缀命中时走 paged 路径
```

两条边界的作用不同。cu_seqlens_q 标记每条序列 Query 的起止，cu_seqlens_k 标记 Key 的起止，后者把已缓存的前缀长度也累计进去。这是 FlashAttention 变长接口的标准 CSR 输入，靠它一次 kernel 并行处理整批序列，序列之间互不越界。槽位映射则是为每个待写 token 提前算好它在 KV 池里的物理地址，因为分页布局下 token 散落在非连续块里，这个换算放在 CPU 端整数运算里提前完成。

紧凑打包比 padding 省多少，取决于批次里长度的分散程度。padding 会按最长序列铺满无效零，紧凑打包只算真实 token，常见场景能削减 40% 到 90% 的无效计算。

## 4. Decode 极简输入

Decode 每一步只喂上一轮产出的一个 token，数据准备必须压到极简。

```python
# build_decode —— 每条序列只取 4 个标量
input_ids[:bs]     = [s.last_token for s in seqs]      # 上一 token
positions[:bs]     = [len(s) - 1 for s in seqs]        # 当前位置
slot_mapping[:bs]  = [self._decode_slot(s, block_size) for s in seqs]
cache_seqlens[:bs] = [len(s) for s in seqs]            # 当前总长度
```

槽位只算当前这一个 token 该落到的物理位置，因为每步只追加一个。cache_seqlens 配合页表告诉 paged attention 这条序列历史 KV 读到哪里为止。decode 的批次大小会随请求陆续完成而动态变小，这也是 decode 走 CUDA Graph 按档位录图的原因。

## 5. 页表补齐

GPU 算子要的是规整二维张量，每条序列的页数却各不相同。把页表统一铺成最大宽度，短的序列后面补 -1。

```python
def _fill_block_tables(self, seqs):
    for s in seqs:
        flat.extend(s.block_table)
        flat.extend([-1] * (width - len(s.block_table)))   # 补到最大宽度
    block_tables[:len(seqs)].copy_(tensor(flat))
```

-1 是无效页标识。paged attention 内核遇到它会安全跳过，不会越界访问。填充只在有前缀命中的 prefill 和 decode 阶段需要，纯首 chunk 的 prefill 没有历史页表可填。

## 6. 异步拷贝：pin_memory 加 non_blocking

所有列表数据先转成 CPU 张量，再拷进常驻 GPU 缓冲区。这里有两个关键字，缺一个延迟都会导致延迟上升。

```python
@staticmethod
def _cp(dst, data, dtype):
    cpu = torch.tensor(data, dtype=dtype, pin_memory=True)
    dst.copy_(cpu, non_blocking=True)
```

锁页内存让 CUDA 的 DMA 能直接搬运；非阻塞拷贝让 CPU 提交完立即返回去继续调度，拷贝本身和 GPU 上已有的计算重叠。这两者合起来，把每步的 H2D 延迟藏进计算时间里。

采样结果的回传方向同理。模型跑完采样后，结果不立即逐个同步回 CPU，而是先放到独立拷贝流里的 pinned 缓冲，一次 record 一个事件；调度器继续跑，直到真正要读 token id 时才同步一次。v2 里每条序列逐个取数造成的 O(batch) 次硬同步，在这里变成了 O(1) 次。

## 7. 采样参数的整批下传

采样不是每次每个请求单独配置的。Batch 每步把每条序列的 temperature、top_p、top_k、min_p 拷进常驻数组，同时用几个布尔量汇总整批的采样形态，采样器据此选择最省的路径。

```python
self.all_greedy = all(t <= 1e-5 for t in temps)   # 整批贪心，直接取 argmax
self.use_top_k  = any(k < vocab for k in top_ks)  # 有 top-k 才进 top-k 分支
```

整批全贪心时可以跳过所有概率计算，只有个别请求非贪心时才降级走完整分支。这批汇总量是采样器避免逐请求分支的关键。
