## 1. 算子剖析

### 1.1 测试方法

对 [01-v2性能瓶颈.md](./01-v2性能瓶颈.md) 中定位的瓶颈逐一做性能对比分析：

| 瓶颈  | 测试项| v2 实现| v3 实现 |
| --- | --- | --- | --- |
| A   | `attn_prefill`| SDPA causal| FlashAttention-2 / FlashInfer paged |
| A   | `attn_decode`| 逐条 gather + SDPA | FlashInfer paged batch decode |
| B   | `layer_decode` / `layer_prefill` | 整层前向组合 | 整层前向组合|
| C   | `kvwrite`| `index_copy_` | Triton `store_kvcache`|
| D   | `rmsnorm` | pow/mean/rsqrt 三段式| Triton 单核融合|
| D   | `rope`| index_select + chunk + rotate | Triton 单核融合|
| D   | `silu`| `F.silu` + `mul` 两核 | FlashInfer `silu_and_mul` 单核|
| D   | `mlp`| 双 GEMM + cat| 融合 `gate_up_proj` GEMM|
| E   | `sampler`| sort + softmax + multinomial  | topk + 阈值掩码 + gumbel-max|

> 计时方式：CUDA event，预热后取200次运行的中位数。输入形状对齐 Qwen3-0.6B 真实维度。

### 1.2 实测结果

> 数值为 CUDA event 计时中位数（ms），加速比 = v2 / v3，越大越好。
> 测试环境：RTX 4090 D，bf16，Qwen3-0.6B 维度。

#### 1.2.1 RMSNorm（瓶颈 D）

| 输入形状        | v2 (ms) | v3 (ms) | 加速比       |
| ----------- | ------- | ------- | --------- |
| 1×4096×1024 | 0.097   | 0.053   | **1.82x** |
| 8×256×1024  | 0.097   | 0.053   | **1.83x** |
| 32×1×1024   | 0.096   | 0.052   | **1.84x** |

> v3 的 Triton 单核把 pow/mean/rsqrt/mul 四步合并为一次读一次写，prefill 和 decode 形状都稳定 ~1.8x。这是纯带宽算子，融合消除的是中间张量的 HBM 读写。

#### 1.2.2 RoPE（瓶颈 D）

| 输入形状        | v2 (ms) | v3 (ms) | 加速比       |
| ----------- | ------- | ------- | --------- |
| 4096×16×128 | 0.199   | 0.108   | **1.83x** |
| 256×16×128  | 0.200   | 0.104   | **1.91x** |
| 32×16×128   | 0.199   | 0.104   | **1.90x** |

> v3 的 Triton RoPE 单核在寄存器内完成旋转，v2 需要 `index_select + chunk + 4 个 elementwise + cat`。稳定 ~1.8-1.9x。

#### 1.2.3 SiLU+Mul（瓶颈 D）

| 输入形状        | v2 (ms) | v3 (ms) | 加速比       |
| ----------- | ------- | ------- | --------- |
| 1×4096×6144 | 0.125   | 0.047   | **2.66x** |
| 8×256×6144  | 0.043   | 0.028   | **1.56x** |
| 32×1×6144   | 0.035   | 0.027   | **1.30x** |

> FlashInfer `silu_and_mul` 单核相对 `F.silu`+`mul` 两核。token 越多（prefill）收益越大（2.66x），decode 单 token 时 kernel launch 占比高、收益收窄。

#### 1.2.4 MLP（瓶颈 D）

| 输入形状        | v2 (ms) | v3 (ms) | 加速比       |
| ----------- | ------- | ------- | --------- |
| 1×4096×1024 | 0.805   | 0.623   | **1.29x** |
| 8×256×1024  | 0.361   | 0.319   | **1.13x** |
| 32×1×1024   | 0.157   | 0.103   | **1.52x** |

> v3 把 `gate_proj`+`up_proj` 两个 GEMM 合并为单个 `[2*3072, 1024]` GEMM，消除了 `cat` 和一次 HBM 读入。收益 1.1-1.5x，GEMM 本身是计算瓶颈，融合收益主要来自少一次 kernel launch 和输入只读一次。

#### 1.2.5 KV 落盘（瓶颈 C）

| 输入形状     | v2 (ms) | v3 (ms) | 加速比       |
| -------- | ------- | ------- | --------- |
| 32 tok   | 0.024   | 0.031   | **0.77x** |
| 256 tok  | 0.024   | 0.031   | **0.77x** |
| 4096 tok | 0.029   | 0.031   | **0.93x** |

> **v3 的 Triton store_kvcache 在独立微基准中并不比 index_copy_ 快**。这是符合预期的：`index_copy_` 是 cuDNN/cuBLAS 同级的成熟 scatter，Triton 特化核的优势不在速度，而在两点：① 兼容 CUDA Graph 捕获（`index_copy_` 会触发 graph 捕获限制）；② 直接按 NHD 布局落盘，与 FlashInfer 读取格式天然对齐。kvwrite 在整体耗时中占比很小（<1%），不是性能热点，此模块 v3 的取舍是兼容性优先。

#### 1.2.6 Prefill Attention（瓶颈 A）

| 输入形状          | v2 SDPA (ms) | v3 FA2 (ms) | v3 FlashInfer (ms) | FA2 加速 | FI 加速 |
| ------------- | ------------ | ----------- | ------------------ | ------ | ----- |
| 1×256×16×128  | 0.086        | 0.112       | 0.243              | 0.77x  | 0.35x |
| 1×1024×16×128 | 0.115        | 0.120       | 0.324              | 0.96x  | 0.35x |
| 1×4096×16×128 | 0.648        | 0.640       | 0.927              | 1.01x  | 0.70x |

> **单条无前缀 prefill 下 v2 并不吃亏**，因为 PyTorch 的 SDPA 底层就是 FlashAttention 内核，与 FA2 同源。FlashInfer 的 paged prefill 单条时偏慢（0.35-0.70x），它的优势在于：① 变长多条批量时避免 SDPA 逐条 pad；② 直接消费分页 block_table，无需 gather；③ 前缀命中时只算续 chunk。
>
> v3 实测中首 chunk 走 FA2、续 chunk 走 FlashInfer 正是对上面结论的验证：**单条场景 FA2 与 v2 SDPA 打平，变长批与前缀场景 FlashInfer 才有收益**。

#### 1.2.7 Decode Attention（瓶颈 A）

| 输入形状                 | v2 (ms) | v3 (ms) | 加速比        |
| -------------------- | ------- | ------- | ---------- |
| 1×1×16×128 ctx=256   | 0.244   | 0.197   | **1.24x**  |
| 1×1×16×128 ctx=4096  | 0.250   | 0.202   | **1.24x**  |
| 8×1×16×128 ctx=256   | 1.510   | 0.224   | **6.73x**  |
| 8×1×16×128 ctx=4096  | 1.621   | 0.356   | **4.55x**  |
| 32×1×16×128 ctx=256  | 5.848   | 0.290   | **20.18x** |
| 32×1×16×128 ctx=4096 | 6.247   | 0.857   | **7.29x**  |

> **这是 v3 最大的单点收益**。v2 的 decode 是逐条 `gather + SDPA`，时间随 batch 线性增长（1.5ms→6.2ms）；v3 的 FlashInfer batch decode 一次 kernel 处理整批，8 条时 6.7x、32 条时最高 20x。同时 v2 的 gather 每步把 KV 全部搬进连续张量，这部分在 v3 完全消失。

#### 1.2.8 Sampler（瓶颈 E）

| 输入形状       | v2 (ms) | v3 (ms) | 加速比       |
| ---------- | ------- | ------- | --------- |
| 1×151936   | 0.476   | 0.803   | **0.59x** |
| 8×151936   | 0.609   | 0.970   | **0.63x** |
| 256×151936 | 15.474  | 16.292  | **0.95x** |

> **v3 的 gumbel-max 在纯 GPU 时间上反而不如 v2 的 multinomial**。原因：gumbel-max 需要额外生成 `[bs, vocab]` 的指数随机张量（`exponential_`），随机数生成在 GPU 上是显式开销；multinomial 是库级实现的采样。
>
> 但 v3 的采样优化重点不在 kernel 本身，而在**消除 CPU-GPU 同步**：v2 逐序列 `.item()` 同步取回，v3 整批一次 `.tolist()` 取回 + 参数整批打包 + 贪心路径直接 `argmax` 短路。

#### 1.2.9 整层 decode 前向（瓶颈 B，eager 组合）

| 输入形状                    | v2 (ms) | v3 (ms) | 加速比       |
| ----------------------- | ------- | ------- | --------- |
| 1 tok decode, ctx=4096  | 0.756   | 0.569   | **1.33x** |
| 8 tok decode, ctx=4096  | 2.303   | 0.589   | **3.91x** |
| 32 tok decode, ctx=4096 | 7.440   | 1.042   | **7.14x** |

> 整层（RMSNorm + qkv + RoPE + attention + o_proj + MLP）组合后，单 token 1.33x，批量放大到 7.1x。批量收益全部来自 FlashInfer batch decode；单 token 的 1.33x 来自 Triton norm/rope + 融合 MLP。**叠加 CUDA Graph 后 decode 还有更大的发射开销削减**（见第二部分）。

#### 1.2.10 整层 prefill 前向

| 输入形状        | v2 (ms) | v3 (ms) | 加速比       |
| ----------- | ------- | ------- | --------- |
| 1×256×1024  | 0.613   | 0.606   | **1.01x** |
| 1×1024×1024 | 0.627   | 0.664   | **0.94x** |
| 1×4096×1024 | 1.956   | 1.825   | **1.07x** |

> 整层 prefill 单条无前缀场景 v3 与 v2 基本持平（0.94-1.07x）。这与 1.2.6 的观察一致：单条时 SDPA/FA2 同源，算子融合（norm/rope/MLP）的收益被 GEMM 计算主导掩盖。**v3 prefill 的真正收益来自系统级机制**：chunked prefill、前缀缓存、piecewise prefill CUDA Graph（见第二、三部分）。

### 1.3 算子级结论汇总

| 模块           | 瓶颈  | 单 token/decode | 批量/decode    | prefill 长文 | 说明                |
| ------------ | --- | -------------- | ------------ | ---------- | ----------------- |
| RMSNorm      | D   | **1.84x**      | **1.82x**    | **1.82x**  | Triton 单核融合       |
| RoPE         | D   | **1.90x**      | **1.83x**    | **1.83x**  | Triton 单核融合       |
| SiLU+Mul     | D   | 1.30x          | 1.56x        | **2.66x**  | FlashInfer 单核     |
| MLP          | D   | **1.52x**      | 1.13x        | 1.29x      | gate/up GEMM 融合   |
| KV 写         | C   | 0.77x          | 0.77x        | 0.93x      | 兼容优先，非热点          |
| Prefill Attn | A   | —              | —            | ~1.0x      | 单条持平，变长批/前缀才赢     |
| Decode Attn  | A   | 1.24x          | **6.7~20x**  | —          | **v3 最大单点收益**     |
| Sampler      | E   | 0.59x          | 0.63x        | 0.95x      | 收益在同步消除，非 kernel  |
| 整层 decode    | B   | 1.33x          | **3.9~7.1x** | —          | 批量放大              |
| 整层 prefill   | —   | —              | —            | ~1.0x      | 收益在 chunked/前缀/CG |

**总结**：v3 的算子级优化在 **decode 批量场景收益最大**；**prefill 单条场景算子级持平**，真正的收益在系统级机制。kvwrite 与 sampler 的优化目的不在 GPU 速度而在**兼容性与同步消除**。

## 第二部分：系统级机制实测

> 第一部分的算子微基准覆盖不到系统级机制（CUDA Graph 发射开销、前缀缓存、调度策略）——它们只体现在场景级延迟与并发行为里。本部分逐机制实测。

### 2.1 Piecewise Prefill CUDA Graph

v3 的 `prefill_cuda_graph` 把 prefill 切成若干 `(bs, L)` 网格并逐个捕获 CUDA Graph（见 `src/core/prefill_cuda_graph.py`）。能否生效由 `can_use` 决定：**piece 的 replay GPU 时间必须低于 eager 发射地板**，Qwen3-0.6B 上该有利区间为 ≤~1536 token。

测试（`bench_prefill_cg.py`）：单请求 TTFT（add_request → 第一个 token），eager 与 prefill-CG 各跑一遍。

| prompt len | eager (ms) | prefill-CG (ms) | CG 加速 |
| --- | ---: | ---: | ---: |
| 128 | 20.66 | 3.07 | **6.72x** |
| 256 | 21.46 | 4.16 | **5.16x** |
| 512 | 20.51 | 6.41 | **3.20x** |
| 1024 | 19.24 | 10.82 | **1.78x** |
| 1536 | 19.78 | 15.96 | **1.24x** |

> - eager 的 TTFT 稳定在 ~20ms（360 次 kernel 发射串行化的 CPU 地板）；piece CG 一次 replay 替换全部发射，短 prompt 直接压到 3ms。
> - 收益随长度单调收窄（6.72x → 1.24x）：prompt 越长 GPU 计算占比越高，发射开销占比越低。**1536 token 是 0.6B 上的收益边界**，与代码注释一致。
> - 该测试同时验证了 `can_use` 的自适应逻辑：只有 `piece_gpu < eager_floor` 才走 CG，长文自动回退 eager，不会出现"CG 反而更慢"。

### 2.2 前缀命中（Prefix Cache）

场景（`bench_prefix_cache.py`）：先跑一条 2048-token 的 seed 请求把 KV 发布进索引，再测两条命中请求的 TTFT——完全命中（prompt 与 seed 相同）与部分命中（前 1536 相同、后 512 不同）。`prefix_backend` 分别取 `none/hash/radix`（v3）与 `hash`（v2）。

**v3（block_size=256，命中粒度 256 token）：**

| backend | seed (ms) | 完全命中 (ms) | 部分命中 (ms) | 全命中加速 | 部分命中加速 | 全命中 cached |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| none | 25.17 | 24.82 | 24.78 | 1.01x | 1.02x | 0 |
| hash | 23.19 | 18.45 | 18.83 | **1.26x** | **1.23x** | 2048 |
| radix | 23.56 | 15.64 | 18.94 | **1.51x** | **1.24x** | 2048 |

**v2（block_size=16）：**

| backend | seed (ms) | 完全命中 (ms) | 部分命中 (ms) | 全命中加速 | 部分命中加速 | 全命中 cached |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| hash | 38.09 | 48.02 | 92.48 | **0.79x** | **0.41x** | 2048 |

> - **v3 前缀命中真实有效**：radix 全命中 1.51x、hash 1.26x；无缓存（none）时命中无收益（1.01x），排除了数据巧合。
> - **v2 的前缀命中反而是负收益**（0.41~0.79x）。命中完全成功（cached=2048），但 v2 的续 prefill 走 eager 路径——`_prefill` 里 `ctx.store.gather` 把全部 2048-token KV 逐层搬进连续张量，再构造 `512×2048` 的 dense attn_mask。gather + mask 的开销完全吞掉了"少算 1536 token"的收益（92.48ms > 无缓存的 38.09ms）。这是 v2 前缀缓存"做了但没用起来"的直接证据，也解释了 v3 为何引入 FlashInfer paged prefill 处理续 chunk。
> - radix 优于 hash 符合预期：radix 用压缩字典树匹配，命中时只走共享前缀路径，且逐块 LRU 回收策略更贴合缓存语义。

### 2.3 PD 交错：dec@P / short_P

v2 设计文档（`vllm-v2/docs/00-v2版本设计.md`）提出两个短请求服务质量指标：

> - **dec@P**：长 Prefill 请求尚未完成全部 Prefill 的时段（Prefill 窗口）内，短请求已产出的 decode token 数。越大 → 短请求被阻塞程度越低。
> - **short_P**：长请求进入系统排队起，到所有短请求全部完成的时间。越小 → 短请求受长请求拖累越轻。

测试场景（`bench_scheduler_metrics.py`）：4 条短请求（prompt=128, max_tokens=8）先入队，随后 1 条长请求（prompt=3000, max_tokens=4）入队；`max_num_batched_tokens=1024` 使长请求 prefill 跨 3 步，prefill 窗口足够长。对比 v2/v3 × `mix_prefill_decode` 开/关四个组合：

| 引擎 | PD 交错 | dec@P | short_P | 长请求 TTFT |
| --- | --- | ---: | ---: | ---: |
| v2 | mix=True  | **8** | 658.5 ms | 485.8 ms |
| v2 | mix=False | 0 | 659.1 ms | 362.3 ms |
| v3 | mix=True  | **8** | 201.0 ms | 133.0 ms |
| v3 | mix=False | 0 | 205.2 ms | 82.3 ms |

> - **PD 交错让短请求在长请求 prefill 窗口内从"零产出"变为"产出 8 个 decode token"**，v2/v3 一致。prefill-first 下，长请求的 3 个 prefill chunk 连续占满整步预算，短请求直到长请求 prefill 完成才拿到执行，窗口内产不出任何 token（dec@P=0）；mix 模式下 decode 优先，短请求在长请求 prefill 的每个空隙持续产出（窗口内每短请求多产出 2 个 token）。
> - **short_P 在两版引擎上差异不大**（v2: 659 vs 658；v3: 201 vs 205），印证了 v2 设计文档的判断：从总吞吐/总时长看，PD 交错与 prefill-first 接近，**差异体现在完成时序（dec@P）而非总量**。
> - **v3 相对 v2 的绝对收益同样显著**：同一 mix 策略下 short_P 从 659ms → 201ms（**3.3x**）、长请求 TTFT 从 486ms → 133ms（**3.7x**），这是 FlashInfer batch decode + 算子融合在端到端短请求服务质量的累积体现。
> - 注意 mix=False 的长请求 TTFT（82ms）低于 mix=True（133ms）：prefill-first 优先服务长请求，代价是短请求被完全阻塞（dec@P=0）。**mix 模式用 ~51ms 的长请求延迟换取短请求从"零产出"到持续产出**，这正是 PD 交错的价值交换。

## 第三部分：端到端对比

> 配置：Qwen3-0.6B，context_len=4096，max_num_seqs=8。
> v2_eager 与 v3_eager 关闭 CUDA Graph；v3_cudagraph 开启 decode CUDA Graph。

### 3.1 引擎初始化时间

| 版本           | Init Time | 相对 v2 |

| v2_eager     | 7.63s     | 1.00x |
| v3_eager     | 9.92s     | 1.30x |
| v3_cudagraph | 8.83s     | 1.16x |

> v3 初始化略慢，源于 KV cache 分页初始化（block_size=256）与 CUDA Graph 预热。

> v3 的 TTFT 比 v2 低 **15-18%**。CUDA Graph 对 TTFT 影响小（piecewise prefill CG 的效果见 2.1，这里测的是已含 decode CG 的常规路径）。

### 3.3 单请求 Decode / E2E 吞吐

| Token 长度 | 指标     | v2_eager | v3_eager | v3_cudagraph  |
| -------- | ------ | -------- | -------- | ------------- |

### 3.4 多并发吞吐

| Batch Size | v2_eager  | v3_eager  | v3_cudagraph   |

### 3.5 与 nano-vllm / 官方 vllm 的多引擎综合对比

用统一的随机 token 数据（`bench_e2e_data.py`，16 条请求，prompt 100~400 token，输出 50~150 token，总输出 1750 tokens）跑四个引擎的连续批处理吞吐：

| 引擎 | wall (s) | 输出 tokens | 吞吐 (tok/s) | 相对 v3 |
| --- | ---: | ---: | ---: | ---: |
| v2（eager） | 11.14 | 1750/1750 | 157.1 | 0.05x |
| nano-vllm（CUDA Graph） | 1.82 | 1750/1750 | 959.7 | 0.32x |
| **v3（decode CG + FlashInfer）** | 0.58 | 1750/1750 | **3040.2** | 1.00x |
| 官方 vllm 0.26.0 | 0.50 | 1750/1750 | **3532.9** | 1.16x |

> - **v3 相对 nano-vllm 快 3.2x**：同为教学级实现（v3 `src/` 约 4000 行 vs nano-vllm 约 1400 行），v3 的差距来自 FlashInfer paged batch decode（nano-vllm 走 SDPA）+ Triton 融合算子 + 采样同步消除。
> - **v3 达到官方 vllm 0.26.0 的 86%（3040 vs 3533 tok/s）**，已处于同一量级。剩余 14% 差距主要来自官方 vllm 的调度器-执行器异步流水线与更精细的算子调优，属于工程深度差异而非架构性差距。
> - **v2 只有 v3 的 1/19**：v2 的逐条 gather decode 在 16 条并发下是绝对瓶颈（与 1.2.7 的 batch decode 20x 收益互相印证）。

## 综合结论

| 指标             | v2_eager  | v3_eager  | v3_cudagraph | v3_cg vs v2 |
| -------------- | --------- | --------- | ------------ | ----------- |
| TTFT (256 tok) | 24.2ms    | 20.4ms    | 20.5ms       | **1.2x**    |
| Decode (1 seq) | 37.0 t/s  | 58.0 t/s  | 414.1 t/s    | **11.2x**   |
| Batch=8 E2E    | 144.9 t/s | 397.2 t/s | 2385.0 t/s   | **16.5x**   |
| Init Time      | 7.63s     | 9.92s     | 8.83s        | 0.86x       |

**v3 的优化收益分层清晰**：

1. **算子级**：Triton 融合 norm/rope（~1.8x）、FlashInfer silu（~2.7x）、融合 MLP GEMM（~1.3-1.5x）——这些是"每一层都在省"，28 层累加后在 decode 单 token 整层体现为 1.33x。
2. **Attention 级（实测 1.2-20x）**：decode 批量是最大单点收益（FlashInfer batch decode 消除逐条 gather+SDPA），也是并发扩展性的来源。
3. **系统级机制（第二部分实测）**：
   - **piecewise prefill CG 把短文 TTFT 从 ~20ms 压到 3~16ms**（1.24~6.72x，0.6B 上 1536 token 为收益边界，长文自动回退 eager）。
   - **前缀命中真实生效**：radix 全命中 1.51x、hash 1.26x；**v2 的命中反而减速（0.41~0.79x）**，因为 v2 续 prefill 走 eager gather + dense mask，缓存收益被吞掉——这是 v3 引入 FlashInfer paged prefill 的直接理由。
   - **PD 交错（mix）让短请求从"零产出"变为持续产出**（dec@P: 0 → 8）：用 ~51ms 长请求 TTFT 延迟换短请求在 prefill 窗口内的 decode token；short_P 总量不变，印证"PD 交错改变完成时序而非总吞吐"。
4. **端到端（第三部分实测）**：v3 是 v2 的 **19x**、nano-vllm 的 **3.2x**、官方 vllm 0.26 的 **86%**，已达生产级同一量级。
5. **两类"假慢"**：kvwrite（0.77x）与 sampler（0.59x）在纯 GPU kernel 时间上 v3 不如 v2，但分别服务于 CUDA Graph 兼容性和 CPU-GPU 同步消除，是刻意取舍而非性能回退。
