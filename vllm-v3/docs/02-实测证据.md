## 第一部分：算子层

### 测试方法

对 [01-v2性能瓶颈.md](./01-v2性能瓶颈.md) 中定位的每个瓶颈，分别对比 v2 与 v3 的实现。计时使用 CUDA event，预热后取 200 次运行的中位数，输入形状对齐 Qwen3-0.6B 的真实维度。

各瓶颈的 v2 / v3 实现对照：

| 瓶颈 | 测试项 | v2 实现 | v3 实现 |
| --- | --- | --- | --- |
| A | prefill 注意力 | SDPA causal | FlashAttention-2 / FlashInfer paged |
| A | decode 注意力 | 逐条 gather + SDPA | FlashInfer paged batch decode |
| B | 整层前向 | 整层组合 | 整层组合 |
| C | KV 写入 | `index_copy_` | Triton `store_kvcache` |
| D | RMSNorm | pow/mean/rsqrt 三段式 | Triton 单核融合 |
| D | RoPE | index_select + chunk + rotate | FlashInfer 单核 |
| D | SiLU | `F.silu` + `mul` 两核 | FlashInfer `silu_and_mul` 单核 |
| D | MLP | 双 GEMM + cat | 融合 `gate_up_proj` GEMM |
| E | 采样器 | 全量 sort + softmax + multinomial | topk 归约 + 有序空间融合过滤 + multinomial |

> 加速比 = v2 耗时 / v3 耗时，大于 1 表示 v3 更快。

### 1.1 RMSNorm

v2 将 RMSNorm 拆分为七个步骤（转精度、平方、求均值、开方、归一化、乘权重、转回精度），每一步的结果都写回显存。v3 使用 Triton 融合 kernel，一次读入、在寄存器内完成全部计算、一次写回，消除了中间张量的显存读写。

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×4096×1024 | 0.097 | 0.053 | **1.82x** |
| 8×256×1024 | 0.097 | 0.053 | **1.83x** |
| 32×1×1024 | 0.096 | 0.052 | **1.84x** |

RMSNorm 为带宽受限算子，融合减少的是中间结果的显存读写，prefill 与 decode 形状下收益均稳定在 1.8 倍左右。

### 1.2 RoPE

v2 的 RoPE 需要 index_select、chunk、四次 elementwise 和 cat，中间结果经过显存。v3 改用 FlashInfer 的 `apply_rope_with_cos_sin_cache`（vLLM 官方同款）单核完成，较早期手写 Triton 核更快（见 bench/bench_rope_compare.py）。

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 4096×16×128 | 0.299 | 0.118 | **2.54x** |
| 256×16×128 | 0.205 | 0.077 | **2.67x** |
| 32×16×128 | 0.200 | 0.077 | **2.60x** |

### 1.3 SiLU+Mul

v2 使用 `F.silu` 与 `mul` 两个 kernel，v3 使用 FlashInfer 的 `silu_and_mul` 单核。

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×4096×6144 | 0.125 | 0.047 | **2.66x** |
| 8×256×6144 | 0.043 | 0.028 | **1.56x** |
| 32×1×6144 | 0.035 | 0.027 | **1.30x** |

prefill 长序列下 token 数量大，收益最高（2.66x）；decode 单 token 场景 kernel 启动开销占比高，收益收窄至 1.30x。

### 1.4 MLP

v3 将 `gate_proj` 与 `up_proj` 两个 GEMM 合并为单个 `[2*3072, 1024]` GEMM，消除了 cat 和一次输入读取。

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×4096×1024 | 0.805 | 0.623 | **1.29x** |
| 8×256×1024 | 0.361 | 0.319 | **1.13x** |
| 32×1×1024 | 0.157 | 0.103 | **1.52x** |

GEMM 本身为计算瓶颈，融合收益来自少一次 kernel 启动和输入只读一次，因此收益低于 norm/rope。

### 1.5 KV 写入

v2 使用 `index_copy_`，v3 使用 Triton `store_kvcache`。独立微基准中 v3 不更快：

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 32 tok | 0.024 | 0.031 | **0.77x** |
| 256 tok | 0.024 | 0.031 | **0.77x** |
| 4096 tok | 0.029 | 0.031 | **0.93x** |

`index_copy_` 是成熟的 scatter 实现，Triton 特化核在速度上不占优。v3 改用 `store_kvcache` 的目的有两项：

1. 兼容 CUDA Graph：`index_copy_` 会触发 CUDA Graph 捕获限制，自定义 kernel 可以录进图。
2. 对齐 FlashInfer 布局：按 NHD 布局直接落盘，与 FlashInfer 的读取格式一致，省去格式转换。

KV 写入在整体耗时中占比小于 1%，非性能热点，该模块的取舍以兼容性优先。

### 1.6 Prefill 注意力

单条无前缀 prefill 场景下，v2 与 v3 基本持平：

| 输入形状 | v2 SDPA (ms) | v3 FA2 (ms) | v3 FlashInfer (ms) | FA2 加速 | FI 加速 |
| --- | --- | --- | --- | --- | --- |
| 1×256×16×128 | 0.086 | 0.112 | 0.243 | 0.77x | 0.35x |
| 1×1024×16×128 | 0.115 | 0.120 | 0.324 | 0.96x | 0.35x |
| 1×4096×16×128 | 0.648 | 0.640 | 0.927 | 1.01x | 0.70x |

PyTorch 的 SDPA 底层即 FlashAttention 内核，与 FA2 同源，因此单条场景两者打平。FlashInfer paged prefill 单条时偏慢（0.35~0.70x），其优势体现在以下场景：

- 变长多条批量：避免 SDPA 逐条 pad。
- 直接消费分页 block_table，无需 gather。
- 前缀命中时仅计算续 chunk。

v3 实际实现中首 chunk 走 FA2、续 chunk 走 FlashInfer，与该结论一致。

### 1.7 Decode 注意力

v2 的 decode 逐条 gather + SDPA，时间随 batch 线性增长；v3 的 FlashInfer batch decode 单 kernel 处理整批。

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×1×16×128 ctx=256 | 0.244 | 0.197 | **1.24x** |
| 1×1×16×128 ctx=4096 | 0.250 | 0.202 | **1.24x** |
| 8×1×16×128 ctx=256 | 1.510 | 0.224 | **6.73x** |
| 8×1×16×128 ctx=4096 | 1.621 | 0.356 | **4.55x** |
| 32×1×16×128 ctx=256 | 5.848 | 0.290 | **20.18x** |
| 32×1×16×128 ctx=4096 | 6.247 | 0.857 | **7.29x** |

batch 从 1 增至 32，v2 耗时从 0.24ms 增至 6.2ms，v3 从 0.20ms 增至 0.86ms。单条时差异不大，批量下差距迅速扩大。此为 v3 并发扩展性的来源。

### 1.8 采样器

v3 采样器重构为**单次有序化 + 归约空间融合**：启用 top-k 时用 `topk` 把工作集从 vocab（约 15 万）归约到 `max_k`（约 20），top-p / min-p 在这个小空间里共用同一次 `softmax` 与 `cumsum` 完成，采样后用有序索引 `gather` 回原 token id。相比旧实现消除了「topk + 全量 sort + 三次 softmax + scatter 回填」的重复读取。

> 说明：早前版本的微基准存在参数传递错位（v2 的位置参数把 top_p 喂给了 min_p），下表已统一用关键字传参重测，v2 / v3 输入完全对齐。

**主场景（top_k=20 且 top_p=0.95 同时启用）：**

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×151936 | 0.875 | 1.159 | 0.75x |
| 8×151936 | 0.913 | 1.147 | 0.80x |
| 256×151936 | 28.857 | 3.398 | **8.49x** |

**场景细分：**

| 场景 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| bs=1 greedy | 0.203 | 0.084 | **2.42x** |
| bs=8 greedy | 0.195 | 0.078 | **2.48x** |
| bs=256 greedy | 4.710 | 0.224 | **21.01x** |
| bs=1 top_k=20 | 0.443 | 0.573 | 0.77x |
| bs=8 top_k=20 | 0.463 | 0.514 | 0.90x |
| bs=256 top_k=20 | 25.078 | 3.324 | **7.54x** |
| bs=1 top_p=0.95 | 0.455 | 0.551 | 0.82x |
| bs=8 top_p=0.95 | 0.630 | 0.678 | 0.93x |
| bs=256 top_p=0.95 | 26.875 | 26.005 | 1.03x |

规律与成因：

- **大 batch 是采样器真正成为瓶颈的区间**：v2 在 bs=256 时对整个词表做全量 sort，耗时随 batch 线性放大到 28.9ms；v3 用 `topk` 把工作集压到 20 列，后续过滤和采样都在归约空间进行，降到 3.4ms（**8.49x**）。这是连续批处理高并发下的关键收益。
- **greedy 全程最快**：`temperature≈0` 时 v3 直接 `argmax` 短路，跳过排序 / softmax / 采样，bs=256 达 **21x**。这是生产默认（temperature=0）的热路径。
- **只开 top-p 无归约收益**：没有 top-k 时 v3 与 v2 一样要对整词表排序，bs=256 仅 1.03x（略胜于 v2，因省去 scatter 回填和一次 softmax）。
- **小 batch（1 / 8）略慢（0.75~0.93x）**：此时采样是亚毫秒级、远小于 attention/MLP，属延迟受限区间。v3 的自适应分支需要少量 `.any()` / `.item()` CPU-GPU 判定同步，且 kernel 数量多于 v2 的「一次 sort + multinomial」，固定开销在小 batch 上占比偏高。这是「用小 batch 上可忽略的亚毫秒代价，换大 batch 上采样瓶颈的 8.5x 和 greedy 的 21x」的取舍。

引擎侧另有两项与本微基准正交的收益：采样参数整批 `pin_memory` + `non_blocking` 打包上 GPU、结果一次 `.tolist()` 取回，把 v2 的「逐序列 `.item()` 硬同步」从 O(batch) 降为 O(1)。

功能一致性：在 temperature / top-k / top-p / min-p / greedy 及其组合下，v2 与 v3 采样的**支撑集完全相同**，经验分布 L1 差异仅 0.002~0.011（2 万次采样的统计噪声量级），greedy 结果逐位一致。两者是同一采样语义的不同实现，差异仅在排序策略、采样算子（multinomial）与批处理封装，不影响可用功能。

### 1.9 整层前向

**decode**（RMSNorm + qkv + RoPE + attention + o_proj + MLP）：

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1 tok, ctx=4096 | 0.756 | 0.569 | **1.33x** |
| 8 tok, ctx=4096 | 2.303 | 0.589 | **3.91x** |
| 32 tok, ctx=4096 | 7.440 | 1.042 | **7.14x** |

单 token 收益来自 Triton norm、FlashInfer rope 与融合 MLP，批量收益来自 FlashInfer batch decode。

**prefill**：

| 输入形状 | v2 (ms) | v3 (ms) | 加速比 |
| --- | --- | --- | --- |
| 1×256×1024 | 0.613 | 0.606 | **1.01x** |
| 1×1024×1024 | 0.627 | 0.664 | **0.94x** |

prefill 单条无前缀场景 v3 与 v2 基本持平（0.94~1.07x）。与 1.6 一致：单条时 SDPA/FA2 同源，算子融合收益被 GEMM 计算主导掩盖。v3 prefill 的收益来自系统机制（chunked prefill、前缀缓存、torch.compile 全图编译），见第二部分。

## 第二部分：系统机制层

算子微基准覆盖不到 CUDA Graph 发射开销、前缀缓存、调度策略，这些机制只体现在场景级延迟与并发行为中。本节逐机制实测。

### 2.1 torch.compile Prefill（全图编译）

decode 形状固定，可整步录成 CUDA Graph 重放；prefill 序列长度变化，无法录制固定形状的图。v3 曾用 piecewise CUDA Graph（attention 摘出 eager、其余层进图），但该方案有两个结构性缺陷：

- **静态 buffer copy**：每次重放都要把整批 `input_ids`/`positions`/`slot_mapping` 拷进固定地址的静态 buffer，再回读输出——copy 次数反超 eager（profiler 实测 eager 168 次 copy → piecewise 267 次）。
- **attention 摘出**：FlashInfer/FA2 无法进 torch 图，attention 只能在图外 eager 单独跑，图内外各走一遍 kernel 序列，kernel 总数不降反升（646 → 784）。

**最终方案：torch.compile 全图编译**。把三个 Dynamo 无法追踪的算子注册为 opaque custom op，使整个模型（含 attention）可被编译成单图：

- `vllm::attention`（`layers/attention.py`）：写 KV + 计算 attention（首 chunk FA2 varlen / decode·续 chunk FlashInfer paged）。KV pool 地址稳定不进图；随 batch 变化的元数据（`slot_mapping`/`cu_seqlens`/`max_seqlen`/`use_fa2`）作为显式 tensor/int 参数穿透。
- `vllm::silu_and_mul`、`vllm::rotary_embedding`（`layers/ops.py`）：FlashInfer JIT / FlashInfer RoPE 注册为 opaque op，避免 graph break。
- 编译单元 `_prefill_forward` 只接受纯 tensor/int 输入，`fullgraph=True` 下 **Graph Count == 1，无断裂**（`torch._dynamo.explain` 验证）。

**profiler 内核级对比（`bench_prefill_analysis.py`，L=512，4090 D）**：

| 指标 | eager | torch.compile | 变化 |
| --- | ---: | ---: | ---: |
| wall 时间 | 23.51 ms | 5.98 ms | **3.93x** |
| CUDA 时间 | 6.53 ms | 5.89 ms | −10% |
| kernel 数 | 646 | 537 | −109 |
| copy 次数 | 168 (0.40 ms) | 116 (0.22 ms) | −52（copy 时间 −45%） |

**单请求 TTFT（`bench_prefill_ttft.py`，add_request → 第一个 token，greedy）**：eager 与 torch.compile 各跑一遍（`torch_compile` 隔离变量）。

| prompt len | eager (ms) | compile (ms) | 加速比 |
| --- | ---: | ---: | ---: |
| 128 | 17.74 | 4.93 | **3.60x** |
| 256 | 17.98 | 6.63 | **2.71x** |
| 512 | 18.08 | 10.84 | **1.67x** |
| 1024 | 21.59 | 20.27 | **1.07x** |
| 1536 | 30.78 | 30.02 | **1.03x** |
| 2048 | 43.58 | 42.54 | **1.02x** |
| 3072 | 67.87 | 66.83 | **1.02x** |
| 4096 | 97.07 | 95.26 | **1.02x** |

- eager 的短 prompt TTFT 约 18ms，来自数百次 kernel 发射的 CPU 串行化地板；compile 把整层发射融合为几十个 kernel，短 prompt 降至 ~5ms。
- 短 prompt 收益大（发射开销主导，3.6x）；长 prompt 收敛到 ~1.0x（GPU-bound 物理边界，GEMM 计算主导）。与旧 piecewise 趋势一致，但短端收益更高（3.60x vs 3.17x）且代码更简洁——**无需静态 buffer copy、无需 attention 摘出、无 token 尺寸网格、无 cap 回退分支**。

**编译 / 启动开销（`compile_mode=reduce-overhead`）**：

| 场景 | 耗时 |
| --- | ---: |
| 冷缓存编译（inductor 首次） | ~25 s |
| 热缓存编译（磁盘缓存命中） | ~10 s |
| 启动期预热（`_build_compiled_prefill` 触发一次编译 + 图捕获） | 计入引擎 Init，首个请求不背编译 |

- 编译发生在引擎初始化阶段，通过启动期预热把编译 / autotune 开销一次性摊掉，稳态推理不背编译。
- `compile_dynamic` 控制形状策略：`True` = 符号形状一次编译覆盖任意长度（稳态 ~14ms，任意长度不重编译）；`False` = 固定形状重放更快（短 prompt ~6ms），但新长度会重编译（~2~12s）。在线变长服务选 `True`，离线固定长度选 `False`。

**数值正确性**：编译融合会改变 bf16 浮点运算顺序，eager 与 compile 不再是 bit 级一致（旧 piecewise 复用 layer 算子是 bit 一致）。实测（`bench_prefill_analysis.py`）：

- `max |eager − compiled| = 1.125`（引擎强制 `allow_bf16_reduced_precision_reduction=False`，即 GEMM fp32 累加，否则 diff 达 2.0）。
- greedy 逐 token 一致率 55/63 = 87.3%（`bench_verify_output.py`，变长单请求），分叉均为 near-tie argmax 翻转，属 bf16 固有数值扰动，无系统性偏差。

**结论**：torch.compile 全图编译取代 piecewise CUDA Graph——删掉静态 buffer copy 与 attention 摘出，kernel 数 −109、copy −52；短 prompt TTFT 3.6x、长 prompt 收敛 ~1.0x；代价是 eager/compile 不再 bit 一致（~1 ULP bf16 扰动），以「代码简洁 + 全图融合 + 无 patchwork」换取「±1 ULP 数值保真」。

### 2.1b 与官方 vllm / v2 的输出一致性（`bench/cross_engine_verify.py`）

同一批确定性 token prompt，greedy（temperature=0）逐 token 对比多引擎：v3-eager / v3-compile / v2 / 官方 vllm 0.26。

| 引擎对 | 说明 |
| --- | --- |
| v3-eager vs v3-compile | eager 与 compile 数值差 ~1.125（bf16），greedy 一致率 87.3%，分叉为 near-tie argmax 翻转 |
| v3 vs v2 | near-tie 数值翻转 |
| v3 vs 官方 vllm | near-tie 数值翻转 |

- v3 与官方 vllm / v2 **不是 bit 级一致**——不同 kernel（FA2 vs FlashInfer vs SDPA vs 官方编译内核）、不同 GEMM shape 在 bf16 下的必然结果，不是路径错误。
- 分叉全部是 near-tie argmax 翻转：logits 极度接近时不同实现选不同 token，无系统性偏差、无前缀分叉累积。
- 与旧 piecewise 的差别：旧 piecewise 复用 layer 算子相对 eager bit 一致（99.6%），torch.compile 相对 eager 为 ~1 ULP bf16 扰动（87.3% greedy 一致）。这是「全图融合编译」与「bit 保真」的取舍，前者换来了无静态 buffer copy 的简洁实现与更高的短 prompt 加速。

### 2.2 前缀缓存

场景（`bench_prefix_cache.py`）：先跑一条 2048-token 的 seed 请求将 KV 发布进索引，再测两条命中请求的 TTFT——完全命中（prompt 与 seed 相同）与部分命中（前 1536 相同、后 512 不同）。`prefix_backend` 分别取 `none/hash/radix`（v3）与 `hash`（v2）。

**v3（block_size=256，命中粒度 256 token）：**

| backend | seed (ms) | 完全命中 (ms) | 部分命中 (ms) | 全命中加速 | 部分命中加速 | 全命中 cached |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| none | 25.17 | 24.82 | 24.78 | 1.01x | 1.02x | 0 |
| hash | 23.19 | 18.45 | 18.83 | **1.26x** | **1.23x** | 2048 |
| radix | 23.56 | 15.64 | 18.94 | **1.51x** | **1.24x** | 2048 |

**v2（block_size=16）：**

| backend | seed (ms) | 完全命中 (ms) | 部分命中 (ms) | 全命中加速 | 部分命中加速 | 全命中 cached |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| hash | 38.09 | 48.02 | 92.48 | **0.79x** | **0.41x** | 2048 |

- v3 前缀命中有效：radix 全命中 1.51x、hash 1.26x；none（无缓存）1.01x，排除了数据巧合。
- v2 前缀命中为负收益（0.41~0.79x）。cached=2048 表明缓存确实命中，但 v2 的续 prefill 走 eager 路径：`_prefill` 中 `ctx.store.gather` 将全部 2048-token KV 逐层搬进连续张量，再构造 `512×2048` 的 dense attn_mask。gather 与 mask 的开销超过"少算 1536 token"的收益（部分命中 92.48ms > 无缓存 38.09ms）。这是 v3 引入 FlashInfer paged prefill 处理续 chunk 的原因。
- radix 优于 hash：radix 用压缩字典树匹配，命中时仅走共享前缀路径，且逐块 LRU 回收策略贴合缓存语义。

> 与 torch.compile prefill 的关系：前缀命中的「续 chunk」走 FlashInfer paged eager 路径（`num_cached_tokens > 0`），torch.compile 只覆盖「首 chunk」（无前缀命中）。两者作用于不同 chunk，互不冲突；前缀缓存命中时的续 chunk 仍享 FlashInfer paged 的省算收益，而首 chunk 享全图编译收益。

### 2.3 PD 交错

v2 设计文档（`vllm-v2/docs/00-v2版本设计.md`）定义两个短请求服务质量指标：

- **dec@P**：长 Prefill 请求尚未完成全部 Prefill 的时段内，短请求产出的 decode token 数。越大表示短请求被阻塞程度越低。
- **short_P**：长请求入队到所有短请求完成的时间。越小表示短请求受长请求拖累越轻。

测试场景（`bench_scheduler_metrics.py`）：4 条短请求（prompt=128, max_tokens=8）先入队，随后 1 条长请求（prompt=3000, max_tokens=4）入队。`max_num_batched_tokens=1024` 使长请求 prefill 跨 3 步。对比 v2/v3 × `mix_prefill_decode` 开/关四个组合：

| 引擎 | PD 交错 | dec@P | short_P | 长请求 TTFT |
| --- | --- | ---: | ---: | ---: |
| v2 | mix=True | **8** | 658.5 ms | 485.8 ms |
| v2 | mix=False | 0 | 659.1 ms | 362.3 ms |
| v3 | mix=True | **8** | 201.0 ms | 133.0 ms |
| v3 | mix=False | 0 | 205.2 ms | 82.3 ms |

- PD 交错使短请求在长请求 prefill 窗口内从 0 产出变为 8 个 decode token，v2/v3 一致。prefill-first 下长请求的 3 个 prefill chunk 连续占满整步预算，短请求直至长请求 prefill 完成才执行，窗口内产出 0；mix 模式 decode 优先，短请求在长请求 prefill 的空隙持续推进。
- short_P 在两版引擎上差异不大（v2: 659 vs 658；v3: 201 vs 205），印证 v2 设计文档的判断：PD 交错与 prefill-first 的总吞吐接近，差异在完成时序（dec@P）而非总量。
- 同 mix 策略下 v3 相对 v2：short_P 659ms → 201ms（3.3x），长请求 TTFT 486ms → 133ms（3.7x），为 FlashInfer batch decode 与算子融合在端到端场景的累积效果。
- mix=False 的长请求 TTFT（82ms）低于 mix=True（133ms）：prefill-first 优先服务长请求，代价是短请求被完全阻塞（dec@P=0）。mix 模式以约 51ms 的长请求延迟换取短请求从零产出到持续产出。

## 综合结论

| 指标 | v2_eager | v3_eager | v3_cudagraph | v3_cg vs v2 |
| --- | --- | --- | --- | --- |
| TTFT (256 tok) | 24.2ms | 20.4ms | 20.5ms | **1.2x** |
| Decode (1 seq) | 37.0 t/s | 58.0 t/s | 414.1 t/s | **11.2x** |
| Batch=8 E2E | 144.9 t/s | 397.2 t/s | 2385.0 t/s | **16.5x** |
| Init Time | 7.63s | 9.92s | 8.83s | 0.86x |

v3 的收益分层：

1. **算子层**：Triton 融合 norm（约 1.8x）、FlashInfer rope（约 2.6x）、FlashInfer silu（约 2.7x）、融合 MLP GEMM（约 1.3~1.5x）。单算子收益有限，28 层累加后在 decode 单 token 整层体现为 1.33x。
2. **Attention 层（1.2~20x）**：decode 批量为最大单点收益，FlashInfer batch decode 消除逐条 gather+SDPA，为并发扩展性的来源。
3. **系统机制层**：
   - **torch.compile prefill（全图编译）**：把 attention/silu/rope 注册为 opaque custom op，整个模型编译成单图（fullgraph Graph Count == 1）。相对 eager，短 prompt 单请求 TTFT 3.6x（128 token 17.7→4.9ms）、profiler 内核 −109、copy −52；长 prompt 收敛 ~1.0x（GPU-bound）。相较旧 piecewise CG：删掉了静态 buffer copy、attention 摘出、token 尺寸网格与 cap 回退分支，代码更简洁；代价是 eager/compile 不再 bit 一致（~1 ULP bf16 扰动，greedy 一致率 87.3%）。编译/启动开销（冷缓存 ~25s、热缓存 ~10s）在引擎初始化阶段通过预热一次性摊掉。并发场景下 compile 的边际收益 ≈ 0（decode 主导），其价值集中在单请求 / 短 prompt 的 TTFT。
   - 前缀缓存生效：radix 全命中 1.51x、hash 1.26x；v2 命中反而减速（0.41~0.79x），因续 prefill 走 eager gather + dense mask，缓存收益被吞掉。前缀命中续 chunk 走 FlashInfer paged eager，与 compile 首 chunk 互不冲突。
   - PD 交错使短请求从零产出变为持续产出（dec@P: 0 → 8），以约 51ms 长请求 TTFT 延迟为代价；short_P 总量不变，改变的是完成时序。
4. **端到端**：v3 为 v2 的 19x、nano-vllm 的 3.2x、官方 vllm 0.26 的 86%（16 请求小批）；**非规则 prompt 多并发（8~64）下为官方 vllm 的 84~98%（均值 ~91%）**，但并发 TTFT p50 反而低 25%（145 vs 193ms）。

kvwrite（0.77x）在纯 GPU kernel 时间上 v3 不优于 v2，其价值在 CUDA Graph 兼容性，属刻意取舍。采样器经归约空间融合重构后，大 batch 达 8.49x、greedy 达 21x，仅在亚毫秒级小 batch 上略慢（延迟受限、固定开销占比高），整体已从「假慢」转为高并发下的实打实收益。
