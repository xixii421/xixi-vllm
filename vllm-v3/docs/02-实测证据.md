# 实测证据：v2 / v3 / nano / 官方 vLLM 性能对比

> 测试环境：NVIDIA RTX 4090 D，Qwen3-0.6B，PyTorch 2.13，FlashAttention-2 2.8.3，FlashInfer 0.6.15，Triton 3.7.1，官方 vLLM 0.26.0
> 测试日期：2026-08-17
> 计时口径：算子级用 CUDA event 预热后取均值，端到端用 wall-clock 吞吐

前面[01-v2性能瓶颈](./01-v2性能瓶颈.md)从原理上定位了 v2 的几处瓶颈，这一节我们从算子和端到端两个层面来分析和v2、nano-vllm以及vllm官方之间的整体性能差距。

## 1. 算子层

在进行端到端的验证之前，我们系统性的把所有算子基本都进行了替换，换成了高性能版本。

> [!NOTE]
> 这里有小伙伴会问到，为什么我们不都是自己手写triton或者手撕xx算子呢？在实际开发中，对于通用算子来说，调库已经是比较高效的了，而只有对于某些特殊需求或者特殊场景下，我们才需要单独优化。

这里我们把每个瓶颈都单独测试，输入形状按 Qwen3-0.6B 的实际维度来（hidden=1024，intermediate=3072，16 头 / 8 KV 头，head_dim=128）。

目前Qwen3的整个算子情况如下：


| 算子         | 瓶颈  | v2 实现                         | v3 实现                     | prefill 加速 | decode 加速 |
| ---------- | --- | ----------------------------- | ------------------------- | ---------- | --------- |
| RMSNorm    | D   | pow/mean/rsqrt                | `F.rms_norm` 融合核          | 6.4x       | 6.1x      |
| RoPE       | D   | index_select + chunk + rotate | FlashInfer `apply_rope`   | 7.3x       | 7.3x      |
| SiLU+Mul   | D   | `F.silu` + `mul`              | FlashInfer `silu_and_mul` | 6.1x       | 1.6x      |
| MLP        | D   | gate/up 双 GEMM + cat          | 融合 `gate_up_proj`         | 1.2x       | 1.5x      |
| KV 写入      | C   | `index_copy_` scatter         | Triton `store_kvcache`    | 1.5x       | 1.5x      |
| decode 注意力 | A   | 逐条 gather + SDPA              | `flash_attn_with_kvcache` | 不适用        | 3.3~23.6x |




### RMSNorm

v2 把 RMSNorm 拆成七步：转精度、平方、求均值、开方、归一化、乘权重、转回精度，每一步的中间结果都写回显存。v3 直接用 PyTorch 原生的 `F.rms_norm` 融合核，一次读入、在寄存器里算完、一次写回，省掉了中间张量的来回搬运。


| 形状          | v2 (ms) | v3 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×1024 | 0.070   | 0.011   | 6.35x |
| 8×256×1024  | 0.071   | 0.011   | 6.42x |
| 32×1×1024   | 0.065   | 0.011   | 6.06x |


prefill 和 decode 形状下收益都稳定在 6 倍左右，因为这个算子本身就是带宽受限，融合省的就是显存读写。

### RoPE

v2 的 RoPE 需要 `index_select` 从缓存里逐 token 取 cos/sin，再 chunk、做四次 elementwise、最后 cat。v3 换成 FlashInfer 的 `apply_rope_with_cos_sin_cache`，一个 kernel 全搞定。


| 形状          | v2 (ms) | v3 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 4096×16×128 | 0.201   | 0.028   | 7.31x |
| 256×16×128  | 0.199   | 0.027   | 7.26x |
| 32×16×128   | 0.200   | 0.028   | 7.25x |


这个加速比不小，主要吃掉了 `index_select` 从 [32768, 128] 缓存逐 token gather 的开销。

### SiLU+Mul

v2 是 `F.silu` 和 `mul` 两个 kernel，v3 用 FlashInfer 的 `silu_and_mul` 单核完成。


| 形状          | v2 (ms) | v3 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×6144 | 0.112   | 0.018   | 6.14x |
| 8×256×6144  | 0.027   | 0.012   | 2.16x |
| 32×1×6144   | 0.020   | 0.012   | 1.60x |


prefill 长序列 token 多，收益最高（6.14x）；decode 单 token 时 kernel 启动开销占大头，收益收窄到 1.60x。

### MLP

v3 把 `gate_proj` 和 `up_proj` 两个 GEMM 合并成一个 `[2*3072, 1024]` 的 GEMM，省了一次 cat 和一次输入读取。


| 形状          | v2 (ms) | v3 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×1024 | 0.756   | 0.613   | 1.23x |
| 8×256×1024  | 0.343   | 0.302   | 1.14x |
| 32×1×1024   | 0.084   | 0.054   | 1.54x |


GEMM 本身是计算瓶颈，融合的收益只来自少一次 kernel 启动和输入少读一次，所以比 norm/rope 低很多，这是符合预期的。

### KV 写入

v2 用 `index_copy_`，v3 用 Triton 的 `store_kvcache`。这是个纯访存的 scatter，物理上限就是 HBM 带宽，Triton 的收益来自两点：128-bit 向量化访存、K/V 单 kernel 融合，把 `index_copy_` 约 23 us 的固定发射开销吃掉了。


| token 数 (d=1024 bf16) | v2 index_copy_ (us) | v3 Triton (us) | 加速比   |
| --------------------- | ------------------- | -------------- | ----- |
| 1                     | 23.35               | 15.18          | 1.54x |
| 256                   | 23.26               | 15.01          | 1.55x |
| 4096                  | 23.34               | 14.94          | 1.56x |
| 8192                  | 44.54               | 22.29          | 2.00x |




### decode 注意力

这是 v3 最大的一处单点收益。v2 的 decode 是逐条把分页 KV gather 成连续张量，再喂给 SDPA，时间随 batch 线性放大；v3 的 `flash_attn_with_kvcache` 直接消费分页 block_table，一个 kernel 处理整批（`bench_decode_attention.py`，B=8，NHEADS_Q=16，NKV=8，head_dim=128）。


| ctx 长度 L | v2 decode (us) | v3 decode (us) | 加速比    |
| -------- | -------------- | -------------- | ------ |
| 256      | 578.2          | 25.5           | 22.64x |
| 1024     | 575.0          | 31.6           | 18.17x |
| 2048     | 583.4          | 51.6           | 11.32x |
| 4096     | 598.3          | 154.3          | 3.88x  |
| 8192     | 975.2          | 296.5          | 3.29x  |


用 `torch.profiler`（L=2048，B=8，单层）看一下差距到底在哪：


| 引擎  | kernel 数 | 总 GPU 时间 | 关键内核                                |
| --- | -------- | -------- | ----------------------------------- |
| v2  | 1650     | 15394 us | gather(高级索引) 9211 us + SDPA 4459 us |
| v3  | 100      | 2684 us  | SDPA flash kernel 2551 us           |


v2 那 800 次 `gather` 就是把分页 KV 逐条搬进连续张量，纯搬运就花了 9.2 ms，SDPA 本身才 4.4 ms。v3 把这些 gather 全去掉了，kernel 数从 1650 降到 100。这也解释了为什么 decode 的并发扩展性上 v2 和 v3 完全是两个量级。

## 2. 机制层：torch.compile 对 prefill 的加速

decode 的形状固定，可以整步录成 CUDA Graph 重放；prefill 的序列长度一直在变，录不了固定形状的图。v3 的做法是把 attention / silu / rope 注册成 opaque custom op，让整个 prefill 前向能被 `torch.compile` 编译成一个完整的图（fullgraph，Graph Count == 1）。单请求 TTFT 实测（`bench_prefill.py`，greedy，两边都开 decode CG，只隔离 compile 这一项）：


| prompt 长度 | eager (ms) | compile (ms) | 加速比   |
| --------- | ---------- | ------------ | ----- |
| 32        | 16.47      | 2.77         | 5.94x |
| 128       | 16.23      | 3.20         | 5.08x |
| 512       | 15.97      | 6.40         | 2.49x |
| 1024      | 15.79      | 12.00        | 1.32x |
| 2048      | 22.94      | 22.25        | 1.03x |


短 prompt 的收益最大（发射开销主导，5~6x），长 prompt 收敛到 1.0x（GEMM 计算主导，到了 GPU 算力的物理边界）。编译发生在引擎初始化阶段（冷缓存约 25s，热缓存约 10s），启动期预热一次就摊掉了，稳态推理不再背这个成本。

## 3. 端到端



### greedy 下的 decode 吞吐

greedy（temperature=0）是生产默认，最能体现 v3 对 v2 的核心加速（`bench_decode_e2e.py`，prompt=256，max_tokens=128）：


| batch | v2 eager decode (tok/s) | v3 cudagraph decode (tok/s) | 加速比    |
| ----- | ----------------------- | --------------------------- | ------ |
| 1     | 36.5                    | 429.2                       | 11.76x |
| 2     | 62.1                    | 683.5                       | 11.01x |
| 4     | 98.5                    | 1367.7                      | 13.89x |
| 8     | 141.2                   | 2574.0                      | 18.23x |


单请求 TTFT：v2 24.66 ms，v3 16.26 ms。注意 v2 的吞吐从 batch=1 到 8 只涨了 3.9 倍，而 v3 涨了 18.2 倍，接近线性。差距就来自前面说的 FlashAttention batch decode，以及 CUDA Graph 消除了逐 kernel 发射的 CPU 串行化瓶颈。

### 四引擎连续批处理吞吐（T=0.6）

nano-vllm 直接禁止 greedy，所以四引擎统一用 temperature=0.6 + ignore_eos 来比（`bench_compare.py`，16 条变长请求，prompt 100~400，总输出 1685 token）：


| 引擎                      | wall (s) | 输出 token  | 吞吐 (tok/s) | 相对 v2  |
| ----------------------- | -------- | --------- | ---------- | ------ |
| v2（eager）               | 10.85    | 1685/1685 | 155.3      | 1.00x  |
| v3（decode CG + compile） | 0.57     | 1685/1685 | 2957.5     | 19.04x |
| nano-vllm（CUDA Graph）   | 0.74     | 1685/1685 | 2263.1     | 14.57x |
| 官方 vLLM 0.26.0          | 0.52     | 1685/1685 | 3262.2     | 21.01x |


v3 相对 v2 是 19 倍，相对 nano 快 1.31 倍，达到官方 vLLM 的 90.7%。这个数据在 greedy 和采样两种场景下趋势一致，说明核心收益（FlashAttention batch decode + CUDA Graph）是稳定的。

这里顺手说一个踩过的坑：采样器里 `_gumbel_sample` 一开始加了 `@torch.compile`，结果连续批处理中 decode 的 batch 会随请求陆续完成而动态递减（16 到 13 再到 8），每个新 batch 都触发一次重编译，编译开销直接算进了稳态吞吐，T>0 场景吞吐掉到 1001 tok/s。去掉装饰器、改回 eager 标准算子（和 ullm / 官方 vLLM 一致）后，吞吐回到 2957.5 tok/s。细节在 [09-Sampler](./09-Sampler.md) 的优化 3。
