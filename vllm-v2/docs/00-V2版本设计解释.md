# vllm-v2

> **核心设计**：Continuous Batching+ Chunked Prefill

> [上一节](../README.md) | [代码增改清单](./01-相比v1的增改.md) | [代码架构与三面分离](./02-代码架构与三面分离.md)

v1 解决的是**单条请求**怎样把历史 K/V 存进页池、怎样前缀复用、怎样让 Attention 按契约读写。 v2 把控制流扩展到**多请求同时推进**。

## 1. v1 版本回顾
v1 的 Engine 一次只服务一条 `Sequence`。尽管页池和前缀索引已经为**多请求共池**准备好了显存形态，但是控制流仍是串行的。即一条 `generate` 跑完，再接下一条。

v1 消除了单条路径上的重复算 K/V，也用分页缓解了显存碎片。服务端的日常负载却是**多用户并发**：

- 请求 A 在 Prefill；
- 请求 B 在 Decode；
- 各请求剩余长度、到达时刻都不同。

若仍按 v1 串行驱动，那么主要有三个层面的影响：
1. **吞吐下降**。Decode 每步只处理 1 个 token，单条很难喂饱 GPU；多请求再串行，Decode 阶段墙钟近似相加。
2. **尾延迟差**。长短请求混到时，后到的短请求必须等先到的长请求整段结束，用户体感被最长请求拖住。
3. **页池与前缀闲置**。页可以分给不同 Sequence，Engine 却从未同时驱动多条，共池与跨请求前缀命中用不满。

静态批处理（Static Batching）倒是可以把多条凑成一批一起跑，能抬高硬件占用。但它同时要求**整批一起开始、一起结束**，短请求仍要陪长请求耗到批寿命结束，才能腾出槽位。Continuous Batching 正是针对这一调度粒度提出的解法。



## 2. Continuous Batching
在设计V2版本的时候，同样要想清楚批处理是为了解决什么问题？


Continuous Batching（连续批处理）又称Iteration-level Scheduling（迭代级调度）或In-flight Batching（途中批处理）。目前，vLLM、SGLang 等主流推理引擎均已将其作为默认的服务方式。


自回归语言模型的生成过程划分为两个阶段：
- **Prefill**：一次性将整个Prompt（提示词）输入模型，计算并存储所有位置的Key和Value，形成完整的KV Cache.
- **Decode**：每一步将上一步新生成的单个Token作为输入，利用已有的KV缓存来去计算当前Step的注意力，采样得到下一个Token，如此反复循环，直到生成EOS（结束符）或者达到设定的最大长度。

在早期的推理服务中，普遍采用静态批处理策略。其流程为：系统先等待并凑齐一批请求（假设共 B 条），然后对这一批请求统一执行 Prefill，再统一逐步执行 Decode。必须等到这一批内所有请求全部生成完毕，整批所占用的计算资源才会被释放，接着才开始处理下一批请求。
表面上看，GPU 一直在执行计算，但批次的整体实际寿命取决于该批中**生成长度最长的那个请求**。

考虑一个简单的例子：批次中包含三个请求 R1、R2、R3，它们分别需要生成 30、200 和 80 个 token。在静态批处理下，整批的存活时间被强制拉到 200 步。这导致了三种典型的资源浪费和性能问题：

1. **早结束请求的槽位空转**：R1 在第 30 步已经生成 EOS 并完成，但直到第 200 步整批结束前，它所占用的槽位都无法被释放。中间约 170 步里，该槽位要么填入填充数据，要么重复已完成序列的无意义计算，GPU 的有效算力被白白稀释。
2. **队头阻塞**：短请求的响应延迟被同批最长请求强行拖长。对 R1 的用户而言，实际只需要 30 步即可获得完整回答，却必须等到第 200 步才能收到结果。这种等待并非由请求本身的复杂度引起，纯粹是因为和慢请求被绑在了同一批里。
3. **中途无法入队**：一旦批次开始执行，其成员集合就会被固定。在此期间新到达的请求（例如 R4）无法中途插入，只能排在队列里，直到当前整批完全结束并释放资源后，才有机会被编入下一个批次。当请求到达率较高时，队列迅速堆积，导致系统的尾部延迟急剧恶化。

这些问题的根本原因在于调度粒度过于粗糙。静态批处理以“一整批请求的完整生命周期”作为决策单元，而语言模型解码阶段的真实节奏却是“每一步生成一个 token”。二者之间的不匹配直接造成了上述浪费。


### 2.1 把调度粒度变成单步
解决静态批处理缺陷的关键，是让调度决策跟上解码的节拍。CB 的思路是在每一次模型前向计算之前，都重新决定本轮迭代要推进哪些请求。批次成员不再被预先确定，而是在系统运行过程中随着请求的结束与新请求的到来而动态变化。批次成员表实质上变成了一份随时间变动的活名册。


一次完整的迭代可以划分为四个步骤：

一次完整的引擎步可以写成四拍，拍拍相扣：

1. **调度**：读取当前系统中的等待队列和正在运行的请求，根据既定策略和可用资源（如显存余量），选定本轮迭代要处理的序列，并决定每个序列在本步要向前推进几个 token（Decode 阶段通常是 1 个；Prefill 阶段则可能一次性处理整个 prompt 或将其切分）。
2. **模型前向计算**：将调度阶段选出的序列组装为一个微批次，实际执行一次 Transformer 前向过程。这次前向可能包含新请求的 Prefill，也可能同时包含多个已有请求的单步 Decode。
3. **采样**：对模型输出的 logits 进行采样，为每个序列产生 0 个或 1 个新 token。
4. **资源回收**：检查各序列的状态，若某序列已生成 EOS 或达到最大长度，立即将其从运行队列中移除，并释放它所占用的 KV 缓存页等显存资源。由此腾出的并发位，可在下一轮迭代的步骤中被新请求占用。

仍沿用之前的例子：R1、R2、R3 分别需要生成 30、200、80 个 token，并假设在第 31 步时新请求 R4 到达。在 Continuous Batching 下，批次的变化
过程如下：
```text
步序（Decode）     本步 batch 成员              本步发生的事
─────────────────────────────────────────────────────────────
  1 … 30           {R1, R2, R3}               三人各前进一步
  31               {R2, R3, R4}               R1 在步 30 已 EOS → 释放槽位
                                              R4 在步 31 立刻占用空位
  32 … 80          {R2, R3, R4}               三人继续
  81               {R2, R4, …}                R3 结束 → 再腾坑给后来者
  …                {R2, …}                    R2 一直跑到 200
```

用时间线图来对比，静态批与连续批的差异非常明显（横轴为解码步数，实心块表示正在计算，空白块表示占坑但无有效输出，“|”表示请求完成）：

```text
静态批处理：整批寿命 = max(R1,R2,R3) = 200；R4 被阻塞在外

步:  0        30       80              200
     |---------|--------|---------------|
R1   █████████|░░░░░░░░░░░░░░░░░░░░░░░░  ← 30步已完成，其后空转
R2   ██████████████████████████████████
R3   █████████████████|░░░░░░░░░░░░░░░░  ← 80步已完成，其后空转
R4                                      ████…  ← 整批结束后才能开始


连续批处理：每步都可以更换成员，空槽即时被填充

步:  0        30       80              200
     |---------|--------|---------------|
R1   █████████|                           ← 结束即释放
R2   ██████████████████████████████████
R3   █████████████████|
R4            ████████████████████████…   ← 从第31步起占用R1腾出的槽位
     ↑         ↑        ↑
   三人并行   R1↓ R4↑   R3↓ 再招新人
```

在静态批处理中，第 30 步之后 R1 的槽位仍然被空占，而 R4 只能等待整批结束。连续批处理则在同一时刻将空位立刻转给 R4，长请求 R2 不受任何影响，短请求也无需再被拖住。

由此可以清晰地理解“Continuous”的含义：即系统在生成过程中持续地接纳请求的结束与新请求的到来，做到边生成、边换请求。系统的并发度不再是一个固定值，而是根据等待队列的长度、运行中请求的状态以及显存预算自然浮动。

> 负载高时可以保持高并发，负载低时可能仅剩一两条序列；但无论并发度如何变化，其调度逻辑始终是同一个循环，在降低延迟、提升吞吐和高效利用显存之间取得了更优的Trade-off。


### 2.2 Prefill 与 Decode 在 CB 里的角色
连续批处理是一种调度范式，它在具体执行时仍然要处理语言模型的两个经典阶段。这两个阶段的计算形态差异很大，因此在系统设计中承担了不同的角色。
- **Prefill**：一次性处理一个提示词的全部 token，本质上是计算密集型的矩阵乘法操作。在连续批处理中，请求从等待队列被取出，经过 Prefill 建立完整的 KV 缓存，申请相应的显存页和 token 预算，之后转为运行态，加入后续的 Decode 循环。
- **Decode**：每次只处理 1 个 token，计算量很小，但对显存带宽的压力很大，属于访存密集型操作。在连续批处理中，系统把当前处于运行态的多条请求合并为一个形状为 [B, 1] 的批次，通过一次前向计算同时推进所有请求的一步解码。

> 一个超长的 prompt 如果独占一整步迭代，就会再次造成队头阻塞，只不过阻塞对象从**长 Decode**换成了**长 Prefill**。为此，又发展出了 Chunked Prefill（分块预填充） 和 PD 交错（Prefill-Decode 交错调度）作为连续批处理的配套机制，它们负责将长 Prefill 切碎、与 Decode 穿插执行，避免 Prefill 阻塞 Decode。

> Decode 阶段对连续批处理的依赖性特别强。单条请求每步只算 1 个 token，kernel 启动、数据搬运等固定开销占比很高；只有把 B 条请求捆进同一次 forward，才能将这些开销有效摊薄，从而在相同硬件上实现更高的多请求吞吐。




### 2.3 CB 优化哪些指标？
从系统设计的角度看，连续批处理直接作用于调度层面。

| 第一性收益 | 含义 |
| :--- | :--- |
| **多请求吞吐 / GPU 有效利用率** | 同样硬件与到达流下，单位时间完成更多 token |
| **尾延迟形态** | 短请求完成时间与同批最长输出解耦；有空位即可处理 |

### 2.4 收益效果差异

| 负载 | CB 相对静态批 |
| :--- | :--- |
| 输出长度差异大（聊天、工具调用、有的 10 token 有的 1k） | 收益大，因为空槽回收频繁 |
| 输出几乎等长、离线整齐批处理 | 收益小，静态批实现更简单也往往够用 |
| 到达率极低（经常只有 1 条在跑） | 几乎无换入空间，CB 退化成单请求 |

## 3 PD 交错是什么

在 Continuous Batching 框架下，新请求必须经过 Prefill 阶段才能进入运行队列参与 Decode。当一条请求携带极长的提示词（例如 2k token）时，若要求其 Prefill 在单次迭代内一次性完成，就会产生严重的调度问题。

> 问题一：假设某次迭代调度了一条 2000 token 的 Prefill 请求。Prefill 本身是计算密集型操作，处理 2000 个 token 的矩阵乘和注意力计算将消耗大量时间，单步迭代的耗时因此被显著拉长。在这一整步迭代期间，所有已经在运行中的 Decode 请求都无法得到推进，只能被动等待。

> 问题二：即使我们将长 Prefill 切分成块，如果调度策略只要等待队列中有 Prefill 请求，就只处理 Prefill，不处理 Decode，那么当一个超长 prompt 被切成多块后，系统仍然会连续许多步只执行 Prefill 块。在这段持续的 Prefill 窗口中，所有正在运行中的 Decode 请求的输出进度会完全停滞。此时，那些已经处于生成阶段的短请求，其 dec@P（Prefill 窗口期间产出的 decode token 数）会降为零，用户侧观察到的是已经开始的生成突然“卡住不动”。

这两种本质是同一个问题：Prefill 与 Decode 在时间维度上未能有效交错，导致延迟敏感型请求被吞吐敏感型操作过度阻塞。

为了解决问题一，现代推理引擎引入了 Chunked Prefill 机制，但是要根治 Decode 饥饿问题，必须在同一个迭代步内实现 Prefill 与 Decode 的混合执行，即在每一轮迭代中同时推进一部分 Prefill和一部分 Decode。这种调度方式被称为 PD 交错（Prefill‑Decode interleaving），在主流引擎中通常通过 mix_prefill_decode 等选项默认启用。

PD 交错的一步典型流程如下：

> **优先保障 Decode**
为当前运行队列中的每一条请求预留一个 token 的计算预算。这一步确保了无论 Prefill 压力多大，所有正在生成的请求至少能前进一步。

> **剩余预算用于一个 Prefill Chunk**
设定一个单步 token 总预算（例如 max_num_batched_tokens）。从该预算中扣除步骤 1 已占用的 Decode token 数后，若仍有剩余容量，则从等待队列中取出一个 Prefill 请求的下一块（chunk），其 token 数量不超过剩余预算。

> **预算不足时推迟**
如果当前剩余 token 预算不足以容纳一个最小的 Prefill chunk，则该 Prefill chunk 被推迟到后续迭代。

伪代码如下：
```
for each iteration:
    budget = max_num_batched_tokens
    # 1. 先安排 Decode
    for each seq in running:
        schedule(seq, 1 token for decode)
        budget -= 1
    # 2. 若有剩余预算，从 waiting 中拉一个 Prefill chunk
    if waiting is not empty:
        next_chunk = waiting.front().next_chunk(max_tokens = budget)
        if next_chunk.size > 0:
            schedule(next_chunk)
```

这种混合策略使得系统能够在同一个 batch 中同时包含 `[B_dec, 1]` 的 Decode 序列和 `[1, N_chunk]` 的 Prefill 序列，两者在一次 model.forward 中并行完成。


引入这一机制后，需要一套与之匹配的评价指标，以准确衡量短请求在多长请求并存时的服务质量。

定义两个关键指标：

> **dec@P**：在一条长 Prefill 请求尚未完成其全部 Prefill 的时段（Prefill 窗口）内，其他正在运行的短请求已经产出的 decode token 数。这个值越大，说明短请求被阻塞的程度越低。

> **short_P**：从长请求进入系统排队起，到所有与之同时存在的短请求全部完成生成所经历的时间。这个值越小，说明短请求受长请求拖累的程度越轻。

需要注意的是，从总吞吐量（tokens/s）的角度看，PD 交错与纯 Prefill‑first 策略往往非常接近。两者完成的总 token 数几乎没有差异，PD 交错仅仅是通过细粒度穿插改变了完成的时序。甚至在部分实现中，由于 Decode 和 Prefill 合批可能带来额外的 kernel 调度开销或 batch 形状不规则，总吞吐还可能出现微弱下降。因此，在验证和对比时，应优先观察 dec@P 和 short_P 这类延迟分布指标，总吞吐量仅作为辅助参考，不应作为主要优化目标。
