# 08 — ZMQ、Gloo ControlChannel 与 NCCL

v4 里同时出现三条通信路径：**ZMQ**、**Gloo ControlChannel**、**NCCL**。  
它们不是重复建设，而是分别服务三种不同的「传什么、谁和谁传、要不要 GPU」。

并行策略见 [00-并行环境.md](00-并行环境.md)；控制面分叉见 [07-控制面与并行.md](07-控制面与并行.md)；NCCL 原语细节见 [集合通信.md](集合通信.md)。

---

## 0. 先看结论

| 通道 | 传什么 | 谁连谁 | 后端 | 对应并行 |
| --- | --- | --- | --- | --- |
| **ZMQ** | 请求 / 输出增量（CPU 消息） | 门面 `Engine` ↔ 多个 `EngineCore` 副本 | ZeroMQ ipc | **DP** |
| **Gloo ControlChannel** | 调度 wire + 采样 token id（CPU 字节） | driver rank0 ↔ 同 Engine 的其它 worker | PyTorch Gloo | **TP / PP 控制面** |
| **NCCL** | GPU 张量 | 同 Engine 内 TP / PP rank | NCCL | **TP / PP 计算面** |

判断口诀：

1. **传 GPU 张量、要集合语义** → NCCL  
2. **同一次 step、同一份模型、多卡要对齐执行** → Gloo 控制面 + NCCL 计算面  
3. **多份独立引擎、只分发请求** → ZMQ  

```
                    ┌─────────────────────────────────────┐
  用户请求           │  Engine（门面）                       │
                    └──────────────┬──────────────────────┘
                                   │
              dp>1 用 ZMQ           │  dp=1 本进程直接调
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  EngineCore + Scheduler               │
                    │  （每 DP 副本各一份）                   │
                    └──────────────┬──────────────────────┘
                                   │
              tp/pp>1 用 Gloo       │  广播 SchedulerOutput
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Worker × (tp×pp)                     │
                    │  ModelRunner / Qwen3                  │
                    │  ──── NCCL：TP all-reduce / PP P2P ── │
                    └─────────────────────────────────────┘
```

---

## 1. 什么是 NCCL

### 1.1 定义

**NCCL**（NVIDIA Collective Communications Library）是 NVIDIA 的 **GPU 集合通信库**。  
它在多张 GPU 之间做 all-reduce、all-gather、reduce-scatter、broadcast、send/recv，并自动选择 NVLink / PCIe / 网卡等路径。

在 PyTorch 里，通常通过 `torch.distributed` 的 `nccl` backend 使用。v4 里每个逻辑 `Group` 的 `device_group` 就是 NCCL 组。

### 1.2 在 v4 里干什么

NCCL 只服务 **单 Engine 内的 TP×PP 计算面**：

| 并行 | 原语 | 传什么 | 频率 |
| --- | --- | --- | --- |
| **TP** | all-reduce / all-gather | 层内激活分片 | 每层多次（decode 一步可达几十次） |
| **PP** | send / recv | `hidden_states + residual` | 每步 stage 边界各一次 |

代码入口：

- TP：`communication_op.tensor_model_parallel_all_reduce` 等  
- PP：`send_tensors` / `recv_tensors`（`ModelRunner` 图外调用）  
- 组划分：`parallel_state.initialize_model_parallel` → `TP` / `PP` 的 `device_group`

### 1.3 为什么必须用 NCCL

1. **数据在 GPU 上**。TP/PP 传的是 bf16/fp16 激活，走 CPU 再回拷太慢。  
2. **需要集合语义**。TP 的 all-reduce 不是「A 发给 B」，而是「组内所有卡求和后每人拿到同一结果」。  
3. **拓扑感知**。同机有 NVLink 时走直连；无 P2P 时自动退到主机内存中转——你这台 4090+4070 无 P2P 机上，慢就慢在这里，但语义仍正确。  
4. **可与 CUDA Graph 配合**。TP 的集合通信可进图；PP 的 P2P 在 v4 里刻意放在 **piecewise CG 图外**，避免捕获脆弱。

### 1.4 NCCL 不适合什么

- 不传「请求进队 / 采样结果回传」这类 **CPU 小消息控制流**（用 Gloo / ZMQ 更合适）。  
- **不做 v4 的 DP**：DP 是独立 Engine 副本，副本之间没有「同一份模型上的张量同步」。

## 2. 什么是 Gloo 与 ControlChannel

### 2.1 Gloo 是什么

**Gloo** 是 Facebook 开源的 **CPU 侧** 集合通信库，也是 PyTorch `torch.distributed` 的一个 backend。  
它擅长在 CPU 上做 broadcast、all-reduce、send/recv，不依赖 GPU，也不要求传张量形状固定。

v4 的每个 `Group` 除了 NCCL `device_group`，还有一个 **Gloo `cpu_group`**。  
控制面走 Gloo，计算面走 NCCL，互不抢同一条 GPU 通信路径。

### 2.2 ControlChannel 是什么

`ControlChannel`（`distributed/control_channel.py`）是 v4 在 **WORLD 的 Gloo cpu_group** 上封的一层字节通道：

| API | 语义 | 用途 |
| --- | --- | --- |
| `broadcast(bytes, src=0)` | driver → 全体 worker | 广播 `ControlCommand`（含 `SchedulerOutput`） |
| `send(bytes, dst)` / `recv(src)` | 点对点 | 采样 rank 把 counts / token ids 回传 rank0 |

消息用 **msgspec msgpack** 序列化。先传长度再传 payload，适配变长 wire。

注意：`src` / `dst` 是 **全局 rank**（WORLD），不是 TP/PP 组内 rank。

### 2.3 在 v4 里干什么

只服务 **单 Engine、tp/pp>1** 时的控制面：

```
Scheduler（只在 rank0）
    │  ScheduledBatch → to_wire() → SchedulerOutput
    ▼
MultiprocExecutor.run
    │  Gloo broadcast(ControlCommand{op=execute, sched=wire})
    ▼
全体 Worker.execute_model   ←── 同一份 schedule
    │  内部用 NCCL 做 TP/PP 计算
    ▼
末 PP × tp0 采样
    │  Gloo send(token ids) → rank0
    ▼
Scheduler.update
```

单卡 `UniprocExecutor` 不需要 ControlChannel（本进程直接调 Worker）。

### 2.4 为什么用 Gloo，而不是再塞一套 ZMQ / 再走 NCCL

| 备选 | 为什么不选 |
| --- | --- |
| **NCCL 传调度** | 调度是 CPU 字节流、变长、低频；为控制流建 GPU 缓冲 + NCCL 广播既重又不必要，还会和计算面通信搅在一起。 |
| **ZMQ 连 TP/PP worker** | TP/PP worker 已经在同一个 `torch.distributed` world 里；再用 ZMQ 等于维护第二套进程拓扑。Gloo 与 NCCL **共享同一套 rank**，spawn / torchrun 一条路径即可。 |
| **共享内存 / 管道** | 多机 torchrun 跨节点时不通用；Gloo 本机、跨机都能用。 |

一句话：**已经有分布式进程组时，控制面用同组的 Gloo；还没有共同 world 时，才用 ZMQ。**

### 2.5 和 ZMQ 的边界

| | Gloo ControlChannel | ZMQ |
| --- | --- | --- |
| 进程关系 | 同一 NCCL/Gloo **world**（tp×pp） | **独立** Engine 进程（无共同 world） |
| 同步模型 | 每步 lockstep：广播 → 一起算 → 回收 | 异步：副本各自 step，门面 drain |
| 消息内容 | 同一份 `SchedulerOutput` | 不同请求的 `RequestWire` / `CoreOutput` |
| 谁创建 | `MultiprocExecutor` | `MPClient` |

## 3. 什么是 ZMQ

### 3.1 定义

**ZeroMQ（ZMQ）** 是一个高性能 **消息库**（不是 broker 中间件）。  
进程之间用 socket 模式直接通信，常见模式：

- **PUSH / PULL**：单向流水线（v4 DP 用这个）  
- **PUB / SUB**：发布订阅  
- **REQ / REP**：请求应答  

传输可选 `inproc`（同进程）、`ipc`（本机）、`tcp`（跨机）。v4 用 `ipc://` 连本机多进程。

### 3.2 在 v4 里干什么

只服务 **DP（`dp_size>1`）**：

```
Engine 门面
    │  add_request → round-robin
    ▼  ZMQ PUSH
EngineCoreProc × dp_size   （各有独立 Scheduler / Executor / NCCL world）
    │  各自 step
    ▼  ZMQ PULL
门面 drain → 汇总 EngineCoreOutput
```

实现：`control/mp_client.py`。每个副本：

1. `dp_size` 归 1  
2. 切自己的 `device_ids`  
3. 独立 `nccl_port`  
4. 跑完整的 `EngineCore`

副本之间 **没有** NCCL、也没有 Gloo。

### 3.3 为什么 DP 用 ZMQ，而不是 NCCL / Gloo

| 备选 | 为什么不选 |
| --- | --- |
| **NCCL DP 组** | 训练里 DP 要 all-reduce 梯度；推理没有梯度。v4 的 DP 是「多份完整引擎各算各的请求」，不需要跨副本张量同步。 |
| **把所有副本塞进一个大 world** | 会让 `world_size = dp×tp×pp`，rank 布局、采样 driver、KV 账本全部变复杂；而副本之间本来就不该共享 schedule。 |
| **Gloo 连副本** | Gloo 假定进程已在同一个 `init_process_group` 里。DP 副本是 **各自** `init`，没有共同 world，Gloo 用不上。 |

ZMQ 正好匹配「门面 ↔ 多个独立服务进程」：

- 消息是请求 / 输出，不是 GPU 张量  
- 副本生命周期独立（可单独失败、单独端口）  
- 对齐官方 vLLM 的 `MPClient` 思路  

### 3.4 ZMQ 不适合什么

- 不传 TP 每层的激活（太慢、无集合语义）。  
- 不替代同 Engine 内的控制面：TP/PP worker 已在同一 world，用 Gloo 更直接。

## 4. 三者如何叠在一起

### 4.1 按并行组合看

| 配置 | ZMQ | Gloo ControlChannel | NCCL |
| --- | --- | --- | --- |
| 单卡 | 无 | 无 | 无 |
| tp=2 | 无 | 有 | TP all-reduce |
| pp=2 | 无 | 有 | PP P2P |
| tp=2 pp=2 | 无 | 有 | TP + PP |
| dp=2 | 有 | 无* | 无* |
| dp=2 tp=2 | 有 | **每副本内**有 | **每副本内** TP |

\* 门面与副本之间只有 ZMQ；每个副本内部若再开 tp/pp，才会在副本自己的 world 里用 Gloo + NCCL。

### 4.2 一步数据流（`dp=1, tp=2, pp=2`）

```
1. Scheduler.schedule()          → ScheduledBatch（CPU）
2. to_wire()                     → SchedulerOutput（CPU）
3. Gloo broadcast                → 4 个 Worker 收到同一份 wire
4. 各 Worker ModelRunner
     - PP：NCCL recv / send 中间张量
     - TP：NCCL all-reduce / gather（层内）
5. 末 PP × tp0 采样
6. Gloo send token ids → rank0
7. Scheduler.update()
```

### 4.3 一步数据流（`dp=2, tp=1, pp=1`）

```
1. Engine.add_request → ZMQ PUSH → 副本 A 或 B（round-robin）
2. 副本内各自 Scheduler + UniprocExecutor（无 Gloo）
3. 副本 ZMQ PUSH 输出 → 门面 PULL drain
```

两条路径 **不会混用同一条物理通道**：ZMQ 在「引擎之间」，Gloo/NCCL 在「引擎内部」。

## 5. 设计原则（为什么这样拆）

### 5.1 按「数据面 vs 控制面」拆

| 面 | 特征 | 选型 |
| --- | --- | --- |
| **计算面** | GPU 张量、高频、带宽敏感 | NCCL |
| **同 world 控制面** | CPU 小消息、与 rank 对齐、每步一次 | Gloo ControlChannel |
| **跨引擎控制面** | 无共同 world、请求路由 | ZMQ |

### 5.2 按「是否共享模型状态」拆

- **共享同一份模型切分（TP/PP）** → 必须同 world → Gloo + NCCL  
- **各持完整模型副本（DP）** → 独立 world → ZMQ  

### 5.3 和常见误区对照

| 误区 | 实际 |
| --- | --- |
| 「DP 也该用 NCCL」 | 推理 DP 无梯度；v4 DP = 多引擎 |
| 「控制面也能走 NCCL」 | 能，但重；CPU 调度用 Gloo 更干净 |
| 「TP/PP 也用 ZMQ 广播 schedule」 | 已有进程组时多余；多机 torchrun 也更别扭 |
| 「三条通道重复」 | 三条对应三种拓扑关系，正交 |

## 7. 一句话记忆

> **NCCL 搬 GPU 上的模型激活；Gloo ControlChannel 在同一次推理的多卡之间对齐「算什么」；ZMQ 在多份独立引擎之间分发「谁的请求」。**
