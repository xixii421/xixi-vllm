# 04 控制与并行

通过上边基础部分的学习，我们终于开始了正式的多卡并行的方案与实现。
而在多卡并行中，我们主要实现 TP、PP和DP，并且通过Gloo、NCCL和ZMQ三条通道来进行并行。
至于这些东西是什么，且待我细细讲解。

## 1. v3 为什么是单卡

v3 及更早版本只支持单卡。
整个推理程序跑在单个进程里。
程序启动后，任务调度、模型加载、KV 分配、前向执行、结果采样都在同一进程地址空间内完成。

调用链是一条函数调用：

```
用户（add_request / step / generate）
  → Engine                          # tokenizer、请求入队、对外 API
      → Scheduler.schedule()        # 本步跑哪些 prefill / decode
      → ModelExecutor.run(sched)    # 计算面入口
          → ModelRunner.run()       # 组 batch、attention、forward
          → Sampler                 # logits → token id
      → ModelExecutor.read_samples()
      → Scheduler.postprocess()     # 写回 token、回收已完成序列的 KV
```

可以按职责拆成五层：


| 层      | v3 模块                     | 功能                                                           |
| ------ | ------------------------- | ------------------------------------------------------------ |
| 对外 API | `Engine`                  | 加载 tokenizer，收请求，循环 `step`，把 token 解码成文本                     |
| 调度     | `Scheduler`               | `waiting` / `running` 队列，按序列数、token 预算、KV 剩余块挑本步 batch       |
| 执行桥    | `ModelExecutor`           | 加载整份模型到 `cuda:0`，分配 KV 池，把 `ScheduledBatch` 交给 `ModelRunner` |
| 计算     | `ModelRunner` + `Sampler` | 填 GPU batch、forward、采样，可选 CUDA Graph                         |
| 权重     | `nn.Linear` 等             | 一层一份完整权重                                                     |


这套结构在 v3 版本就已经被我们基本已经压榨到性能极限了。

但是当我们想把 v3 进一步扩展的时候，却发现事情没那么简单。扩展到多卡究竟需要什么呢？我们逐层来分析一下。

## 2. 扩到多卡要改什么

上边提到我们主要实现TP、DP和PP三类并行，而这三类并行切的对象不同，因此改动也会落在不同层上。策略本身见 [00-并行环境.md](00-并行环境.md)。

对于TP来说，他主要处理的核心是两张卡的权重要切出去。每张卡拿某层权重的一块（例如 `o_proj` 按行切开）。
对于用户来说，他的同一批序列两张卡都要算；各算各的分片之后，必须做 all-reduce / all-gather，下一层才能继续。
层与层之间两张卡始终需要互相等待，因此最佳方案就是两张同构卡，这样能够保证计算时间一致。

```
同一批序列、同一份 schedule
  GPU0: W 的左半  |  GPU1: W 的右半
  GPU0: 下层左半  |  GPU1: 下层右半
  ...以此类推
```

而 PP 则更多的是按照模型的层进行切分，层与层之间的激活是顺着卡向下流动的。
一个典型的例子就是 GPU0 只持有前半段层，GPU1 只持有后半段。
同一批序列先在 GPU0 上算完前半段，把 `hidden` / `residual` 发给 GPU1，GPU1 再算后半段。
但是这个问题是 GPU0 和 GPU1 一般需要有等待，需要等上一张 GPU 算完之后才会把消息发送给下一张GPU。

```
同一批序列、同一份 schedule
  GPU0: 层 0..13  send ──►  GPU1: 层 14..27  ──► 采样
```

对于DP则是把整个engine完整拷贝，两张卡都有一份完整的模型，包括 Scheduler。
但是对于请求来说，会有一部分请求走 卡0，另一批请求走 卡1.
两张卡是相对独立处理的，只是有一个分发器去把任务不断的分发到不同的卡上。

```
请求 A ──► GPU0（完整模型 + 自己的 Scheduler）
请求 B ──► GPU1（完整模型 + 自己的 Scheduler）
两张卡互不等待
```


|             | TP            | PP               | DP       |
| ----------- | ------------- | ---------------- | -------- |
| 一张卡上有什么     | 每一层的一部分权重     | 连续若干层的完整权重       | 整份模型     |
| 两张卡算不算同一批序列 | 每一层都要同步       | 前后接力             | 各算各的请求   |
| 卡之间传什么      | 每层的分片结果（集合通信） | stage 边界的 hidden | 请求和输出文本  |
| 谁跟谁说话       | 组内所有卡，每层都说话   | 只跟相邻 stage       | 卡之间无消息传递 |
| 调度          | 一份，所有卡共用      | 一份，所有卡共用         | 每张卡一份    |


落到 v3 的五层，工作清单是：

**进程与设备。** 每张卡一个进程，各自 `cuda.set_device`。进程之间要能建组：谁是 rank 0、world 有多大、NCCL 走哪张网卡。v3 没有这一层。

**调度结果怎么到各卡。** TP / PP 下各卡必须处理同一批序列，否则 `block_table`、输入 token 对不上。v3 的 `schedule()` 结果只在本进程有效，扩多卡要在 `schedule` 和 `run` 之间加一次广播。DP 相反：各副本各自调度，门面只负责把请求分出去。

**权重怎么切、forward 里怎么通信。** TP 要把 `nn.Linear` 改成按维分片，每层做 all-reduce 或 all-gather。PP 要按层切模型，stage 边界 send/recv `hidden_states` 和 `residual`。DP 权重不切，整模型复制。

**采样结果怎么回来。** v3 采样就在本进程。TP / PP 下 logits 只在部分 rank 上完整（PP 只有末 stage 有 logits），token id 要送回跑 Scheduler 的那个进程，才能 `postprocess`。

**请求从哪进。** v3 的 `add_request` 进唯一一个 Scheduler。DP 有多份 Scheduler，门面要把请求 round-robin 出去，再把各副本的输出攒回来。

**CUDA Graph。** v3 只在一张卡上捕获。多卡时图内的 NCCL 调用要求各 rank 同时进捕获窗口，进出要 barrier。PP 的 send/recv 形状随 token 数变，整图录 P2P 会反复重捕获。

同一份 Scheduler 逻辑可以继续用。真正要分叉的是：请求进几个 Engine、一份 schedule 送给几个 Worker、Worker 上的模型切成什么样。

## 3. 两类数据，三条通道

扩多卡之后，进程之间要传两类东西。

一类是控制消息：本步的 `SchedulerOutput`（序列化后的 CPU 字节，每步一次），以及采样 rank 回传的 token id。体积小、频率低、本来就在 CPU 上。

一类是计算张量：TP 每层的分片输出，PP 边界的 hidden / residual。体积大、频率高（28 层模型 decode 一步 TP 可以有几十次 all-reduce），必须走 GPU 直连。

v4 用三条通道分别扛这几件事：


| 通道                    | 传什么               | 连谁                            | 何时出现            |
| --------------------- | ----------------- | ----------------------------- | --------------- |
| Gloo `ControlChannel` | schedule、token id | 同一 Engine 里的 driver 与各 Worker | `tp>1` 或 `pp>1` |
| NCCL                  | GPU 张量            | 同一 Engine 里的 TP / PP rank     | `tp>1` 或 `pp>1` |
| ZMQ                   | 请求、输出增量           | 门面与多个独立 Engine                | `dp>1`          |


控制消息为什么走 Gloo。`init_process_group` 之后每个组已经有一份 CPU 后端。把 `SchedulerOutput` 用 msgpack 打成字节，在 WORLD 的 Gloo `cpu_group` 上 broadcast 即可。若把这段调度塞进 NCCL，小消息要先上 GPU 再下 GPU，还会和每层 all-reduce 抢同一条 NCCL 队列。若再给每个 TP Worker 拉一条 ZMQ，等于在已经建好的 process group 上再铺一套地址；多机 `torchrun` 还要自己维护 socket。只靠共享内存则跨机直接断掉。

计算张量为什么走 NCCL。经主机 `copy` 再汇总，延迟扛不住每层通信。NCCL 认 NVLink、PCIe P2P、IB / TCP，向上只暴露 all-reduce、all-gather、send/recv。带宽量级见 [02-服务器通信测量.md](02-服务器通信测量.md)。

DP 为什么走 ZMQ、不进 NCCL world。训练里的数据并行要做梯度 all-reduce，推理没有梯度，副本之间也不传激活。若把 `dp × tp × pp` 揉成一个大 world，rank 编号、采样 rank、KV 池会缠在一起，而各副本本来就不该共享同一份 schedule。ZMQ 的 PUSH / PULL 只做请求路由，本机用 `ipc://`。

单卡三条通道都没有：`UniprocExecutor` 仍是本进程函数调用，和 v3 一样。

## 4. v3 的模块在 v4 里怎么拆

调度语义没改：仍然是 `schedule → run → 读采样 → 更新序列`。
为了把上一节的分叉接进去，v3 的几个类被拆开。

```
v3：
  Engine
    ├─ Scheduler
    └─ ModelExecutor
         └─ ModelRunner

v4（dp=1, tp=1, pp=1，行为与 v3 相同）：
  Engine                         # tokenizer、add_request、generate，对外接口不变
    └─ InprocClient              # 同进程包装，接口与 MPClient 对齐
         └─ EngineCore           # 原 Engine.step 里的循环
              ├─ Scheduler
              └─ UniprocExecutor # 原 ModelExecutor
                   └─ Worker
                        └─ ModelRunner
```

对照：


| v3                          | v4                                          |
| --------------------------- | ------------------------------------------- |
| `Engine.step` 里的循环          | `EngineCore.step`                           |
| `Scheduler.postprocess`     | `Scheduler.update`                          |
| `ModelExecutor`             | `Executor` + `Worker`                       |
| `ScheduledBatch` 直接进 runner | 先 `to_wire()` 成 `SchedulerOutput`，再给 Worker |


`to_wire()` 把 `Sequence` 收成可序列化的增量：decode 只带 `last_token`、`block_table`、采样参数。本进程路径也走这一步，多卡广播时不用再单独写一套格式。

启动时先按 `dp` 选 Client，再按 `tp/pp` 选 Executor：

```
Engine(config)
  └─ make_client(dp)
        ├─ dp == 1 → InprocClient → EngineCore
        │                └─ create_executor(tp, pp)
        │                      ├─ tp=pp=1 → UniprocExecutor
        │                      └─ else    → MultiprocExecutor
        └─ dp  > 1 → MPClient
                       └─ 每副本把 dp 置 1，再走上面的 EngineCore 路径
```

`run.py` 覆盖单机（含 DP）。多机 TP×PP 用 `run_torchrun.py`，不含 DP。

## 5. 进程组与集合通信

TP / PP 一旦跨进程，就要有「哪些 rank 在一组里做通信」。
v4 的 `world_size = tp × pp`，DP 不进这个 world。

```
global_rank = pp_rank × tp_size + tp_rank
```

每个逻辑组有两个物理组：`device_group` 走 NCCL 传 GPU 张量，`cpu_group` 走 Gloo 做 barrier 和 ControlChannel。


| 组     | ranks                                         | 做什么                        |
| ----- | --------------------------------------------- | -------------------------- |
| WORLD | `0 .. tp×pp-1`                                | 控制面广播、采样回传                 |
| TP    | 同一 `pp_rank` 上连续 `tp_size` 个 rank             | 层内 all-reduce / all-gather |
| PP    | 同一 `tp_rank` 上步进 `tp_size` 的 `pp_size` 个 rank | stage 间 send / recv        |


例如 `tp=2, pp=2`：rank 0=(pp0,tp0)，1=(pp0,tp1)，2=(pp1,tp0)，3=(pp1,tp1)。TP 组是 `{0,1}` 和 `{2,3}`；PP 组是 `{0,2}` 和 `{1,3}`。

NCCL 原语和 v4 里的用法：


| 原语             | 数据流                | 用在哪                                   |
| -------------- | ------------------ | ------------------------------------- |
| all-reduce     | 各卡同形张量，规约后每卡一份相同结果 | 行并行：`o_proj`、`down_proj`              |
| all-gather     | 各卡一段，拼完每卡都有整段      | 列并行需要完整输出时                            |
| reduce-scatter | 按 chunk 规约再各留一块    | `communication_op` 已封装，当前 linear 路径未用 |
| send / recv    | 组内一对 rank          | PP 边界传 hidden / residual              |


![集合通信原语数据流](posts/collectives.png)

封装在 `communication_op.py`。TP 走 `get_tp_group()`，PP 的 `send_tensors` / `recv_tensors` 用组内 rank（`group_peer`）。`group.size == 1` 时这些函数直接返回，单卡零通信。

NCCL 自己按消息大小选 ring 或 tree，传输层在同机走 P2P（NVLink / PCIe），跨机走 IB 或 TCP。`set_nccl_env` 默认 `NCCL_P2P_LEVEL=PXB`（P2P 限在 PCIe 桥内），多机再设 `NCCL_SOCKET_IFNAME`。

## 6. 张量并行 TP

TP 把一层的权重按维度切开。列并行切输出维，各卡算局部 `Y_i`，需要完整结果时 all-gather；行并行切输入维，各卡算部分和，all-reduce 得到完整 hidden。Qwen3 一层里 `qkv_proj` / `gate_up` 列切、`o_proj` / `down_proj` 行切，decode 一步大约两次 all-reduce。切分细节见 [06-linear.md](06-linear.md)、[05-词表.md](05-词表.md)。

控制面仍是一份 Scheduler，跑在 rank 0。`tp>1` 时 `create_executor` 给出 `MultiprocExecutor`：spawn 出其余 Worker，rank 0 自己也是一个 Worker。一步是：

```
Scheduler（rank0）
  → Gloo 广播 SchedulerOutput
  → 各 Worker 本地 forward，TP 组内 NCCL 集合通信
  → 采样 rank 把 token id 经 Gloo 送回 rank0   （纯 TP 时采样 rank 就是 0）
  → Scheduler.update
```

若各卡各自跑 Scheduler，序列集合会分开，那是 DP。若漏掉广播，各卡看到的 `block_table` 和 input id 会不一致，attention 直接算错。

## 7. 流水线并行 PP

PP 按层切开。每张卡只加载自己那一段，显存按层数下降。通信发生在 stage 边界，一步一两次，传的是当前 batch 的 `hidden_states` 和 `residual`。

v4 是 sync lockstep：各 stage 每步处理同一份 schedule，先 decode 再 prefill。没有 1F1B，前一段算完后一段才能算，气泡按 stage 数增加。采样只在末 stage 做，因为前面的 stage 还没有 logits。

`ModelRunner.run_forward` 编排：非首 stage 先 `recv_tensors`，算完本段；非末 stage `send_tensors`；末 stage 采样。CUDA Graph 用 piecewise：recv / send 在图外，本地 compute 在图内，捕获窗口只对齐图内的 TP 集合通信。

TP 和 PP 可以叠。同一步里 Gloo 广播一次，forward 里既有 PP 的 P2P 又有 TP 的 all-reduce，末 PP、tp0 采样后经 Gloo 回传。采样 rank 是 `(pp_size - 1) * tp_size`。

## 8. 数据并行 DP

DP 解决的是吞吐：同样的模型跑多份，请求分到不同副本。每副本有自己的 Scheduler、KV、Worker，step 彼此不同步。

`dp>1` 时 `make_client` 返回 `MPClient`。门面进程只做 tokenizer 和请求镜像，真正的 `EngineCore` 在子进程里：

```
Engine
  → ZMQ PUSH  round-robin → 副本 0 .. dp-1
  ← ZMQ PULL  汇总输出
```

`_replica_config` 把每个副本的 `dp_size` 写成 1，切走自己的 `device_ids`，`nccl_port` 错开。副本内部可以再开 TP / PP，那是副本自己的 NCCL world，和门面无关。

字段含义：`world_size = tp × pp`（单 Engine 的 NCCL 规模）；机器上的卡数约为 `dp × tp × pp`。

## 9. CUDA Graph 和通信

v3 的 decode CUDA Graph 在一张卡上捕获。多卡时，图里的 NCCL 调用会在内部等 peer；各 rank 进出捕获的时刻必须对齐，否则死锁。

`graph_capture` 在窗口前后做：`cuda.synchronize` → TP barrier → PP barrier → 捕获 → 同样再来一遍。PP 的 P2P 留在图外，barrier 主要对齐图内的 TP all-reduce。实测与捕获策略见 [03-性能对比.md](03-性能对比.md)。
