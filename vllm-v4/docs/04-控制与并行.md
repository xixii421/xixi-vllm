# 04 控制与并行

通过上边基础部分的学习，我们终于开始了正式的多卡并行的方案与实现。
而在多卡并行中，我们主要实现 TP、PP和DP，并且通过Gloo、NCCL和ZMQ三条通道来进行并行。
至于这些东西是什么，且待我细细讲解。

## 1. v3 为什么是单卡

v3 及更早版本只支持单卡。
整个推理程序跑在单个进程里。
程序启动后，任务调度、模型加载、KV 分配、前向执行、结果采样都在同一进程地址空间内完成。

调用链是一条函数调用：

```
用户（add_request / step / generate）
  → Engine                          # tokenizer、请求入队、对外 API
      → Scheduler.schedule()        # 本步跑哪些 prefill / decode
      → ModelExecutor.run(sched)    # 计算面入口
          → ModelRunner.run()       # 组 batch、attention、forward
          → Sampler                 # logits → token id
      → ModelExecutor.read_samples()
      → Scheduler.postprocess()     # 写回 token、回收已完成序列的 KV
```

可以按职责拆成五层：


| 层      | v3 模块                     | 功能                                                           |
| ------ | ------------------------- | ------------------------------------------------------------ |
| 对外 API | `Engine`                  | 加载 tokenizer，收请求，循环 `step`，把 token 解码成文本                     |
| 调度     | `Scheduler`               | `waiting` / `running` 队列，按序列数、token 预算、KV 剩余块挑本步 batch       |
| 执行桥    | `ModelExecutor`           | 加载整份模型到 `cuda:0`，分配 KV 池，把 `ScheduledBatch` 交给 `ModelRunner` |
| 计算     | `ModelRunner` + `Sampler` | 填 GPU batch、forward、采样，可选 CUDA Graph                         |
| 权重     | `nn.Linear` 等             | 一层一份完整权重                                                     |


这套结构在 v3 版本就已经被我们基本已经压榨到性能极限了。

但是当我们想把 v3 进一步扩展的时候，却发现事情没那么简单。扩展到多卡究竟需要什么呢？我们逐层来分析一下。

## 2. 扩到多卡要改什么

上边提到我们主要实现TP、DP和PP三类并行，而这三类并行切的对象不同，因此改动也会落在不同层上。策略本身见 [00-并行环境.md](00-并行环境.md)。

对于TP来说，他主要处理的核心是两张卡的权重要切出去。每张卡拿某层权重的一块（例如 `o_proj` 按行切开）。
对于用户来说，他的同一批序列两张卡都要算；各算各的分片之后，必须做 all-reduce / all-gather，下一层才能继续。
层与层之间两张卡始终需要互相等待，因此最佳方案就是两张同构卡，这样能够保证计算时间一致。

```
同一批序列、同一份 schedule
  GPU0: W 的左半  |  GPU1: W 的右半
  GPU0: 下层左半  |  GPU1: 下层右半
  ...以此类推
```

而 PP 则更多的是按照模型的层进行切分，层与层之间的激活是顺着卡向下流动的。
一个典型的例子就是 GPU0 只持有前半段层，GPU1 只持有后半段。
同一批序列先在 GPU0 上算完前半段，把 `hidden` / `residual` 发给 GPU1，GPU1 再算后半段。
但是这个问题是 GPU0 和 GPU1 一般需要有等待，需要等上一张 GPU 算完之后才会把消息发送给下一张GPU。

```
同一批序列、同一份 schedule
  GPU0: 层 0..13  send ──►  GPU1: 层 14..27  ──► 采样
```

对于DP则是把整个engine完整拷贝，两张卡都有一份完整的模型，包括 Scheduler。
但是对于请求来说，会有一部分请求走 卡0，另一批请求走 卡1.
两张卡是相对独立处理的，只是有一个分发器去把任务不断的分发到不同的卡上。

```
请求 A ──► GPU0（完整模型 + 自己的 Scheduler）
请求 B ──► GPU1（完整模型 + 自己的 Scheduler）
两张卡互不等待
```


|             | TP            | PP               | DP       |
| ----------- | ------------- | ---------------- | -------- |
| 一张卡上有什么     | 每一层的一部分权重     | 连续若干层的完整权重       | 整份模型     |
| 两张卡算不算同一批序列 | 每一层都要同步       | 前后接力             | 各算各的请求   |
| 卡之间传什么      | 每层的分片结果（集合通信） | stage 边界的 hidden | 请求和输出文本  |
| 谁跟谁说话       | 组内所有卡，每层都说话   | 只跟相邻 stage       | 卡之间无消息传递 |
| 调度          | 一份，所有卡共用      | 一份，所有卡共用         | 每张卡一份    |

如果要实现多卡，首先要改的就是v3版本的运行假设：单引擎单进程。
即所有的调度、执行、采样、后处理都发生在同一个进程里。
并且默认使用一张GPU。

一旦引入第二张卡甚至更多卡，就首先要回答两个问题：
1. 第二张用来干什么？
2. 如何与它交互？

如果模型本身一张卡可以放下，只是吞吐不够，那么通常做DP。在这种情况下，多进程不是绝对必须的。理论上可以在一个进程里管理多个模型副本，一个副本放 GPU0，另一个副本放 GPU1。但这样做会把很多东西混在一起。
某个副本卡住，另一个副本也可能受影响。所以更常见的做法仍然是每个副本一个进程，每个进程绑定一张 GPU。
这样每个副本仍然保留自己完整的 Scheduler、ModelExecutor、ModelRunner 和后处理逻辑，只是外面再加一层请求分发，把不同请求路由到不同副本。

如果模型一张卡放不下，或者单层权重太大，情况就不太一样了。
这时就要考虑是TP还是PP，亦或者是二者同时运行。

DP 是多个独立副本。每个副本自己接收请求、自己调度、自己执行、自己产出结果。
请求在进入引擎之前被分到不同副本，输出再汇总。
因为每个副本处理的是自己的请求，所以不需要每一步都把同一份 ScheduledBatch 广播给所有副本。

TP 和 PP 则是多个协作执行。
一次推理必须由多个 GPU 一起完成，所以每个参与执行的进程都要拿到同一份 batch 信息。
TP 需要在层内通信，PP 需要在层间通信。
它们每张卡都需要和其他卡一起完成同一批请求。

这就引出了这个问题：为什么多卡通常做成“一张卡一进程？”

严格来说，CUDA 并不禁止一个进程使用多张卡。一个进程可以看到 GPU0，也可以看到 GPU1，甚至可以在同一个进程里给不同设备分配模型、启动不同 stream。
但对推理引擎来说，这样做会把问题复杂化。
每张卡都有自己的 CUDA context、stream、显存占用、通信状态和错误边界。
如果把它们塞进同一个进程，就要在同一个进程里同时管理多个设备的生命周期、同步关系和异常处理。
一旦某张卡 OOM 或者通信挂住，整个进程都可能被拖死。

一张卡一个进程的好处就在这里。每个进程只关心自己那张卡，设备状态更简单，显存统计更清楚，日志和错误也更容易定位。启动时可以通过 CUDA_VISIBLE_DEVICES 或 local_rank 让每个进程只看到自己的 GPU。

更重要的是，多卡之间一旦需要通信，就需要有明确身份。
比如 TP 里的 all-reduce，PP 里的 send/recv都不是普通函数调用，而是多个执行体之间的数据交换。
每个进程都必须知道一共有多少个参与进程，并且还得知道自己是其中第几个。
前者通常叫 world_size，后者叫 rank。两张卡、两个进程，就是 world_size=2，一个进程是 rank=0，另一个是 rank=1。

回到 v3，修改点其实就比较具体了。
- 第一处要改的是**启动方式**。原来 v3 只启动一个引擎进程，现在需要根据并行配置启动多个进程。每个进程拿到自己的 rank、local_rank 和绑定设备，然后仍然构造自己的 ModelExecutor 和 ModelRunner。原来单进程内部的主流程可以保留，设备由当前进程决定。
- 第二处要改的是**调度结果的传播方式**。Scheduler 本身怎么排队、怎么分配 KV 块，这些逻辑可以先不动。需要改的是 Engine.step 的边界。原来 Engine.step 是 schedule() 之后直接调用 ModelExecutor.run(sched)。在 TP 或 PP 下，中间要把 ScheduledBatch 广播给所有参与模型执行的进程。因为每张卡必须拿到同一批请求、同一份 block_table 和 input id。
- 第三处要改的是**模型加载和执行方式**。DP 下，ModelExecutor 和 ModelRunner 基本不用改，只是每个副本重新加载一份完整模型。TP 下，原来的完整 nn.Linear 要改成分片线性层：加载权重时按行或按列切开，前向计算时补上 all-reduce 或 all-gather。PP 下，模型不再完整加载到每个进程，而是按层段加载；ModelRunner 需要在阶段边界发送和接收 hidden_states、residual 等中间结果，最后一个阶段负责产出最终输出。
- 第四处要改的是**采样和后处理的流向**。v3 里 read_samples 和 postprocess 在同一个进程，所以结果直接就能处理。多卡之后，这个路径会变长。TP 下，如果最终输出能在某个 rank 聚齐，仍然可以由该 rank 采样，比如通常放在 rank 0。PP 下，只有最后一个阶段有 logits，所以采样得到的 token id 需要送回负责调度和请求管理的进程，再走原来的 postprocess。
- 最后是 **CUDA Graph**。v3 里的 CUDA Graph 只捕获本卡 decode，情况比较单一。但是多卡之后，如果图中包含 NCCL 集合通信，所有 rank 必须以相同顺序、相同形状进入和退出，否则很容易挂住。必要时则需要在进出图之前加 barrier。PP 的 send/recv 往往会随 token 数和阶段状态变化，不适合直接录进图里。更合适的做法是只把本地稳定的计算录进 CUDA Graph，把跨阶段通信留在图外。

换句话说，v3 要支持多卡，本质上是要把原来“一个进程、一张卡、一份完整模型”的结构，拆成“多个进程、每张卡一个执行体、按并行策略分配模型和请求”。

## 3. 进程之间通信方式
了解了要用到多进程之后，我们还需要解决进程之间数据传输的问题。
在v4的设计中，我选择了Gloo、NCCL和ZMQ来进行通信，各自承担着不同的问题。

### 3.1 通信库

**Gloo** 是 PyTorch 自带的一个 CPU 后端。它只识别 CPU 上的数据，比如一个 `torch.Tensor` 放在内存里，Gloo 负责把它从一台机器发给另一台。Gloo 的典型操作是 broadcast、send、recv 这些，通信的对象是 CPU 张量或元数据。它的特点是比较轻，适合小消息、低频的控制数据。

**NCCL** 是 NVIDIA 的 GPU 集合通信库。它和 Gloo 的区别在两点。**第一**，NCCL 直接操作 GPU 显存里的数据，不走主机内存。**第二**，NCCL 提供的是集合操作：all-reduce 把多张卡的数据规约成一份，all-gather 把多张卡的数据拼成一份。这些操作直接对接 GPU 之间的 NVLink、PCIe P2P、InfiniBand。更加适合较大的张量。

**ZMQ**（ZeroMQ）是一个通用消息库。它和前两个不在一个层次。Gloo、NCCL 是 PyTorch 的进程组后端，ZMQ 本身是一个独立的 socket 库，用来在两个进程之间传任意的字节流。它提供 PUSH/PULL、PUB/SUB 这些消息模式。ZMQ 本身不关心传的是张量还是字符串。ZMQ 的特点是很灵活，适合自己搭一套进程之间的消息通道。

> [!NOTE]
> 简单来说：数据在 CPU 上走 Gloo，数据在 GPU 上走 NCCL，数据是进程之间的任意字节流走 ZMQ。

| 库 | 数据在哪 | 典型操作 | 适合传什么 |
| --- | --- | --- | --- |
| Gloo | CPU 内存 | broadcast、send、recv | 调度结果、token id |
| NCCL | GPU 显存 | all-reduce、all-gather、send/recv | 每层的分片激活 |
| ZMQ | 任意字节流 | PUSH/PULL、PUB/SUB | 请求、输出 |

### 3.2 v4 里分别传什么
多进程之后，通信要按数据性质分开。这里实际有三类东西：调度控制信息、模型计算张量、外部请求和输出。它们的位置、频率、延迟要求都不一样，所以使用的通道也应该不一样。

调度广播属于**控制消息**。它广播的是 ScheduledBatch 的序列化结果，内容本身在 CPU 上产生，体量不大，但每一步都需要稳定到达。这类消息适合走进程组里的 Gloo 后端。Gloo 本身就是 CPU 后端，可以直接广播字节消息，不需要先把数据搬到 GPU，再让它参与 GPU 通信；这样也避免它和模型内部的 NCCL all-reduce 竞争通信资源。为了调度广播单独再搭一套 ZMQ 意义不大，因为进程组已经存在，额外铺一组 socket 只会增加连接、序列化和排障成本。

模型计算张量走 **NCCL**。TP 里的 all-reduce、all-gather，PP 里阶段之间传递的 hidden_states、residual，都是 GPU 显存里的张量。这类通信对带宽和延迟很敏感，应该尽量走 GPU 直连路径，例如 NVLink 或 PCIe P2P。NCCL 本来就是为 GPU 集合通信和点对点通信设计的。

DP 的通信不在模型内部，而在**请求分发层**。纯 DP 下，每个副本都有完整模型。外部只需要把请求分给不同副本，再把它们的输出收回来。这个场景更适合用 ZMQ 做一个独立门面：前端用 PUSH/PULL，或者 ROUTER/DEALER，把请求分发给各个副本，再收集结果。这样 DP 副本可以保持独立。如果后续 DP 再叠加 TP，也是每个 TP 组内部单独建自己的模型通信域，而不是把所有 DP 副本都塞进同一个 NCCL world。

单卡时不需要这些通道。当 tp=1、pp=1、dp=1 时，EngineCore 直接调用 Executor.run，和 v3 一样，只是一次普通函数调用。只有当模型需要拆到多卡，或者需要多个独立副本时，才引入对应的通信层。


## 4. v4 版本设计

v4 没有改调度语义。一次推理的主流程仍然是：

```text
schedule → run → 读取采样结果 → 更新序列
```

真正变化的是模块边界。

v3 里，`Engine` 同时承担了几件事：对外提供 `add_request`、`generate` 这类接口，内部跑 `step` 循环，再直接调用 `ModelExecutor` 执行模型。单卡下这样很简单，所有东西都在一个进程里完成。但到了 v4，需要支持多副本、多进程执行器、不同并行配置，如果这些职责仍然全部塞在 `Engine` 里，后面的扩展会很难放。

所以 v4 把原来的 `Engine` 按职责拆开：对外接口、调度循环、执行后端各自独立。最小配置下，也就是 `dp=1, tp=1, pp=1` 时，v4 的行为和 v3 基本一致，只是结构上多了必要的分层。

```text
v3：
  Engine
    ├─ Scheduler
    └─ ModelExecutor
         └─ ModelRunner

v4，dp=1, tp=1, pp=1：
  Engine
    └─ InprocClient
         └─ EngineCore
              ├─ Scheduler
              └─ UniprocExecutor
                   └─ Worker
                        └─ ModelRunner
```

这里多出来的几层，并不是为了把结构搞复杂，而是为了让单进程和多进程路径有一致的接口。

`Engine` 仍然负责对外能力，比如 tokenizer、`add_request`、`generate` 等。用户看到的使用方式不变。

`InprocClient` 是同进程下的客户端封装。它的作用是把单进程路径包装成和多进程客户端一致的接口。这样以后无论底层是单进程执行，还是多个进程执行，上层调用方式都可以保持一致。

`EngineCore` 承担原来 `Engine.step` 里的内部循环：调度、执行、读取结果、更新请求状态。它不再直接关心外面是单进程还是多进程，只负责把每一步的逻辑推进下去。

`UniprocExecutor` 可以理解为原来的 `ModelExecutor`，但它的职责被进一步收窄：只负责单进程执行路径。真正持有模型、设备和 `ModelRunner` 的是下面的 `Worker`。这样的好处是多进程执行`Executor` 可以管理多个 `Worker`，而单进程路径仍然可以复用同一套抽象。

主要变化可以这样对照：

```text
v3                                  v4
----------------------------------------------------------
Engine.step 里的内部循环        →   EngineCore.step
Scheduler.postprocess           →   Scheduler.update
ModelExecutor                   →   Executor + Worker
ScheduledBatch 直接交给 runner  →   先 to_wire() 成 SchedulerOutput，再交给 Worker
```

其中 `to_wire()` 是一个比较关键的变化。

它的作用是把 `ScheduledBatch` 里真正需要传给执行端的信息整理成一份可序列化的增量数据。例如在 decode 阶段，没有必要把整条序列重新传一遍，只需要带上新生成的 `last_token`、当前请求对应的 `block_table`，以及采样参数即可。

这样做的好处是：单进程路径和多进程路径使用同一份数据格式。即使当前是 `dp=1, tp=1, pp=1`，也会走一次 `to_wire()`。这样后续启用多卡广播时，不需要再为多进程路径单独设计一套消息格式，调试时也更容易对齐。

启动时，v4 会先看 `dp`，再看 `tp/pp`。

```text
Engine(config)
  └─ make_client(dp)
        ├─ dp == 1
        │    └─ InprocClient
        │         └─ EngineCore
        │              └─ create_executor(tp, pp)
        │                    ├─ tp=1, pp=1 → UniprocExecutor
        │                    └─ 其他情况   → MultiprocExecutor
        │
        └─ dp > 1
             └─ MPClient
                  └─ 每个副本内部按 dp=1 处理
                       再进入上面的 EngineCore 路径
```

也就是说，`dp` 决定的是要不要启动多个独立副本。每个副本内部仍然是一个完整的引擎核心，它不再感知外层还有多少个副本，只负责处理自己收到的请求。这样可以避免外层副本编号和内部模型并行编号混在一起。

`tp` 和 `pp` 决定的是每个副本内部怎么执行模型。如果都是 1，就走单进程的 `UniprocExecutor`；只要其中一个大于 1，就需要走多进程执行器，由多个 `Worker` 分别绑定不同 GPU。

入口脚本上，`run.py` 负责单机场景，包括单卡和 DP 多副本。多机下的 `tp × pp` 走 `run_torchrun.py`，这条路径不处理 DP。

## 5. 进程组与集合通信

TP / PP 一旦跨进程，就要有「哪些 rank 在一组里做通信」。
v4 的 `world_size = tp × pp`，DP 不进这个 world。

```
global_rank = pp_rank × tp_size + tp_rank
```

每个逻辑组有两个物理组：`device_group` 走 NCCL 传 GPU 张量，`cpu_group` 走 Gloo 做 barrier 和 ControlChannel。


| 组     | ranks                                         | 做什么                        |
| ----- | --------------------------------------------- | -------------------------- |
| WORLD | `0 .. tp×pp-1`                                | 控制面广播、采样回传                 |
| TP    | 同一 `pp_rank` 上连续 `tp_size` 个 rank             | 层内 all-reduce / all-gather |
| PP    | 同一 `tp_rank` 上步进 `tp_size` 的 `pp_size` 个 rank | stage 间 send / recv        |


例如 `tp=2, pp=2`：rank 0=(pp0,tp0)，1=(pp0,tp1)，2=(pp1,tp0)，3=(pp1,tp1)。TP 组是 `{0,1}` 和 `{2,3}`；PP 组是 `{0,2}` 和 `{1,3}`。

NCCL 原语和 v4 里的用法：


| 原语             | 数据流                | 用在哪                                   |
| -------------- | ------------------ | ------------------------------------- |
| all-reduce     | 各卡同形张量，规约后每卡一份相同结果 | 行并行：`o_proj`、`down_proj`              |
| all-gather     | 各卡一段，拼完每卡都有整段      | 列并行需要完整输出时                            |
| reduce-scatter | 按 chunk 规约再各留一块    | `communication_op` 已封装，当前 linear 路径未用 |
| send / recv    | 组内一对 rank          | PP 边界传 hidden / residual              |

NCCL 自己按消息大小选 ring 或 tree，传输层在同机走 P2P（NVLink / PCIe），跨机走 IB 或 TCP。`set_nccl_env` 默认 `NCCL_P2P_LEVEL=PXB`（P2P 限在 PCIe 桥内），多机再设 `NCCL_SOCKET_IFNAME`。

## 6. 张量并行 TP

TP 把一层的权重按维度切开。列并行切输出维，各卡算局部 `Y_i`，需要完整结果时 all-gather；行并行切输入维，各卡算部分和，all-reduce 得到完整 hidden。Qwen3 一层里 `qkv_proj` / `gate_up` 列切、`o_proj` / `down_proj` 行切，decode 一步大约两次 all-reduce。切分细节见 [06-linear.md](06-linear.md)、[05-词表.md](05-词表.md)。

控制面仍是一份 Scheduler，跑在 rank 0。`tp>1` 时 `create_executor` 给出 `MultiprocExecutor`：spawn 出其余 Worker，rank 0 自己也是一个 Worker。一步是：

```
Scheduler（rank0）
  → Gloo 广播 SchedulerOutput
  → 各 Worker 本地 forward，TP 组内 NCCL 集合通信
  → 采样 rank 把 token id 经 Gloo 送回 rank0   （纯 TP 时采样 rank 就是 0）
  → Scheduler.update
```

若各卡各自跑 Scheduler，序列集合会分开，那是 DP。若漏掉广播，各卡看到的 `block_table` 和 input id 会不一致，attention 直接算错。

## 7. 流水线并行 PP

PP 按层切开。每张卡只加载自己那一段，显存按层数下降。通信发生在 stage 边界，一步一两次，传的是当前 batch 的 `hidden_states` 和 `residual`。

v4 是 sync lockstep：各 stage 每步处理同一份 schedule，先 decode 再 prefill。没有 1F1B，前一段算完后一段才能算，气泡按 stage 数增加。采样只在末 stage 做，因为前面的 stage 还没有 logits。

`ModelRunner.run_forward` 编排：非首 stage 先 `recv_tensors`，算完本段；非末 stage `send_tensors`；末 stage 采样。CUDA Graph 用 piecewise：recv / send 在图外，本地 compute 在图内，捕获窗口只对齐图内的 TP 集合通信。

TP 和 PP 可以叠。同一步里 Gloo 广播一次，forward 里既有 PP 的 P2P 又有 TP 的 all-reduce，末 PP、tp0 采样后经 Gloo 回传。采样 rank 是 `(pp_size - 1) * tp_size`。

## 8. 数据并行 DP

DP 解决的是吞吐：同样的模型跑多份，请求分到不同副本。每副本有自己的 Scheduler、KV、Worker，step 彼此不同步。

`dp>1` 时 `make_client` 返回 `MPClient`。门面进程只做 tokenizer 和请求镜像，真正的 `EngineCore` 在子进程里：

```
Engine
  → ZMQ PUSH  round-robin → 副本 0 .. dp-1
  ← ZMQ PULL  汇总输出
```

`_replica_config` 把每个副本的 `dp_size` 写成 1，切走自己的 `device_ids`，`nccl_port` 错开。副本内部可以再开 TP / PP，那是副本自己的 NCCL world，和门面无关。

字段含义：`world_size = tp × pp`（单 Engine 的 NCCL 规模）；机器上的卡数约为 `dp × tp × pp`。

## 9. CUDA Graph 和通信

v3 的 decode CUDA Graph 在一张卡上捕获。多卡时，图里的 NCCL 调用会在内部等 peer；各 rank 进出捕获的时刻必须对齐，否则死锁。

`graph_capture` 在窗口前后做：`cuda.synchronize` → TP barrier → PP barrier → 捕获 → 同样再来一遍。PP 的 P2P 留在图外，barrier 主要对齐图内的 TP all-reduce。实测与捕获策略见 [03-性能对比.md](03-性能对比.md)。
