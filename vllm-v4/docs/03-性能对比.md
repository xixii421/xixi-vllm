# v4 性能对比

两台机器都没有 NVLink，卡间 P2P 也用不了，多卡通信要绕主机内存。我们在这两台机器上把 v4 跑了一遍：环境 A 是 4090 D + 4070 SUPER，还和官方 vLLM 0.26.0 对过；环境 B 是 4 张 3090，只跑 v4。

先说测下来比较清楚的几件事。

小模型（0.6B）开 CUDA Graph 之后，decode 能快一个数量级；模型变大，这点收益很快变薄。`torch.compile` 主要砍 TTFT，对 decode 几乎没帮助。显存够用、卡间又没 NVLink 时，把模型切成 TP/PP 多半更慢。显存不够才需要切：环境 A 上 14B 靠不均分 PP 才塞得进，环境 B 上 32B 必须 TP=4。数据并行在异构双卡上会被慢卡拖死；四张同构 3090、8B 又能单卡放下时，四卡吞吐最高的是 DP=4 加 CUDA Graph，不是 TP=4。

图在 `docs/figures/`，脚本是 `gen_ieee_figs.py`。原始数字放在文末，正文不再把每张表重抄一遍。拓扑和通信测量见 [00](00-并行环境.md)、[01](01-硬件互联.md)、[02](02-服务器通信测量.md)。

## 1. 两台机器

| | 环境 A | 环境 B |
| --- | --- | --- |
| 机器 | 双路 Xeon 工作站 | SYS-4029GP-TRT，双路 CPU、双 NUMA |
| 评测用 GPU | RTX 4090 D 24 GB + RTX 4070 SUPER 12 GB | 4× RTX 3090 24 GB（物理 GPU 1、2、4、5） |
| 同机未用 | — | GPU 0 是占用中的 RTX PRO 6000 Blackwell；GPU 3 是 A100 80GB，只拿来当 32B 单卡对照 |
| 同构 | 否 | 是 |
| 卡间 | 跨 NUMA，`topo -p2p r` = NS，无 NVLink | GPU1↔2、GPU4↔5 是 PIX，两对之间是 SYS；P2P 全 NS/CNS，`can_device_access_peer` 全 False，无 NVLink |
| NCCL | — | world=4：2 KB ≈ 82 µs（24 MB/s），8 KB ≈ 76 µs（104 MB/s），小消息走主机内存 |
| 精度 | bfloat16 | bfloat16 |
| 对照引擎 | v4 和官方 vLLM 0.26.0（V1） | 只跑 v4 |
| 模型 | Qwen3-0.6B / 4B / 8B / 14B | Qwen3-0.6B / 8B / 32B |
| 开关 | eager、CUDA Graph、`torch.compile` | eager、CUDA Graph；没开 compile |

![两套机器的 GPU 拓扑](figures/fig01_hw.svg)

环境 A 两张卡差一截：4090 快、显存 24 GB，4070 慢、只有 12 GB。DP=2 会被 4070 拖住，12 GB 上再开 CUDA Graph 还可能 OOM。环境 B 四张卡一样，`CUDA_VISIBLE_DEVICES=1,2,4,5` 映射成可见卡 0–3。TP=2 走 PIX 对 `--device-ids 0,1`（物理 1+2）；TP=4 和四卡 DP 用 `0,1,2,3`。

环境 B 上 0.6B 每步大约 57 次 2 KB all-reduce，光通信大约 4.7 ms/token；8B 大约 73 次 8 KB，大约 5.5 ms。单卡 decode 要是已经比这个快，TP 只会更慢。

## 2. 怎么测

脚本是 `bench/bench_v4.py`，官方对照是 `bench/bench_vllm.py`，整表是 `bench/run_matrix.py`。除了 DP，prompt 都是 256 token，贪心，`ignore_eos`，`max_tokens=128`，bf16。v4 这边 `max_num_seqs=16`，`context_len=4096`。单副本 KV 用 `num_kvcache_blocks=64`。`dp>1` 时脚本会把 KV 提到 128、`max_num_seqs` 至少 64，prompt 改成 128，一次打 32 路，看聚合吞吐。

| 指标 | 怎么算 |
| --- | --- |
| TTFT (ms) | 提交到第一个 token 的墙钟 |
| decode (tok/s) | 128 个生成 token 去掉第一个 |
| batch8 (tok/s) | 8 路一起跑，总生成 token / 墙钟 |
| DP 吞吐 (tok/s) | 32 路一起跑 |

DP 吞吐和 batch8 不是一回事：路数 32 对 8，prompt 128 对 256。后面碰到这两个数，只看谁更大一截，不当成加速比。

每组只跑了一次。TTFT 大概有 5%–10% 晃动；decode 和 batch 是 100 多个 token 的平均，稳一些。看结论优先看后两个。

![这次实际跑过的配置](figures/fig02_coverage.svg)

空着的格子多半是机器限制：环境 A 只有两张卡，没有 TP=4；环境 B 没测 0.6B 的 TP=2，3090 上也没开 compile。官方 V1 离线路径已经没有 PP，所以没有 PP 对照。环境 B 没跑官方引擎。

## 3. 环境 A

单卡默认用 4090 D。TP=2、PP=2 是 4090 + 4070。

### 0.6B

0.6B 每步算得很少，时间耗在 Python 和 kernel 启动上。

![0.6B](figures/fig03_envA_06b.svg)

单卡 decode：eager 65.3 tok/s，CUDA Graph 433.9（6.6×）。TP=2 上这个倍率更大（8.3×），因为每步有一堆小 all-reduce，eager 更亏。PP=2 每卡层数减半，eager 自己就到了 90.5，Graph 再加成 257.9，只有 2.8×。

compile 几乎只动 TTFT。单卡从 19.43 ms 降到 4.78 ms（4.1×），decode 还是 63.9，和 eager 的 65.3 差不多。TP=2 编译里带着 all-reduce，走了 `max-autotune`，TTFT 反而从 25.74 ms 涨到 29.43 ms。

开了 Graph 再做 TP/PP，decode 都低于单卡。eager 里 PP=2 是个例外：90.5 对单卡 65.3（1.39×），层少、启动次数少。TP 还是更慢。

完整数字在附录 A.1。

### 8B

8B 每步要搬大约 16 GB 权重，瓶颈在访存和算力，Graph 和 compile 都没 0.6B 那么夸张。

![8B](figures/fig04_envA_8b.svg)

单卡 decode 38.4 → 57.6（大约 1.5×）。compile 对 TTFT 只有 1.01–1.13×。Graph 下 batch-8：单卡 400.2，TP=2 334.3（0.84×），PP=2 247.3（0.62×）。8B 能进 4090 的 24 GB，这台机器上切成两张卡没有吞吐收益。

PP=2 纯 compile 以前误用了 `max-autotune-no-cudagraphs`，卡过 15 分钟。后来只让 `tp>1` 走这个 mode，纯 PP 用 `reduce-overhead`，大概 1 分钟能编完。附录 B 有记录。

### Graph / compile 跟模型大小

![0.6B、8B、14B 的倍率](figures/fig05_opt_scale.svg)

柱顶的倍率：Graph decode 是 6.6× / 1.5× / 1.2×，compile TTFT 是 4.1× / 1.13× / 1.04×。14B 是 PP=2，不是单卡。模型越大，启动开销占比越低，这两项相对收益就越小。

### 相对单卡

0.6B 用 decode 比，8B 用 batch-8 比，都是同一模式相对单卡。

![相对单卡](figures/fig06_scaling.svg)

虚线是 1.0。Graph 下 TP=2、PP=2 都在线下。明显高于 1 的只有 0.6B eager 的 PP=2（1.39×）。

### 14B 和 4B 的 DP

14B 单卡放不下。用的是 `--pp-layer-counts 12,28 --device-ids 1,0`：12 层给 4070，28 层给 4090。20/20 会把 4070 打爆。

4B 的 DP=1 就是单卡 4090；DP=2 是 4090 + 4070，请求 round-robin，看 32 路聚合。

![14B PP 和 4B DP](figures/fig07_14b_dp.svg)

14B 上 Graph 大约 1.2×，compile 大约 1.04×。4B 的 DP=2 比 DP=1 慢（eager 1146.7 对 1432.8），慢卡卡住 round-robin，两份权重和 KV 还各占一份显存。DP=2 再开 Graph，4070 上 OOM：模型和 CUDA 上下文大约 10.8 GB，再加按 `max_num_seqs` 捕获的图，12 GB 不够。

### 和官方 vLLM

只在环境 A 上对了 0.6B、8B 的单卡和 TP=2。

![decode：v4 和 vLLM](figures/fig08_vs_vllm.svg)

0.6B 开 Graph：v4 单卡 decode 433.9，官方 231.8；batch-8 是 2734.4 对 1335.9。eager 两边差不多。8B 的 decode / batch 差几个百分点。compile 不是同一件事：v4 只编 prefill，官方 `VLLM_COMPILE` 是全模型。0.6B 单卡 TTFT，v4 compile 到 4.78 ms，官方还在 23 ms 左右。8B compile TTFT：单卡 35.47 对 38.56，TP=2 47.33 对 51.36。

附录 B 写了对照边界。TTFT、batch-8 的完整表在 A.5、A.6。

## 4. 环境 B：4 张 3090

### 张量并行

![0.6B 和 8B 的 TP](figures/fig09_envB_tp.svg)

0.6B 没测 TP=2。单卡 Graph decode 369.2 tok/s，大约 2.7 ms/token，已经低于前面说的 4.7 ms 通信下限。TP=4 不管 eager（0.73×）还是 Graph（0.70×）都更慢。Graph 的 batch-8 从 2311.7 掉到 1201.0。这尺寸不要做 TP。

8B 在 eager 里 TP 也是负的（TP=2 / TP=4 decode 0.75× / 0.74×）。Graph 把 all-reduce 的 launch 收进去，每卡权重变成 1/TP，decode 才上去：50.2 → 73.5（1.46×）→ 105.4（2.10×）。Graph 相对 eager 的 decode 倍率：单卡 1.37×，TP=2 2.66×，TP=4 3.89×。

TTFT 一直更差。单卡 Graph 69.01 ms，TP=2 95.59，TP=4 86.59。prefill 256 token 时单条 all-reduce 已经是 MB 量级，次数乘延迟盖过 GEMM。batch-8 开 Graph 是 333.2 → 384.1 → 451.0，相对单卡最多 1.35×，离 4 倍还远。

### 四卡怎么切 8B

8B 单卡放得下。下面三个布局都占满 4 张卡。切法和 KV 大小见 A.9。32 路 round-robin：DP=4 每副本大约 8 路，另外两个每副本大约 16 路。六组都没 OOM。

![8B 四卡：DP 和混合并行](figures/fig10_envB_dp.svg)

32 路、一共 4096 个生成 token。DP=4 + Graph 是 1166.3 tok/s。DP=2×TP=2 是 1088.5，DP=2×PP=2 是 994.9。

和上一节的 TP=4 Graph batch-8（451.0）不是同一指标，但量级差得很明显。这台上 8B 要用满四卡，复制四份比切成一份划得来。混合并行副本里还要做 all-reduce 或 PP 传输，副本数又少一半，所以没超过纯 DP。DP×TP 开 Graph 之后比较接近（0.93×），因为 8B 的 TP+Graph 本身已经转正；DP×PP 最慢（0.85×），和环境 A 上 PP 最差对得上。

如果模型单卡放不下，只能先 TP/PP 切开再复制，才会用到混合布局。8B 用不上。

### 32B

3090 上 TP=1、TP=2 eager 都会 OOM（权重大约 62 GB；TP=2 每卡还大约 31 GB）。CG 没跑，eager 已经装不进。只能 TP=4。开 Graph 之后 decode 12.1 → 34.8（2.9×），batch-8 101.7 → 173.3。

单卡对照只能用同机那张空闲的 A100 80GB。HBM 和 3090 的 GDDR6X 不是一种东西，别拿来算「4 张 3090 相当于几张 A100」。

![32B：4×3090 TP=4 和 A100 单卡](figures/fig11_32b.svg)

Graph decode：4×3090 TP=4 是 34.8，A100 单卡是 23.2。TTFT 还是 A100 好（107.96 ms 对 214.50）。A100 上 Graph 几乎没动（20.4 → 23.2），32B 单卡 decode 已经是带宽墙，不是 launch。

## 5. 同一份 8B，两张单卡

两台机器都测了 8B 单卡 eager / Graph。一张 4090 D 对一张 3090，只比较单卡快慢。

![8B 单卡](figures/fig12_cross_8b.svg)

4090 D 三条都更好：Graph decode 57.6 对 50.2，batch-8 400.2 对 333.2，TTFT 40.82 ms 对 69.01 ms。0.6B 单卡 Graph 也是同一方向：decode 433.9 对 369.2，batch-8 2734.4 对 2311.7，TTFT 18.70 ms 对 24.58 ms。

哪张卡更快，推不出并行该怎么切。两台都没 P2P：能单卡放下就单卡加 Graph，或者复制多份；权重大到单卡带宽成瓶颈、或者根本装不下，再上 TP 加 Graph。

## 6. 怎么配

环境 A：0.6B 用单卡 Graph，TTFT 在乎就再开 compile。8B 同样单卡 Graph，别 TP/PP。14B 只能不均分 PP。4B 别 DP 到 4070 上，尤其别再开 Graph。

环境 B：0.6B 单卡 Graph，别 TP=4。8B 四卡用 DP=4 加 Graph（32 路 1166.3 tok/s）；如果只在乎单条 decode、可以接受更差的 TTFT，TP=4 + Graph 能到 105.4 tok/s。32B 只能 TP=4，装进去之后把 Graph 打开。

官方对照只在环境 A。0.6B 开 Graph 时 v4 明显高于官方；8B 两边接近。

以后若要补：Graph 捕获的 batch 上限（环境 A 上 DP=2 OOM 和这个有关），TTFT 改成多次取中位数。

## 附录 B 实现和对照边界

v4 对官方：贪心 decode、单机，没有投机解码和多模态。KV 这边多用显式块数，官方按 `gpu_memory_utilization` 自适应；这组 batch8 都没顶到 KV。compile 不对等，见正文。官方 V1 离线没有 PP。都是单次测量。

PP 的 compile mode：`tp>1` 用 `max-autotune-no-cudagraphs`，单卡或纯 PP 用默认的 `reduce-overhead`。8B PP=2 compile 修之前超过 15 分钟，修之后大约 1 分钟，TTFT 53.43 ms，decode 20.9，batch8 152.4。

PP 的 CUDA Graph 是 piecewise：recv/send 在图外，图内只跑本 stage，写到静态 `_pp_send` / `_decode_out`（vLLM #35162）。`test/test_parallel.py --tp 1 --pp 2`。

DP 副本用 `spawn`。副本里 `tp*pp>1` 时 `MultiprocExecutor` 还要再起 worker。Python 不允许 daemon 进程再有子进程，所以副本是 `daemon=False`，`destroy()` 里 `join` / `terminate`。`daemon=True` 时纯 DP=4 能跑，DP 再叠 TP/PP 会直接 `AssertionError: daemonic processes are not allowed to have children`。
