# v4 性能对比

本文给出 v4 引擎在当前开发机（环境 A）上的完整性能矩阵，并与官方 vLLM（0.26.0）在相同模式下做对照。核心回答三个问题：

- 单卡和多卡（TP、PP）各自跑多快，谁更划算。
- 开启 CUDA Graph（CG）和 `torch.compile` 分别带来多少收益。
- v4 与官方 vLLM 在同一台机器、同一模型、同一批场景下差多少。

硬件互联与并行策略的背景见 [00-并行环境.md](00-并行环境.md)、[01-硬件互联.md](01-硬件互联.md)，通信测量方法见 [服务器测量.md](服务器测量.md)。

## 1. 测试环境与方法

### 1.1 硬件与模型

- 机器：环境 A，RTX 4090 D（24GB）+ RTX 4070 SUPER（12GB），双路 Xeon。
- 拓扑：两卡之间 SYS，`nvidia-smi topo -p2p r` 为 NS，即无 P2P、跨 NUMA，通信绕主机内存。
- 模型：Qwen3-0.6B（hidden=1024，28 层，head_dim=128）。
- 计算精度：bfloat16。
- 默认设备序：`cuda:0` = 4090 D（快卡），`cuda:1` = 4070 SUPER（慢卡），两套环境一致。

### 1.2 测量场景与指标

每个配置测三组场景，prompt 固定 256 token，贪心采样，`ignore_eos`，`max_tokens=128`：

| 指标 | 含义 | 测法 |
| --- | --- | --- |
| TTFT | 首 token 时间 | 单请求从提交到产出首个 token 的墙钟时间 |
| 单请求 decode | 单条请求的解码吞吐 | 128 token 去掉首 token 后的 `tok/s` |
| batch=8 吞吐 | 8 路并发的聚合吞吐 | 8 条请求总 token 数 / 墙钟时间 |

v4 用 `bench/bench_parallel.py`（`--tp --pp --cg --compile`），官方 vLLM 用 `bench/bench_vllm_official.py`（`--tp --cg --compile`）。两者统一 `max_num_seqs=16`、`context_len=4096`、`gpu_memory_utilization=0.6`、`dtype=bfloat16`。

> 注意：以下为单次测量，TTFT 单发噪声约 5%~10%，decode/吞吐已对 100+ token 取平均，较稳定。TTFT 只作趋势参考，结论以 decode 与 batch 吞吐为准。

## 2. v4 基准矩阵

### 2.1 全部 12 配置原始数据

| 配置 | TTFT (ms) | 单请求 decode tok/s | batch=8 吞吐 tok/s |
| --- | --- | --- | --- |
| 单卡 eager | 19.43 | 65.3 | 487.3 |
| 单卡 CG | 18.70 | 433.9 | 2734.4 |
| 单卡 compile | 4.78 | 63.9 | 484.1 |
| 单卡 CG+compile | 4.53 | 432.2 | 2664.6 |
| TP=2 eager | 25.74 | 42.5 | 324.8 |
| TP=2 CG | 25.74 | 354.4 | 2156.9 |
| TP=2 compile | 29.43 | 39.5 | 331.4 |
| TP=2 CG+compile | 27.96 | 348.7 | 2041.1 |
| PP=2 eager | 15.55 | 90.5 | 664.8 |
| PP=2 CG | 27.15 | 257.9 | 1540.5 |
| PP=2 compile | 13.06 | 92.9 | 662.9 |
| PP=2 CG+compile | 29.78 | 236.2 | 1477.6 |

### 2.2 CG 的收益

CG 是对 decode 影响最大的开关，四种并行布局一致成立。

| 布局 | eager decode tok/s | CG decode tok/s | 倍率 | batch=8 倍率 |
| --- | --- | --- | --- | --- |
| 单卡 | 65.3 | 433.9 | 6.6x | 5.6x |
| TP=2 | 42.5 | 354.4 | 8.3x | 6.6x |
| PP=2 | 90.5 | 257.9 | 2.8x | 2.3x |

decode 阶段每步只推少量 token，计算量小，Python 调度与 kernel 启动开销占据主导。CG 把整条 decode 流水线（含 PP 的 recv→层→send）固化成一张图，消除启动开销，单卡从 65 拉到 434 tok/s。TP=2 的倍率反而更高（8.3x），因为 TP 每步有几十次小消息 all-reduce，eager 下这些集合通信的启动开销叠加更严重，CG 一并压掉。PP=2 倍率最低（2.8x），因为 PP 本身层数减半、每步计算已较小，eager 的启动开销占比相对低。

### 2.3 compile 的收益

compile 只作用于 prefill 路径（decode 仍走 CG 或 eager），因此收益集中在 TTFT。

| 布局 | eager TTFT (ms) | compile TTFT (ms) | 倍率 |
| --- | --- | --- | --- |
| 单卡 | 19.43 | 4.78 | 4.1x |
| TP=2 | 25.74 | 29.43 | 0.87x |
| PP=2 | 15.55 | 13.06 | 1.2x |

单卡 compile 把 TTFT 从 19.4 压到 4.8 ms，因为 256 token 的 prefill 在 eager 下要拆成 28 层 × 十几个小算子逐个发射，`torch.compile` 把整段 forward 融合成少数 kernel，Python 与启动开销几乎清零。decode 吞吐几乎不变（63.9 vs 65.3），符合"compile 只编译 prefill"的设计。

TP=2 的 compile 反而让 TTFT 变差（25.7 → 29.4 ms）。原因是在多卡路径下，编译对象是含 all-reduce 的模型 forward，`torch.compile` 采用 max-autotune 会反复试配置，且 prefill 里的集合通信无法被融合，autotune 的额外开销抵消了融合收益。这是当前实现的一个已知短板。

### 2.4 TP 与 PP 的扩展性

以 decode 吞吐看并行扩展（CG 模式）：

| 布局 | decode tok/s | 相对单卡 |
| --- | --- | --- |
| 单卡 CG | 433.9 | 1.00x |
| TP=2 CG | 354.4 | 0.82x |
| PP=2 CG | 257.9 | 0.59x |

CG 模式下 TP、PP 都是负收益，且 PP 更差。原因正是 [01-硬件互联.md](01-硬件互联.md) 里预判的：这台机器无 P2P，TP 每层 all-reduce、PP 每步 send/recv 都要绕主机内存，通信时间压过计算减半省下的时间；再加上 4070 SUPER 明显慢于 4090 D，异构让慢卡成为整条流水线的瓶颈。

eager 模式下结论不同：

| 布局 | decode tok/s | 相对单卡 |
| --- | --- | --- |
| 单卡 eager | 65.3 | 1.00x |
| TP=2 eager | 42.5 | 0.65x |
| PP=2 eager | 90.5 | 1.39x |

eager 下 PP=2 反而比单卡快 39%。因为 eager 被 Python/启动开销主导，PP 把每卡层数从 28 减到 14，直接砍掉一半的调度与发射量；而 TP 每步通信次数多，通信开销盖过了算力减半的收益，仍是负的。

一句话：**显存放得下的模型，单卡 + CG 是这台机器的最优解；TP 在这台机器上任何模式都是负收益；PP 只在 eager 下有正收益，一旦开 CG 就被通信与异构卡拖累。**

## 3. v4 vs 官方 vLLM

官方 vLLM 用仓库自带的 `.venv-vllm`（vLLM 0.26.0，torch 2.11.0+cu130）。注意 vLLM 的 V1 引擎已移除离线 PP（`LLM` 不再有 `pipeline_parallel_size`），因此 PP=2 只能测 v4，无官方对照。

### 3.1 单卡与 TP=2 的逐项对照

| 模式 | 引擎 | TTFT (ms) | 单请求 decode tok/s | batch=8 吞吐 tok/s |
| --- | --- | --- | --- | --- |
| 单卡 eager | v4 | 19.43 | 65.3 | 487.3 |
| 单卡 eager | vLLM | 23.36 | 60.9 | 469.3 |
| 单卡 CG | v4 | 18.70 | 433.9 | 2734.4 |
| 单卡 CG | vLLM | 23.20 | 231.8 | 1335.9 |
| 单卡 compile | v4 | 4.78 | 63.9 | 484.1 |
| 单卡 compile | vLLM | 23.23 | 61.8 | 474.7 |
| TP=2 eager | v4 | 25.74 | 42.5 | 324.8 |
| TP=2 eager | vLLM | 27.09 | 45.1 | 298.8 |
| TP=2 CG | v4 | 25.74 | 354.4 | 2156.9 |
| TP=2 CG | vLLM | 24.33 | 205.9 | 1108.9 |

### 3.2 结论

**eager 模式两者基本打平。** 单卡 decode 65.3 vs 60.9、batch 487 vs 469，v4 略快 4%~7%；TP=2 则互有胜负（单请求 vLLM 略快，batch v4 略快）。eager 下两者都被 Python/启动开销主导，差距不大。

**CG 模式 v4 显著领先。** 单卡 decode 433.9 vs 231.8（1.9x），batch 2734 vs 1336（2.0x）；TP=2 decode 354.4 vs 205.9（1.7x），batch 2157 vs 1109（1.9x）。v4 的 CG 把整条 decode 流水线（模型、采样、PP 通信）整体固化，而官方 V1 引擎每步仍有调度器与运行时开销，差距在这一档被拉开。

**compile 模式 v4 的 TTFT 优势巨大。** v4 单卡 compile 把 TTFT 压到 4.78 ms，官方 `VLLM_COMPILE`（mode=3）在本次测试中几乎无收益（23.36 → 23.23 ms）。两者差异来自编译范围：v4 对 prefill forward 做整体 `torch.compile` 融合，而官方编译对本模型（0.6B、256 token）没有触发等价的融合收益。这既是 v4 的优势，也说明小模型上官方编译收益有限。

### 3.3 对比的边界与注意点

- 官方 vLLM 是通用引擎，带更多采样、投机解码、多模态等特性，本对比只覆盖"贪心 decode、小模型、单机"这一窄场景。
- 两者 KV cache 容量设置方式不同（v4 显式 64 块，vLLM 按 0.6 显存比例自适应），batch=8 场景下均未触顶，不影响结论。
- v4 的 compile 只编译 prefill，decode 走 CG/eager；官方 compile 是全模型编译，语义并不完全对等。
- 均为单次测量，TTFT 有 5%~10% 噪声，decode 与吞吐较稳定。

## 4. 复现方式

在 `vllm-v4/` 下：

```bash
# v4 矩阵（12 配置，写 bench/out/bench_parallel.txt）
bash bench/run_matrix_v4.sh

# 官方 vLLM 矩阵（6 配置，写 bench/out/bench_vllm_official.txt）
bash bench/run_matrix_vllm.sh
```

单个配置示例：

```bash
# v4：单卡 + CUDA Graph
../.venv2/bin/python bench/bench_parallel.py --tp 1 --pp 1 --cg --tag tp1pp1-cg

# 官方 vLLM：单卡 + CUDA Graph
../.venv-vllm/bin/python bench/bench_vllm_official.py --tp 1 --cg --tag vllm-tp1-cg
```

## 5. 优化方向

综合本矩阵，后续可优先做的三件事：

1. **TP=2 的 compile 负收益**。当前多卡路径用 max-autotune 且对含通信的 forward 编译，TTFT 反涨。可改为对 prefill 的"本地计算段"单独编译、通信段保持 eager，或改用 `reduce-overhead` 模式，避免 autotune 反复试探。
2. **PP 的 decode CG 通信**。PP=2 在 CG 下 0.59x 的扩展主要来自每步 send/recv 绕主机内存。可评估把中间张量收进静态 buffer 后做 pipeline 调度，或对跨卡小消息用合并传输，进一步压低 PP 通信延迟。
3. **TTFT 测量稳定性**。当前 TTFT 单发噪声偏大，可改为多次取中位数，便于回归对比。
