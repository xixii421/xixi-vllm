# 14 · 性能诊断与优化路线（全模块体检报告）

> 对应代码：`src/multimodal/`、`src/models/qwen3_vl.py`、`src/engine/model_runner.py`、`src/config.py`
> 目标：回答四个关键问题 —— **哈希设计对吗？compile 接对了吗？图的大小能确定吗（能不能做 prefill CUDA Graph）？整个模块怎么更简洁高效？** 并给出已落地的 8 项改动与验证结论。

---

## 1. 四个问题，一页答案

| 问题 | 结论 | 落地 |
|------|------|------|
| **哈希设计有问题吗？** | 有。旧版 hash PIL 原始图，与处理器配置脱钩，配置一变就**静默命中错误缓存**；还配了 fingerprint 与 CPU 双份缓存兜底，绕且冗余 | 改为 **hash 像素张量**，配置天然绑定，删 fingerprint + CPU 缓存 |
| **compile 接对了吗？** | 没接对。MM prefill 被条件 `inputs_embeds is None` 挡住，**永远走 eager**——而 MM prefill 恰恰是序列最长、最需要 compile 的路径 | 放开条件 + 新增 `_warm_compiled_mm` 预热 MM 输入形状，实测生效 |
| **图的大小能确定吗？** | **能。** 图的输入被 `vit_cg_token_budgets` 预算化（ViT 编码图）；LLM 侧 prefill 用 **piecewise 分片图**（固定 BS×SeqLen）覆盖。两条路径的图都是"固定大小" | ViT 图已存在；MM prefill 用 compile 兜底（见 §4 权衡） |
| **整个模块怎么更简洁高效？** | 复杂度的主要来源是"自造的复杂设计"（引用计数缓存、CPU 层缓存、重复的分片逻辑）——全部删除或复用 | 8 项改动，净删约 150 行，正确性/性能双提升 |

## 2. 先建立坐标系：v4 的多模态全链路

```text
processor (CPU)                    GPU
┌───────────────┐   pixel_values   ┌──────────────────────────────┐
│ 图→像素张量    │ ───────────────→ │ EncoderCache.get(hash(像素))  │ ← LRU，命中即返回
│ hash(像素张量) │                  │   miss → ViT encode          │
└───────────────┘                  │   hit / eager / CUDA Graph   │
                                   └──────────────┬───────────────┘
                                                  │ embeds + DeepStack
                                   ┌──────────────▼───────────────┐
                                   │ merge: 散落到文本 token 序列    │
                                   │ MRoPE: 构造 3D positions      │
                                   │ DeepStack: 逐层注入           │
                                   │ ┌──────────────────────────┐ │
                                   │ │ LLM forward              │ │
                                   │ │  文本 prefill → piecewise CG │
                                   │ │  MM  prefill → torch.compile│
                                   │ └──────────────────────────┘ │
                                   └──────────────────────────────┘
```

链路中每个方框都是一个"可被哈希 / 可被预算化 / 可被图化"的对象。下文逐个诊断。

## 3. 诊断一：哈希设计

### 3.1 旧设计的问题

旧实现里，哈希发生在 CPU 侧 `hash_pil_image(pil_image)`，返回后与 `config_fingerprint` 拼成 CPU 缓存 key。问题：

1. **hash 与数据语义脱钩**。`hash(cat.jpg)` 只编码了"这是哪张图"，没编码"这张图被处理成了什么"。改 `max_side`、改归一化参数后，**像素张量变了但 hash 不变** → CPU 缓存命中旧 pixel_values → 后面的 `grid_thw` 错位 → 静默错误。
2. **fingerprint 是"错误设计的补丁"**。为了修上面的脱钩，又引入"处理器配置指纹"拼进 key。但 fingerprint 只在 CPU 缓存这一层有效，GPU 侧 EncoderCache 的 key 仍是裸 `mm_hash`——两层 key 含义不一致，维护成本翻倍。
3. **双份缓存职责重叠**。CPU 层 `_img_cache`（省 image_processor 时间）+ GPU 层 EncoderCache（省 ViT 时间），key 都要走 `mm_hash` 打通，多一层状态就多一层出错面。

### 3.2 与官方对比

- **官方 vLLM**：在 `MultiModalInput` 构造时计算 `encoder_cache_key`，哈希对象是**经过 processor 处理的输入**。也就是"配置变化 → 输入变化 → key 变化"。
- **v4 现在**：哈希对象就是 `pixel_values` 本身（`hash_image_pixels`）。这是官方思路的极致化——**key 与数据完全同一实体**，指纹、CPU 缓存全部多余。

### 3.3 落地后的设计

```src/multimodal/hasher.py
def hash_image_pixels(pixel_values: torch.Tensor) -> str: ...
```

- `uid` 只由 `pixel_values` 决定，**处理器配置被隐式编码**进张量数值里。
- 删除：`_img_cache`、`_fingerprint_config`、CPU 层一切缓存状态。
- 语义：`uid = f(原始图, 全部预处理参数)`，且**无状态**（纯函数）。

> **教学点**：缓存 key 必须"绑定数据语义"。问自己一个问题——**"同 key 必同值"是否成立？** 旧设计 `hash(PIL) == hash(PIL)` 但值（pixel）不同 → 不成立；新设计 `hash(pixel) == hash(pixel)` 且值就是 pixel 本身 → 恒成立。

## 4. 诊断二：compile 集成

### 4.1 旧条件为什么挡住 MM prefill

```src/engine/model_runner.py
# 旧逻辑
use_compiled = ... and inputs_embeds is None and deepstack is None
```

MM prefill 的输入是 `inputs_embeds`（视觉 token 已 merge）+ 3D positions + deepstack，所以这个条件把 **所有** MM prefill 都挡在 compile 之外。而实际场景里，**带图请求的 prefill 长度往往是最长的**（一张大图产生上千个视觉 token），是 GPU 最忙、最该被编译优化的阶段。这是"正确但过于保守"的典型。

### 4.2 落地：放开条件 + 专项预热

新逻辑允许 MM prefill 进入 compile，并新增 `_warm_compiled_mm`：

```src/engine/model_runner.py
def _warm_compiled_mm(self, ...):
    # 用 MM 真实输入形状预热：inputs_embeds + 3D positions + deepstack
    ...

# 新逻辑
use_compiled = ...  # 不再排除 inputs_embeds / deepstack
```

**为什么需要预热？** `torch.compile`（inductor）对**动态 shape** 的策略是"每次新 shape 都重编译 Triton 内核"。MM prefill 的输入长度每次请求都不同，如果不在空闲时把常见 shape 编译好，第一次真实请求会撞上"编译卡顿"（traffic light 问题）。预热让编译发生在空闲窗口，让运行时直接命中已编译内核。

### 4.3 与 prefill CUDA Graph 的关系（关键权衡）

同样为了固定 MM prefill 的形状，**为什么不用 CUDA Graph 而用 compile？**

| | prefill CUDA Graph | torch.compile |
|---|---|---|
| 输入形状 | 必须固定（piecewise 分片 + padding） | 可动态，新 shape 重编译 |
| 覆盖文本 prefill | ✅ 已实现（`prefill_cuda_graph.py`） | ✅ |
| 覆盖 MM prefill | 需要**另一套图**（输入签名是 embeds + 3D positions + deepstack，与文本图的 input_ids 签名不同），维护两套图 | ✅ 一套机制覆盖 |
| 灵活性 | 高（replay 开销极低） | 中（有编译缓存管理成本） |

**当前 v4 的组合是最优性价比**：文本 prefill 走 piecewise CG（形状规整、命中率高），MM prefill 走 compile（形状剧烈变化，CG 的固定形状收益被 padding 抵消，compile 的动态重编译更省心）。**只有文本和 MM 的形状都高度规整时，才值得为 MM 单独建图**——这是 §7 的路线图项。

## 5. 诊断三：图的大小能否确定 → prefill CUDA Graph

用户的核心疑问：**"图的大小是不是可以确定的？这样就可以进行 prefill CUDA graph？"** 答案是分两层的：

### 5.1 ViT 编码图：可以确定，用预算化

ViT 的输入是 `pixel_values [N_patches, flat_patch]` + grid 元数据。`N_patches = t×h×w` 由图像分辨率决定，**看似变化无穷，但可以用 token 预算表框住**：

```10:13:src/multimodal/vision.py
    def __init__(self, vit, *, token_budgets=None, max_batch_size=4):
        ...
        self.token_budgets = sorted(token_budgets or [64, 128, 256, 512, 1024, 2048])
```

`try_encode` 找到**最小的、能装下当前总 token 数**的预算 → 用该预算的固定缓冲 + graph replay。**padding 的代价是"图内多算的 token"**，但因为预算粒度是 2 的幂（64→2048），平均浪费率 ≤ 1/2，且被"零内核启动开销"完全覆盖。第 10 讲已有详细分析，这里只重申：**ViT 图的输入是"可预算化的"，因此大小可以确定。**

### 5.2 LLM prefill 图：可以确定，用 piecewise 分片

MM prefill 的总长度 = 文本 tokens + 视觉 tokens + padding。视觉 tokens 已被预算化，**真正动态的是文本部分** → 用第 5 讲/`prefill_cuda_graph.py` 的 **piecewise 方案**：把任意长度切成固定 `(BS, SeqLen)` 分片，最后一片 padding 到分片大小（KV 写入用 `slot=-1` 跳过）。**图本身的大小永远是固定的**，变的只是"这次回放几次、最后一次 pad 多少"。

### 5.3 结论

> **"图的大小是否确定"取决于你愿意付出多少 padding。** v4 的回答：
> - ViT 图：预算化（padding 均值 25%，graph replay 收益完全覆盖）；
> - LLM 文本 prefill：piecewise 分片（padding 只出现在最后一个分片，且有 `slot=-1` 零成本丢弃）；
> - LLM MM prefill：compile（图需要另建一套签名，padding 收益 < 建图维护成本）。
>
> 所以 **prefill CUDA Graph 不仅在文本路径可用，在 MM 路径也"可以确定"**，只是当前用 compile 是更省的方案。

## 6. 诊断四：其他发现与落地（P0/P1/P2）

### 6.1 P0 · EncoderCache 引用计数泄漏（已修 → 纯 LRU）

`release()` 从未被调用 → entry 永不驱逐 → 长跑 OOM。改为纯 LRU 后删除 `_refs/retain/release/can_allocate` 约 60 行。详见第 09 讲 §6。

### 6.2 P1 · MM prefill 绕过 compile（已修）

见 §4，放开 `use_compiled` 条件 + `_warm_compiled_mm`。

### 6.3 P1 · ViT CG 命中率不足（已修 → 扩预算）

`vit_cg_token_budgets` 从 `(64,128,256,512,1024)` 扩到 `(64,128,256,512,1024,2048)`、`max_batch_size` 从 1 提到 4：

```src/config.py
vit_cg_token_budgets = (64, 128, 256, 512, 1024, 2048)
vit_cg_max_batch_size = 4
```

高分辨率图（token > 1024）与多图并发（batch > 1）原本必然 miss，现在能命中图。代价是每个预算都要占一份显存缓冲（2048 token 预算约 ×4 内存），由显存换延迟。

### 6.4 P2 · 像素预搬运（已修）

旧逻辑把多张图的 pixel 在 **CPU 侧** cat 一次再整体搬 GPU（一次大拷贝 + 一次中间 CPU 分配）。新逻辑**每张图直接 pinned → GPU non_blocking**，再在 GPU 上 cat：

```src/models/qwen3_vl.py
# 旧: cpu_pixels = torch.cat([p.cpu() for p in pixels])  →  .to(device)
# 新: 各自 .to(device, non_blocking=True) → 在 GPU 上 cat
```

pinned 内存 + non_blocking 让拷贝与上一个 kernel 重叠；GPU cat 省一次 H2D 往返。多图 + 高分辨率场景收益明显。

### 6.5 P2 · 抽 `shard_copy` 复用 QKV 分片（已修）

ViT 的 `qkv` 和 LLM 的 fused `qkv/gate_up` 权重复制逻辑相同（把单个权重切片拷进融合张量的特定行），原两处各写一遍。抽出：

```src/models/loader.py
def shard_copy(src, dst, row0, num_rows): ...
```

两处调用点收敛为一行，删除重复约 40 行。

### 6.6 顺带修复的两个既有 bug

| Bug | 位置 | 修复 |
|-----|------|------|
| 多图占位符过度展开（`str.replace` 会连第一个图已展开的 pad 一起替换） | `processor.py::_expand_image_pads` | 改用 `prompt.split(pad)` + 逐个 join |
| Triton 3.2 下 `_scaled_gemm_kernel` 共享内存超限（OutOfResources） | `fused_gemm.py` | 显式 `num_stages=2` |

## 8. 剩余优化路线（做还是不做，都说得清）

| 优先级 | 方向 | 预期收益 | 成本 | 建议 |
|--------|------|----------|------|------|
| P1' | MM prefill 独立 CUDA Graph（embeds 签名图） | prefill 启动开销再降一个量级 | 维护第二套图 + padding 预算 | **暂缓**，compile 已够，形状太动态 |
| P2' | ViT CG 动态预算（按请求自适应选择预算粒度） | 减少 padding 浪费 | 预算选择逻辑复杂化 | 视命中率数据决定 |
| P2' | pixel 搬运进 ViT CG（把 H2D 也 graph 化） | 省拷贝启动 | 需要 pinned 静态缓冲 | 低优先 |
| 工程 | 把 `vit_cg_*` 配置并入统一的 profile 文件 | 配置可观测 | 一文件 | 推荐 |

**判断标准**：每项改动都要能回答"**省的是内核启动还是 HBM 往返？省的量 vs 维护成本**"。图化省启动，融合省 HBM，缓存省重复计算——别用错工具。
