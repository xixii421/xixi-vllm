# 02 · 图像预处理与模板展开

> 对应代码：`src/multimodal/processor.py`、`src/multimodal/image.py`、`src/multimodal/hasher.py`
> 目标：讲清楚"一张 PIL 图片"和"一段用户文本"如何变成模型能吃下的 `pixel_values + image_grid_thw + token_ids`。

---

## 1. 为什么需要预处理

LLM 只认识 token（整数 id），ViT 只认识"归一化像素张量"。两者都需要从原始输入加工而来：

| 原始输入 | 加工目标 | 谁来做 |
|---------|---------|--------|
| PIL 图片 | `pixel_values`（归一化像素）+ `image_grid_thw`（网格描述） | `image_processor` + 封装 |
| 用户文本 | `token_ids`（含占位符展开）+ 占位符区间 | `tokenizer` + `apply_chat_template` + 展开 |

`processor.py` 的核心职责是把这两件事的产物打包成一份 `MultiModalInputs`，并为每张图计算**像素哈希**——它是 GPU 侧 `EncoderCache` 的缓存 key（第 09 讲）。

## 2. 图像预处理链：`_prepare_pil` + `_encode_image`

### 2.1 预处理（EXIF + RGB）

```25:47:src/multimodal/processor.py
    @staticmethod
    def _prepare_pil(image):
        """Match official vLLM multimodal image prep: EXIF + RGB (RGBA→white bg)."""
        image = normalize_image(image)
        return convert_image_mode(image, "RGB")

    def _encode_image(self, image) -> _CachedImageFeat:
        """Run HF image_processor only (no text)."""
        image = self._prepare_pil(image)
        ip = self.p.image_processor
        out = ip(images=[image], return_tensors="pt")
        pv = _cpu_unpinned(out["pixel_values"])
        grid = out["image_grid_thw"]
        if grid.dim() == 1:
            grid = grid.view(1, -1)
        g = grid[0]
        g_tuple = (int(g[0]), int(g[1]), int(g[2]))
        n_patches = g_tuple[0] * g_tuple[1] * g_tuple[2]
        return _CachedImageFeat(
            pixel_values=pv, grid_thw=g_tuple, num_patches=n_patches
        )
```

分三层看：

**第一层：`_prepare_pil`** —— 只做两个确定性操作：
- `normalize_image`（`image.py`）：`ImageOps.exif_transpose` 修正 EXIF 旋转。手机照片常带旋转标记，不转的话图像是横着的。
- `convert_image_mode(image, "RGB")`（`image.py`）：RGBA → RGB 时用白底合成（`rgba_to_rgb`），PNG 透明区域变成白底而不是黑底。

```18:31:src/multimodal/image.py
def normalize_image(image: Image.Image) -> Image.Image:
    with contextlib.suppress(Exception):
        image = ImageOps.exif_transpose(image)
    return image


def rgba_to_rgb(
    image: Image.Image,
    background_color: tuple[int, int, int] | list[int] = (255, 255, 255),
) -> Image.Image:
    assert image.mode == "RGBA"
    converted = Image.new("RGB", image.size, background_color)
    converted.paste(image, mask=image.split()[3])
    return converted
```

**第二层：`_encode_image`** —— 调用 HF 的 `image_processor`（`Qwen3VLImageProcessor`），得到 `pixel_values` 和 `image_grid_thw`。**HF 的 processor 内部做了 resize（按 min/max_pixels 缩放）、归一化（mean/std）、转 tensor**，这些都不需要我们手写。

> **为什么 v4 不自己写 image_processor？** HF 的 `Qwen3VLImageProcessor` 遵循 Qwen 官方的"像素预算"缩放逻辑（min_pixels/max_pixels），自己重写极易出错（缩放算法、插值方式、归一化都必须与训练时完全一致）。**复用 transformers 是正确做法**——这本身就是"标准件复用"的一个例子（第 13 讲会展开）。

**第三层：`_cpu_unpinned`** —— 把 `pixel_values` 保持为 **CPU、contiguous、非 pinned** 的 tensor。

```53:61:src/multimodal/processor.py
def _cpu_unpinned(t: torch.Tensor) -> torch.Tensor:
    t = t.detach().contiguous()
    if t.device.type != "cpu":
        t = t.cpu()
    if t.is_pinned:
        out = torch.empty(t.shape, dtype=t.dtype, device="cpu")
        out.copy_(t)
        return out
    return t
```

**为什么故意 unpinned？** 每个请求的 `_encode_image` 都是**实时执行**的（CPU 侧不做缓存了，见第 4 节），`pixel_values` 只是临时握在手里、等待 `process()` 结束时打包进 `MultiModalInputs`。此时 pin 它没有意义——pinned 内存池是稀缺资源（不可换页），应该只给"即将做 H2D 的张量"用。真正要搬 GPU 的那一步在 `encode_and_merge`（`qwen3_vl.py`）里，那里才 `pin_memory()`。**pin 的时机放在"即将使用"处，而不是"提前很久"处**——这是内存工程的细节（第 12 讲会讲 H2D 优化）。

### 2.2 `grid_thw` 是什么

`image_grid_thw` 是一个 `[N, 3]` 的整数张量，`(t, h, w)` 三要素：

```text
t = temporal 维度块数（图片恒为 1，视频才是帧数）
h = 高度方向 patch 块数
w = 宽度方向 patch 块数
```

例如一张图经过 HF processor 缩放后被切成 `14×14` 的 patch 网格，`grid_thw = [1, 14, 14]`。

**为什么需要它？** 三个用途：
1. 决定占位符展开数量：`t * h * w // merge_size²` 个 `<|image_pad|>`（见第 01 讲）。
2. ViT 前向需要它来生成位置编码（第 03 讲）和 `cu_seqlens`（第 04 讲）。
3. MRoPE 需要它来生成 3D 位置（第 05 讲）。

**`num_patches` 与 `num_tokens` 的区别**要特别注意：

```41:50:src/multimodal/processor.py
@dataclass(slots=True)
class _CachedImageFeat:
    pixel_values: torch.Tensor  # CPU, contiguous, unpinned
    grid_thw: tuple[int, int, int]
    num_patches: int

    @property
    def num_tokens(self) -> int:
        # Qwen-VL: vision tokens after spatial merge.
        return self.num_patches  # filled with merge-aware count at cache time
```

- `num_patches = t * h * w`：patch 总数（进 ViT 的 token 数，也是 ViT 输出的 token 数）。
- 散落到文本序列的视觉 token 数是 `num_patches // merge_size²`（`_vision_tokens`），因为 **PatchMerger 会把 `2×2` 的 patch 合并成一个**（第 03 讲）。

## 3. 文本侧：chat template → 占位符展开 → tokenize

### 3.1 构建消息并套模板

```139:145:src/multimodal/processor.py
        msgs = [
            {
                "role": "user",
                "content": [{"type": "image", "image": img} for img in images]
                + [{"type": "text", "text": text}],
            }
        ]
        prompt = self.p.apply_chat_template(
            msgs, tokenize=False, add_generation_prompt=True
        )
        prompt = self._expand_image_pads(prompt, feats)
        ids = self.p.tokenizer.encode(prompt)
```

注意这里用的是**多模态消息格式**（`content` 是 `[{type:image}, {type:text}]` 的列表），HF 的 `Qwen3VLProcessor.apply_chat_template` 会把它渲染成含 `<|image_pad|>` 占位符的字符串。

### 3.2 占位符展开

```105:123:src/multimodal/processor.py
    def _expand_image_pads(self, prompt: str, feats: list[_CachedImageFeat]) -> str:
        """Replace each single ``<|image_pad|>`` with grid-sized repeats (Qwen-VL).

        Uses ``split`` so multi-image prompts expand each placeholder in order;
        a naive ``str.replace(..., count=1)`` loop re-matches the pad rows just
        emitted for the previous image (first span over-expands, last stays 1).
        """
        pad = self._image_pad
        parts = prompt.split(pad)
        if len(parts) != len(feats) + 1:
            raise RuntimeError(
                f"expected {len(feats)} pad(s) ({pad!r}) in chat template prompt, "
                f"found {len(parts) - 1}"
            )
        out = [parts[0]]
        for i, feat in enumerate(feats):
            out.append(pad * self._vision_tokens(feat))
            out.append(parts[i + 1])
        return "".join(out)
```

**展开逻辑**：chat template 里只有 1 个 `<|image_pad|>`，但实际视觉 token 有 `n = num_patches // merge_size²` 个，所以把 1 个占位符替换成 `n` 个连续占位符。

> **为什么用 `split` 而不是 `str.replace(..., count=1)` 循环？** 这是修复过的一个真实 bug：`replace` 循环在第二张图时，会把**第一张图刚展开出的那一串 pad 再当占位符匹配一次**，导致第一段过度展开、最后一段剩下 1 个 pad → token 数与 `grid_thw` 对不上 → `encode_and_merge` 里张量长度不匹配报错。`prompt.split(pad)` 把占位符位置一次性切开，再按序逐个展开，天然免疫这种"已展开内容被二次匹配"的问题。

> **为什么不在 HF 里直接展开？** HF 的 `Qwen3VLProcessor` 其实可以做多 token 的 placeholder 展开（`image_token_id` 重复），但 v4 走的是"先拿到字符串再统一 tokenize"的路径，展开放在 tokenize 之前更简单。两种方式结果一致。

### 3.3 解析占位符区间（MMPlaceholder）

tokenize 之后，`_placeholders` 负责定位每张图在 `token_ids` 里的起止：

```162:196:src/multimodal/processor.py
    def _placeholders(self, ids: list[int], uids: list[str]) -> list[MMPlaceholder]:
        if self.img_tok is None:
            return []
        out: list[MMPlaceholder] = []
        if self.vs_tok is not None and self.ve_tok is not None:
            vs = [i for i, t in enumerate(ids) if t == self.vs_tok]
            ve = [i for i, t in enumerate(ids) if t == self.ve_tok]
            if len(vs) != len(ve):
                logger.warning(
                    "vision_start/end count mismatch (%s vs %s)", len(vs), len(ve)
                )
            for idx, (s, e) in enumerate(zip(vs, ve)):
                if e <= s:
                    continue
                n = sum(1 for t in ids[s + 1 : e] if t == self.img_tok)
                uid = uids[idx] if idx < len(uids) else f"img-{idx}"
                out.append(
                    MMPlaceholder(
                        modality="image", offset=s + 1, length=n, mm_hash=uid
                    )
                )
            return out

        pos = [i for i, t in enumerate(ids) if t == self.img_tok]
        if not pos:
            return []
        out.append(
            MMPlaceholder(
                modality="image",
                offset=pos[0],
                length=len(pos),
                mm_hash=uids[0] if uids else "img-0",
            )
        )
        return out
```

两种解析路径：
- **带 `vision_start/end` token**（Qwen3 用 `<|vision_start|>`/`<|vision_end|>` 包裹图像）：在 start/end 之间数 `<|image_pad|>` 的个数，得到 `(offset, length)`。支持多图。
- **无 start/end**（某些模板只用一个 image token）：退化为找第一个 image token，length 是所有 image token 的个数。

产出的 `MMPlaceholder` 会进一步变成 `MultiModalFeature` 挂到 Sequence 上（第 08 讲）。

## 4. 像素哈希：CPU 不缓存，key 绑定配置

### 4.1 为什么 CPU 侧不做缓存了

早期 v4 在 `processor.py` 里维护了一个进程级 `_img_cache`（key = `(mm_hash, config_fingerprint)`，value = 预处理结果），想省掉重复的 `image_processor` CPU 时间。**后来整体删除了**，原因：

- **收益极低**：`image_processor` 单张图耗时才几毫秒 CPU 时间，且每个请求都要跑；真正的瓶颈在 GPU 侧（ViT 编码几十毫秒），那部分已有 `EncoderCache` 覆盖（第 09 讲）。
- **双份缓存职责重叠**：CPU 缓存和 GPU 缓存都要靠同一个哈希打通，多一层状态就多一层出错面。
- **正确性隐患**：为了"配置变了不命中旧缓存"，还得额外拼一个 `config_fingerprint`（把 min_pixels/max_pixels/patch_size 等参数 SHA-1 一下）——这是"错误设计的补丁"，治标不治本。

**v4 现在的做法**：CPU 侧只做**无状态的纯函数**——每次请求实时 `_encode_image` + 算哈希，把"缓存"这件事**完全交给 GPU 侧的 `EncoderCache`**。

### 4.2 哈希对象：像素张量，而不是 PIL 图

        uids = [hash_image_pixels(f.pixel_values) for f in feats]
```

    ...
```

**为什么 hash 像素张量而不是 hash 原始 PIL 图？** 因为 `pixel_values = f(原始图, 处理器全部配置)`：

- 改 `max_side`（缩放尺寸）→ `pixel_values` 变了 → `grid_thw` 变了 → **hash 必须跟着变**，否则会命中旧尺寸的缓存，散落 token 数与 `grid_thw` 对不上，静默错位。
- 改归一化 mean/std → 同理。

**hash 像素张量让"配置绑定"自动成立**：配置一变，张量就变，hash 就变，旧缓存自然失效。不需要 fingerprint，不需要额外状态。

> 对比 vLLM 官方：官方在 `MultiModalInput` 构造时算 `encoder_cache_key`，同样以**经过 processor 处理的输入**为哈希对象。v4 的 `hash_image_pixels` 是这一思路的极致——哈希对象就是 `pixel_values` 本身。

### 4.3 与 GPU 侧 EncoderCache 的关系

```
processor.py（CPU，无状态）             EncoderCache（GPU，第 09 讲）
   _encode_image(image)                  key = hash_image_pixels(pixel_values)
   hash_image_pixels(pixel_values)   →   命中 → 直接复用 ViT 输出的 embeds
   → uid（绑定配置）                     miss → 跑 ViT encode → put
```

- **CPU 侧不做缓存**：`_encode_image` 每次实时执行（省心，且 image_processor 不是瓶颈）。
- **GPU 侧缓存**：跳过整个 ViT 前向（省 GPU 时间，这是真正的瓶颈）。

哈希是打通这条链的钥匙：**同一个 uid，在处理器里生成，在 `EncoderCache` 里查。** 由于 uid 绑定配置，配置一旦改变就自然错过缓存——这就是"key 绑定数据语义"的意义。

## 5. 一个完整的 `process()` 数据流

```text
process(text, images)
   │
   ├─ [图像]
   │    _prepare_pil(image)          # EXIF + RGB
   │    _encode_image(image)         # HF image_processor → pixel_values + grid（实时，不缓存）
   │    hash_image_pixels(pixel_values)   # → uid（绑定处理器配置）
   │
   ├─ [文本]
   │    apply_chat_template(msgs)    # → 含 <|image_pad|> 的 prompt
   │    _expand_image_pads(prompt)   # 1 个占位符 → n 个（按各图 grid 逐个展开）
   │    tokenizer.encode(prompt)     # → token_ids
   │    _placeholders(ids, uids)     # → MMPlaceholder 列表
   │
   └─ 打包
        pixel_values = cat(各图 pv)
        grid = [[t,h,w], ...]
        MultiModalInputs(token_ids, mm_kwargs, placeholders, mm_hashes)
```

> 注意：**uid 在这里生成、在 `EncoderCache` 里消费**（第 09 讲）。CPU 侧不再有缓存——`_encode_image` 每次实时跑，哈希是纯函数，缓存这件事整体下沉到 GPU 侧。

## 6. 动手实验

1. 打印 `_encode_image` 返回的 `_CachedImageFeat`：对一张 `1000×800` 的图，`grid_thw` 和 `num_patches` 是多少？`num_tokens`（散落后视觉 token 数）又是多少？体会 `min_pixels/max_pixels` 的缩放效果。
2. 打印 `hash_image_pixels(pixel_values)`，然后改 `max_side`（如 512→1024）再打一次 —— 断言两次 uid 不同（验证"配置绑定"）。
3. 换一张 RGBA 的 PNG，看 `convert_image_mode` 后像素值的变化（透明区应变成 255 而不是 0）。
4. 把 `_expand_image_pads` 的 `n` 改成固定值（比如 64），看 ViT 编码输出 shape 是否报错 —— 体会"占位符数量必须与 grid 一致"的约束。
5. 传入两张不同的图，观察 `_expand_image_pads` 用 `split` 逐个展开（对照：若用 `str.replace(..., count=1)` 循环，第二个占位符会被第一张图已展开的 pad 干扰）。
