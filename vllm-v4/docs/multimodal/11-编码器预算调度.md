# 11 · 编码器预算调度：保证"未编码不过图"

> 对应代码：`src/engine/scheduler.py`（`_clamp_chunk_for_encoder_budget`、`preempt`）、`src/memory/sequence.py`（`prefix_cacheable_full_blocks`、`reset_mrope_state`）
> 目标：讲清多模态调度器的三个不变量 —— 编码器预算截断、preempt 重置 MRoPE、前缀缓存截断，以及它们为什么是正确性底线。

---

## 1. 三个不变量（v4 设计底线）

第 01 讲提过，这里集中讲透。多模态调度正确性依赖三条：

| # | 不变量 | 保证什么 | 代码 |
|---|--------|---------|------|
| 1 | **未编码不过图** | 调度器不会让 prefill 越过未编码的图片 token | `_clamp_chunk_for_encoder_budget` |
| 2 | **Preempt 重置 MRoPE** | 重新 prefill 时位置状态一致 | `preempt` + `reset_mrope_state` |
| 3 | **含图页不进前缀缓存** | 图像 KV 不污染文本前缀缓存 | `prefix_cacheable_full_blocks` |

## 2. 不变量 1：编码器预算截断

### 2.1 为什么需要预算

ViT 编码（每图几十毫秒）和 LLM prefill（每 token 亚毫秒）是**两种完全不同的计算密度**。如果调度器只看 LLM token 预算，可能一个 chunk 里塞了 8 张图 —— 编码器计算变成 8 倍，TTFT 爆炸。

`encoder_compute_budget`（默认 = `max_num_batched_tokens`）限制 **一个 batch 里最多编码多少视觉 token**。调度 chunk 时累加图片 token 数，超预算就在图片前截断。

### 2.2 代码与三种截断情形

```133:160:src/engine/scheduler.py
    def _clamp_chunk_for_encoder_budget(self, seq: Sequence, chunk: int) -> int:
        """Shorten chunk so overlapping vision tokens fit the encoder budget.

        If the next image alone exceeds the budget but the cursor is already at
        that image, still schedule the image (official all-or-nothing exception)
        so the request cannot stall forever.
        """
        if not seq.has_multimodal or chunk <= 0:
            return chunk
        budget = self.encoder_compute_budget
        start = seq.num_cached_tokens
        end = start + chunk
        used = 0
        for mf in seq.mm_features:
            img_start = mf.start
            img_end = mf.start + mf.num_encoder_tokens
            if img_end <= start:
                continue
            if img_start >= end:
                break
            if used + mf.num_encoder_tokens > budget:
                # Truncate before the image when text prefix remains.
                if img_start > start:
                    return img_start - start
                # Already at the oversized image → schedule it alone.
                return min(chunk, img_end - start)
            used += mf.num_encoder_tokens
        return chunk
```

**三种情形**（对照第 01 讲）：

**情形 A：chunk 会越过一张预算放不下的图，且光标还没到图** → 在图片前截断：
```python
if used + mf.num_encoder_tokens > budget:
    if img_start > start:
        return img_start - start   # 只处理到图片前
```

**情形 B：光标已在图片上（图起点 ≤ start），但图超预算** → 调度整张图（all-or-nothing）：
```python
return min(chunk, img_end - start)   # 调度到图片末尾
```
**为什么必须这样？** 图 token 数由 `grid_thw` 决定，调度器不能"半张图"。如果总是截断在图前，而图本身超预算，请求就永远卡在图上 —— **must schedule 的例外保证不死锁**。

**情形 C：预算足够** → 累加 `used`，继续下一张图，最终原样返回 `chunk`。

### 2.3 教学要点

- `used` 只累加**会实际编码的图**（与窗口有交集的，`img_end > start` 才考虑）。
- 截断返回的是**能处理的 token 数**，调度器用 `chunk = min(need, remaining); chunk = _clamp(...)` 直接替换原 chunk —— 语义清晰、无副作用。
- **截断方向是"图前截断"而不是"图后截断"**：图前文本先处理，图留到下一 chunk。这保证图片编码时，其前面的文本 KV 已就位。

## 3. 不变量 2：Preempt 重置 MRoPE

### 3.1 为什么 preempt 会破坏 MRoPE

preempt（抢占）时，被抢占序列的 **KV 被释放**（`kv.deallocate(seq, publish=False)`），它之后要**从第 0 个 token 重新 prefill**。但 `seq.mrope_next`（MRoPE 光标）还停在**被抢占前的位置**。如果不清零，重新 prefill 时位置从旧值续，视觉 token 位置错乱。

### 3.2 代码

```210:220:src/engine/scheduler.py
    def preempt(self, seq: Sequence) -> None:
        if seq.status == SequenceStatus.FINISHED:
            return
        seq.status = SequenceStatus.WAITING
        seq.is_prefill = True
        self.kv.deallocate(seq, publish=False)
        # KV was dropped → the sequence re-prefills from scratch, so its MRoPE
        # cursor must reset too (otherwise chunked position math is stale).
        if seq.has_multimodal:
            seq.reset_mrope_state()
        self.waiting.appendleft(seq)
```

**`reset_mrope_state()` 做了什么**（`sequence.py`）：把 `mrope_next=None`、`rope_delta=0`、`mrope_origin=None` 等 MRoPE 相关状态清零。**注意是"仅当 `has_multimodal`"时重置** —— 纯文本序列不需要，零开销。

### 3.3 教学要点

这是"**状态与资源同生命周期**"的经典例子：MRoPE 光标本质上是从 KV 派生的（`mrope_next` 依赖已处理 token），**KV 丢则光标必丢**。任何"清 KV 但忘清派生状态"的实现都会出隐蔽 bug —— 排查这类 bug 时，要优先检查"哪些状态是从 KV 派生的"。

## 4. 不变量 3：含图页不进前缀缓存

### 4.1 为什么图后文本的 KV 不能进 APC

v3 的自动前缀缓存（APC，hash/radix）按 token 内容哈希 KV 页。**纯文本没问题，但含图序列有根本矛盾**：

1. **"图后文本"的 token 相同，但位置不同** —— 位置依赖图（MRoPE 第 05 讲），图分辨率不同 → 位置不同 → KV 不同。token 哈希一致但 KV 不一致。
2. **图的 token 是 `<|image_pad|>` 占位符**，不同请求的占位符 token 完全相同，但**实际视觉内容不同** —— token 哈希一致但语义不同。

所以含图序列**绝不能把"图及图后"的页 publish/match 进 APC**。

### 4.2 代码：`prefix_cacheable_full_blocks`

```156:160:src/memory/sequence.py
    def prefix_cacheable_full_blocks(self) -> int:
        n_full = self.num_full_blocks()
        if not self.mm_features:
            return n_full
        return min(n_full, self.first_mm_token // self.block_size)
```

**只允许"第一张图之前"的完整块进 APC**：`min(n_full, first_mm_token // block_size)`。`hash_index.py` / `radix_index.py` 在 match/publish 时都通过这个函数取实际 cacheable 范围。

```text
[文本... | 图 token | 文本...]
  ↑ 可缓存      ↑ 不可缓存（含图页）
 first_mm_token
```

> **为什么图前的文本可缓存？** 图前的纯文本 token 位置不受图片影响（MRoPE 三轴相同、无跳跃），KV 与"同一个 system prompt 的纯文本请求"完全一致 → 可以复用。**图前文本是安全的 APC 前缀，图及图后不是** —— 这是"多模态与前缀缓存共存"的精确边界。

## 5. 三个不变量如何协作（一个完整场景）

```text
请求 A（长文本 + 一张 4K 图）被调度：
  chunk 1: 文本前 1000 token → 图前截断（预算不包含图）
           · 图前的完整块 publish 进 APC ✓
  chunk 2: 图（3000 视觉 token）→ 单图调度（情形 B）
           · EncoderCache miss → ViT encode → cache put
           · 含图页不进 APC ✓
  chunk 3: 图后文本 → MRoPE 从图片最大坐标续接 ✓

  中途被 preempt：
    · KV 释放，reset_mrope_state ✓
    · 重新 prefill：chunk 1' 复用 APC 前缀（图前文本 hit）
    · chunk 2' 再编码图时 EncoderCache hit（图已在缓存）
```

**三个不变量互相支撑**：预算截断让"图前文本"可独立成 chunk（进 APC）；preempt 重置保证重新 prefill 的位置正确；APC 截断保证缓存内容的语义安全。配合 EncoderCache（第 09 讲），重复请求的全部成本被逐层消除。

## 6. 动手实验

1. 用长 prompt + 大图，把 `max_num_batched_tokens` 调小，观察 `_clamp_chunk_for_encoder_budget` 在日志/断点里如何截断 chunk。
2. 人为把 `encoder_compute_budget` 设成比单张图 token 数还小，验证情形 B（must-schedule）生效、请求不卡死。
3. 注释掉 `preempt` 里的 `reset_mrope_state()`，构造一个会触发抢占的负载，观察生成结果错乱。
4. 打开 `prefix_backend="hash"`，用同一 system prompt + 不同图片发两个请求，验证图前文本 APC 命中但图后不命中。
