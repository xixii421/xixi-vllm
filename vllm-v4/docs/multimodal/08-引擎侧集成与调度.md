# 08 · 引擎侧集成与调度：多模态如何插进 v3 引擎

> 对应代码：`src/engine/model_runner.py`、`src/engine/scheduler.py`、`src/memory/sequence.py`
> 目标：讲清多模态请求在引擎里的完整路径 —— `Sequence` 上挂什么、调度器加什么、执行器怎么分发、以及"decode 对多模态透明"这个设计如何成立。

---

## 1. 设计原则：文本路径零回归

v4 的首要约束是**纯文本请求完全不受多模态影响**。这是通过在 `model_runner` 里加**条件分支**而不是改造主路径实现的：

```276:297:src/engine/model_runner.py
        # Multimodal prefill: ViT (+EncoderCache), scatter embeds, 3-axis MRoPE.
        inputs_embeds = None
        deepstack = None
        if is_prefill and self.is_multimodal and any(s.has_multimodal for s in seqs):
            inputs_embeds, deepstack, positions3d = self.model.encode_and_merge(
                inputs.input_ids, seqs, self.device
            )
            inputs.inputs_embeds = inputs_embeds
            inputs.deepstack_input_embeds = deepstack
            inputs.positions = positions3d
        elif self.is_multimodal:
            rope_fn = getattr(self.model, "_mrope_module", None)
            if callable(rope_fn):
                host_max = 0
                for s in seqs:
                    if is_prefill:
                        host_max = max(
                            host_max, s.num_cached_tokens + s.num_scheduled_tokens
                        )
                    else:
                        host_max = max(host_max, len(s) + int(s.rope_delta))
                rope_fn().ensure_cache_size(host_max + 1)
```

**分支逻辑**：
- `any(s.has_multimodal for s in seqs)` 为真 → 走 `encode_and_merge`（多模态 prefill 完整路径）。
- 否则 → `ensure_cache_size` 扩展 MRoPE 表（即使是纯文本，也要保证 decode 的 `rope_delta` 有位置可用）。
- 其余所有逻辑（decode CG、prefill CG、compile、eager forward）**原样复用 v3**。

## 2. `Sequence` 上挂什么：`MultiModalFeature`

多模态状态全部挂在一个 `Sequence` 上，不污染全局状态：

```python
# src/memory/sequence.py（关键字段）
seq.has_multimodal          # 是否有 mm_features
seq.mm_features             # list[MultiModalFeature]
seq.mrope_next              # 下一个 token 的 MRoPE 起点（chunked 续接）
seq.rope_delta              # decode 阶段位置偏移
seq.first_mm_token          # 第一张图之前的 token 数（前缀缓存截断用）
```

`MultiModalFeature` 是一个 dataclass，记录一张图的所有信息：

```python
class MultiModalFeature:
    uid: str                 # 图像内容哈希（EncoderCache 的 key）
    start: int               # 图在完整 prompt 中的起始 token 位置
    num_encoder_tokens: int  # 图的视觉 token 数
    grid_thw_tuple: tuple    # (t, h, w)
    data: torch.Tensor       # pixel_values（CPU）
    request_id: str          # 引用计数用
    deepstack: list | None   # 缓存的 DeepStack 特征
    mrope_origin: int | None # 图的 MRoPE 基准位置（跨 chunk 复用）
    ...
```

**为什么这些状态要挂 Sequence 而不是全局？** 因为：
1. chunked prefill 时，**同一张图的编码跨越多个 chunk**，状态必须跟着 sequence 走。
2. 并发多请求时，各自的状态互不干扰。
3. decode 阶段序列已经"带过"图片了，`rope_delta` 让 decode 能正确换算位置。

## 3. 调度器新增：编码器预算（`_clamp_chunk_for_encoder_budget`）

第 01 讲已经看过代码，这里从"为什么插在调度器"的角度再强调：

**调度器是唯一知道"这个 chunk 会包含几张图"的地方**（它决定 `num_scheduled_tokens`）。所以编码器预算截断**必须**在调度器做 —— 让 `encode_and_merge` 拿到的窗口天然满足预算约束，执行层无需再检查。

**截断的三种情形**（`scheduler.py:133-160`）：
1. **chunk 会跨过图片但预算不足** → 在图片前截断（`return img_start - start`），这个 chunk 只处理图前文本。
2. **光标已经在图上了但图超预算** → 调度"单独这张图"（`return min(chunk, img_end - start)`），保证不死锁。
3. **预算够** → 原样返回 chunk。

> **为什么要有情形 2 的"例外"？** 如果图片本身 token 数就超预算（超高分辨率图），永远截断在图片前会导致请求永久无法推进。官方的 all-or-nothing 约定：**单张超预算图必须调度**，即使超预算，否则请求饿死。

## 4. 执行器：一条多模态 prefill 的完整 forward


**执行顺序（优先级从高到低）**：

| 路径 | 条件 | 说明 |
|------|------|------|
| Decode CG | `not is_prefill && can_use` | 纯文本 decode，CG replay |
| Prefill CG | `is_prefill && 无 mm && 首 chunk` | piecewise prefill CG（第 10 讲逻辑的文本侧） |
| **eager / compile** | **含 mm（`inputs_embeds` 非空）** | **多模态必然走这里** |

**注意 `inputs_embeds is None and deepstack is None` 在 prefill CG 和 compile 分支里的双重门控** —— 这就是"多模态 prefill 绕开所有文本侧优化"（piecewise CG、torch.compile）的地方，是第 13 讲的重点优化方向。

**`forward_context` / `attention_context`** 是线程局部上下文，把 paged attention 需要的元数据（`cu_seqlens`、`block_tables`、`slot_mapping` 等）传给 FlashInfer 后端。**多模态和文本用同一个 backend**，只是 `positions` 换成了 3D、`inputs_embeds` 非空。

## 5. decode 为什么对多模态透明

decode 阶段（`is_prefill=False`）**完全不知道图片存在过**：

```64:88:src/engine/scheduler.py
    def _schedule_decode(
        self,
        prefills: list[Sequence],
        decodes: list[Sequence],
        tokens_used: int,
    ) -> int:
        while self.running and self._room(prefills, decodes):
            if tokens_used + 1 > self.max_num_batched_tokens:
                break
            seq = self.running.popleft()
            ...
```

调度器的 `_schedule_decode` **完全不看 `mm_features`** —— 它只按 token 预算和 KV 空间挑选 decode 序列。执行器（`model_runner.py`）的 decode 分支（`_run_batch(seqs, is_prefill=False)`）同样没有多模态分支，只有 `is_prefill=True` 时才会进 `encode_and_merge`。

原因：
1. **视觉 token 的 KV 在 prefill 时已写入 KV cache**（作为普通 token 参与注意力）。decode 只关心"当前 token 与前面所有 token 的注意力"。
2. **MRoPE 在 decode 退化为 1D**（第 05 讲），`rope_delta` 提供偏移，等价于普通 RoPE。
3. **DeepStack 只在 prefill 注入** —— decode 生成的 token 都是文本，不需要再注入。

**这就是"多模态的一切都在 prefill 消化完"的机制基础**：decode 路径与 v3 完全一致，CG 直接复用，**性能零回归**。

## 6. 一个完整的调度 + 执行时间线

```text
t0: add_request(prompt, images=[cat])
    Sequence 入队 waiting，mm_features 挂好
t1: scheduler.schedule()
    → 选中该 seq 为 prefill
    → _clamp_chunk_for_encoder_budget: chunk 包含图片但预算够 → 全量
    → (prefills=[seq], decodes=[])
t2: model_runner.run(prefills, decodes)
    → _run_batch(prefills, is_prefill=True)
    → has_multimodal=True → encode_and_merge
      · embed_tokens(text) → inputs_embeds 骨架
      · _encode_visual: EncoderCache miss → ViT encode → embeds
      · scatter: 视觉 embeds → inputs_embeds 占位符位置
      · _build_deepstack → [ndps][N, hidden]
      · mrope_positions → [3, N] positions
    → eager forward: model(inputs_embeds, deepstack, positions_3d)
t3: scheduler.postprocess(prefills, p_ids)
    → num_cached_tokens 推进，KV publish
t4: 之后每步 decode
    → _run_batch(decodes, is_prefill=False)
    → decode CG replay（视觉 token 的 KV 已就位）
    → 完全透明
```
