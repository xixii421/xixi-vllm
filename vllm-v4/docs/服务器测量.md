# 服务器带宽测量与实机剖析

拓扑矩阵和 P2P 判定都是纸面参数，真正的通信性能必须动手测出来。本文给出系统的测量方法，再用三台真实机器做完整剖析，最后收成一套拿到新机器时的标准探究流程。


整篇文档的结构如下。

- [1] 如何测量一台服务器的真实带宽。
- [2] 用三台真实服务器做完整的架构剖析。
- [3] 拿到新机器时的标准探究流程。

## 1. 如何测量一台服务器的真实带宽

### 1.1 为什么纸面参数不够

`nvidia-smi topo -m` 和 `nvidia-smi topo -p2p r` 回答的是"卡之间物理上能不能直连、走什么拓扑"，但回答不了两个关键问题。

一是带宽到底有多少。标称带宽和实际可用带宽差得很远。PCIe 的 TLP 头和协议开销吃掉 15% 到 20%，NVLink 也有链路层的开销。厂商标称的"PCIe 4.0 x16 单向 31.5 GB/s"，实测有效带宽往往只有 25 GB/s 左右。

二是延迟到底有多高。拓扑矩阵只说"这条路径经过哪些节点"，不说每个节点要花多少时间。同样是 P2P 直连，NVLink 延迟在 1 到 2 微秒，PCIe 同 switch 在 3 到 5 微秒，跨 NUMA 要 10 微秒往上，无 P2P 绕主机内存更是 30 微秒以上。这些差距只有实测才能得到。

所以拿到一台机器，除了看拓扑，还必须做两轮测量，一轮测点对点裸传输，一轮测 NCCL 集合通信。前一轮回答"卡间硬通道能跑多快"，后一轮回答"训练和推理真正用到的 all-reduce 有多快"。

### 1.2 测量工具全家桶

主流的测量工具如下。

**NVIDIA nccl-tests**，官方集合通信基准，编译后得到 `all_reduce_perf`、`all_gather_perf`、`reduce_scatter_perf` 等可执行文件，是判断一台机器能否支撑分布式训练的事实标准。它报告两个带宽指标，algbw 是算法带宽，busbw 是总线带宽。busbw 才是和硬件标称值直接可比的那个，因为它是按集合通信的数据移动次数修正过的。对 all-reduce，busbw = algbw 乘以 2(n-1)/n。

**CUDA Samples 的 p2pBandwidthLatencyTest**，官方点对点基准，输出卡与卡之间的带宽矩阵和延迟矩阵，分 P2P enabled 和 P2P disabled 两种传输。注意 CUDA Samples 的注释提醒过，它不是为性能测量设计的，结果仅供参考，但作为快速体检足够。

**bandwidthTest**，同为 CUDA Samples，测单卡访问自身显存的带宽，用于对照"单卡带宽"和"卡间带宽"的差距。单卡 HBM 带宽在 1 TB/s 量级，卡间走 PCIe 只有几十 GB/s，差了两个数量级，这个对比能帮人建立"为什么要少搬数据"的直觉。

**本仓库的 `bench/bench_bandwidth.py` 和 `bench/probe_server.py`**，用 PyTorch 直接实现上述两类测试，只依赖 torch，拷到任何多卡机器就能跑，不需要编译。bench_bandwidth.py 测点对点裸传输和 NCCL all-reduce 的延迟带宽曲线，probe_server.py 在带宽基础上加了解码步通信量估算和 TP 判语。

### 1.3 点对点裸传输怎么测

点对点测的是两张卡之间直接搬数据的带宽和延迟，对应推理引擎里 send/recv 或者跨卡 copy 的开销。

延迟用最小的消息测。开两个 device 上的张量，来回 copy 一百次取中位数，得到的就是一次跨卡传输的固定开销。这个开销由物理路径决定，NVLink 在 1 到 2 微秒，PCIe 同 switch 在 3 到 5 微秒，跨 NUMA 在 10 微秒以上，无 P2P 绕主机内存要 30 到 50 微秒。

带宽用大消息测。消息从 2KB 一路翻倍扫到 256MB，每个尺寸取多次 copy 的中位数，带宽会随消息变大而上升，直到饱和。饱和带宽就是这条物理通道的有效上限。

以环境 A 为例，`torch.cuda.can_device_access_peer` 返回 NS，传输必须绕主机内存。实测 4B 消息延迟约 37 微秒，带宽从 2KB 的 0.05 GB/s 一路爬升，4MB 处 13.3 GB/s，16MB 处 15.7 GB/s，到 256MB 饱和在 16.7 GB/s。对比单卡 HBM 的约 1 TB/s，卡间通道只有它的六十分之一。

### 1.4 NCCL 集合通信怎么测

点对点测的是裸通道，但实际训练推理用的是集合通信。同一台机器上，all-reduce 的实测往往比点对点裸 copy 更低，因为集合通信有协议开销和算法本身的传输冗余。

NCCL 集合通信用 nccl-tests 测，核心命令如下。

```bash
./build/all_reduce_perf -b 8 -e 512M -f 2 -g 1
```

参数含义，-b 是最小消息字节数，-e 是最大消息字节数，-f 是步进因子（2 表示每档翻倍），-g 是每个节点用几张卡。输出里有两个带宽，algbw 是算法带宽，busbw 是总线带宽。小消息段看延迟，大消息段看 busbw 是否接近硬件上限。

读结果时有一个约定，对比硬件标称值必须用 busbw 而不是 algbw。因为 all-reduce 在 n 张卡之间要移动 2(n-1)/n 倍数据量，algbw 是实际吞吐，busbw 把它折算成单条物理链路的利用率，这样不同卡数之间的结果才有可比性。

本仓库的 `bench/bench_bandwidth.py` 用 torch 实现了同样逻辑。运行环境 A 的实测如下。

```bash
python bench/bench_bandwidth.py --devices 0,1 -b 2048 -e 268435456 -f 2
```

点对点裸传输的结果。

| 消息大小 | 带宽 GB/s | 说明 |
| --- | --- | --- |
| 4 B | 延迟 37 us | 一次跨卡传输的固定开销 |
| 2 KB | 0.05 | 延迟主导，带宽无意义 |
| 32 KB | 0.83 | 延迟主导 |
| 256 KB | 6.08 | 开始进入带宽主导区 |
| 4 MB | 13.30 | 接近饱和 |
| 64 MB | 16.48 | 饱和 |
| 256 MB | 16.69 | 饱和上限 |

NCCL all-reduce（world=2）的结果。

| 消息大小 | 延迟 us | busbw GB/s | 说明 |
| --- | --- | --- | --- |
| 2 KB | 77.3 | 0.02 | 固定延迟主导 |
| 128 KB | 84.4 | 1.45 | 仍是延迟主导 |
| 256 KB | 82.9 | 2.94 | 过渡区 |
| 1 MB | 153.1 | 6.38 | 带宽主导 |
| 4 MB | 458.3 | 8.52 | 饱和点 |
| 64 MB | 7436.8 | 8.40 | 稳定 |
| 256 MB | 29982.0 | 8.34 | 稳定 |

读这两张表的要点，小消息段延迟几乎持平，2KB 到 256KB 都在 77 到 86 微秒，全部被固定的跨卡延迟主导，消息变大带宽才慢慢爬升。这条曲线正好对应 [硬件互联.md](硬件互联.md) 里的无 P2P 档，绕主机内存两次 DMA，上限就在 12 到 13 GB/s。

对比点对点裸 copy 的饱和带宽 16.7 GB/s，all-reduce 的 busbw 只有 8.5 GB/s，恰好是一半。这是集合通信的固有代价，all-reduce 需要每张卡同时向对端发数据和收数据，双向共享同一条物理链路，而点对点单向 copy 只占一条方向。这个对比提醒我们，评估 TP 成本时要用 all-reduce 的实测带宽，不能用裸 copy 的乐观值。

### 1.5 测量结果的读法

拿到一组测量数据，按三步解读。

第一步看延迟。小消息延迟决定通信的固定开销，直接影响每层做一次 all-reduce 的最低耗时。延迟高到几十微秒的机器，层数一多，56 次 all-reduce 叠加起来就是几毫秒。

第二步看带宽饱和值。大消息 busbw 是否接近机器类型对应的预期，NVLink 机器应该在数百 GB/s，PCIe 同 switch 在 20 到 25 GB/s，跨 NUMA 在 12 到 18 GB/s，无 P2P 在 10 GB/s 上下。若远低于预期，可能是 NVLink lane 损坏、驱动异常或者 NCCL 走了错误路径，配合 `NCCL_DEBUG=INFO` 看日志能定位。

第三步折算成业务量。把目标模型的每层通信量代进延迟曲线，得到单步通信总耗时，再和单卡计算时间比。这就是 [并行环境.md](并行环境.md) 里说的通信计算比，也是最终决定用不用 TP 的依据。这一步 `probe_server.py` 已经封装好。

## 2. 三台真实机器的架构剖析

本文分析用的三台机器如下。

| 代号  | 配置 | 关系 |
| ---  | --- | --- |
| 环境 A  | RTX 4090 D + RTX 4070 S，双路 CPU | 单机 |
| 环境 B  | 4 卡，P2P 全 OK | 同构 A100 |
| 环境 C  | A100 80G + 4 张 RTX 3090 + Pro6000| 大模型异构 |

三台机器恰好覆盖了三种不同的硬件互联形态。

### 2.1 环境 A，本地工作站

环境 A 是用户日常开发的机器，配置如下。

- 两张卡，RTX 4090 D（24GB）和 RTX 4070 SUPER（12GB），强异构。
- 双路 Xeon Silver 4310，48 线程，两个 NUMA 节点。
- 卡分挂两个 NUMA 节点，拓扑显示 SYS，即跨 PCIe 加跨 CPU 总线。

关键判据来自两条命令。

`nvidia-smi topo -m` 显示 GPU0 和 GPU1 之间是 SYS，说明两卡之间要穿过 PCIe 交换机和 CPU 间的 UPI 总线。`nvidia-smi topo -p2p r` 显示 NS，即不支持的 P2P，也就是卡之间不能直接对等访问内存。

这两条叠加意味着通信数据要 GPU 0 写到主机内存，再让 GPU 1 从主机内存读，绕一大圈。实测 NCCL all-reduce 2MB 消息约 7.9GB/s，decode 每层 8KB 消息约 86 微秒一次（见上文 1.4 节）。整步 56 次 all-reduce 折算约 1.5ms，已经超过单卡完整 decode 步的计算时间。所以 TP 在这台机器上是负收益，实测也证实了这一点。

### 2.2 环境 B，四卡服务器

环境 B 是远程的 4 卡服务器，型号 SYS-420GP-TNR。它的拓扑矩阵如下。

```
        GPU0    GPU1    GPU2    GPU3
GPU0     X      PIX     SYS     SYS
GPU1    PIX      X      SYS     SYS
GPU2    SYS     SYS      X      PXB
GPU3    SYS     SYS     PXB      X
```

判读矩阵。GPU0 和 GPU1 之间是 PIX，同一 PCIe 交换机下，距离近延迟低。GPU2 和 GPU3 之间是 PXB，穿过 PCIe 桥，次优。GPU0 组和 GPU2 组之间是 SYS，跨 NUMA 节点，最差。同时 `nvidia-smi topo -p2p r` 显示全 OK，卡间支持对等访问，这意味着通信可以走 P2P 直连而不是绕主机内存。

这台机器的状态是 PCIe 同构多卡，P2P 可用但无 NVLink。最佳组合是 GPU0+1 做 TP=2，GPU2+3 做 TP=2，跨 NUMA 的组合要避免。它适合做 TP 实验，但不如 NVLink 机器。

### 2.3 环境 C，六卡异构服务器

环境 C 是远程的 6 卡服务器，型号 SYS-4029GP-TRT。它的拓扑矩阵如下。

```
        GPU0    GPU1    GPU2    GPU3    GPU4    GPU5
GPU0     X      NODE    NODE    SYS     SYS     SYS
GPU1    NODE     X      PIX     SYS     SYS     SYS
GPU2    NODE    PIX      X      SYS     SYS     SYS
GPU3    SYS     SYS     SYS      X      NODE    NODE
GPU4    SYS     SYS     SYS     NODE     X      PIX
GPU5    SYS     SYS     SYS     NODE    PIX      X
```

这台机器的组成如下。

- GPU3 是 A100 80G，其余五张是 RTX 3090 24G，强异构。
- 双路 Xeon Gold 5218R，80 线程，两个 NUMA 节点。
- GPU0/1/2 挂 NUMA0，GPU3/4/5 挂 NUMA1。
- 同 NUMA 内是 NODE 或 PIX，跨 NUMA 是 SYS。

`nvidia-smi topo -p2p r` 显示 GPU0 全 NS，其余卡之间多为 CNS，即芯片组不支持 P2P。NS 和 CNS 的实际效果都是无法直连，数据要绕主机内存。所以这台机器虽然卡多，但 TP 通信环境比环境 A 还差。

更致命的是异构。A100 和 3090 算力相差数倍，放进同一个 TP 组，每步都要等最慢的卡，A100 被 3090 拖到同一速度。所以环境 C 的正确用法是拆开用，A100 单独跑大模型，五张 3090 各自跑中小模型，最多做 PP，不做 TP。

### 2.4 三台机器的对照

| 机器 | 卡数 | 异构 | P2P | NUMA | TP 评价 | 最佳策略 |
| --- | --- | --- | --- | --- | --- | --- |
| 环境 A | 2 | 强异构 | NS | 跨 NUMA | 负收益 | 单卡 4090D + CUDA Graph |
| 环境 B | 4 | 未知 | OK | 跨 NUMA | 可用，优选同交换机 | 同交换机 TP=2 |
| 环境 C | 6 | 强异构 | NS/CNS | 跨 NUMA | 基本不可行 | 拆池，A100 单独用 |

三台机器给出一条共同的经验，无 NVLink 的机器上 TP 普遍是负收益或勉强可用，单卡往往更快。

下图把三台机器的卡间拓扑画在一起对照。可以看到环境 A 的两卡跨 NUMA 且无 P2P，环境 B 的卡对分挂在两个 NUMA 下但组内是 PIX 或 PXB，环境 C 的六张卡横跨两个 NUMA 且强异构。

## 3. 拿到新机器怎么探究

### 3.1 五条命令看硬件

拿到一台新服务器，先跑下面几条命令。

```bash
nvidia-smi -L                                # 有几张卡，什么型号
nvidia-smi --query-gpu=index,name,memory.total,pcie.link.gen.max,pcie.link.width.max --format=csv
nvidia-smi topo -m                           # 卡间拓扑连接类型
nvidia-smi topo -p2p r                       # 是否支持对等访问
lscpu | grep -E "Model name|Socket|NUMA node\(s\)"
```

第一眼要看的东西是卡数、型号、显存、NUMA 数。这些决定了机器属于 [硬件互联.md](硬件互联.md) 的哪一类状态。

### 3.2 判读拓扑矩阵

`nvidia-smi topo -m` 输出的矩阵里，连接类型按质量从好到坏排序。

- NV#，NVLink 连接，最好。
- PIX，同一 PCIe 交换机。
- PHB，同一 PCIe 主机桥。
- NODE，同 NUMA 内的 PCIe。
- PXB，穿过多个 PCIe 桥。
- SYS，穿过 PCIe 加 CPU 互联总线，最差。

`nvidia-smi topo -p2p r` 的判定分三档。OK 表示卡间可直接对等访问内存，P2P 可用。NS 表示不支持。CNS 表示芯片组不支持，实际效果和 NS 类似。只有 OK 才说明通信能走直连。

### 3.3 测真实通信延迟

拓扑只是纸面参数，真实延迟要实测。仓库里提供了 `bench/probe_server.py`，拷到任何有 torch 的机器上直接跑，会输出硬件清单、P2P 矩阵和 NCCL all-reduce 延迟曲线，并给出 TP 判语。

```bash
python bench/probe_server.py --devices 0,1 --hidden 1024 --layers 28 --batch 1
```

以环境 A 为例，上文 1.4 节的实测显示 NCCL all-reduce 2KB 消息约 77 微秒、8KB 约 86 微秒、512KB 约 104 微秒、2MB 约 249 微秒。把每层通信量代进去，可以得到整个 decode 步的通信总耗时，用它和单卡计算时间比较，就知道 TP 值不值。

### 3.4 形成决策

拿到数据之后按以下顺序决策。

1. 单卡显存放得下模型，直接用单卡，不做任何并行。
2. 放不下再考虑并行。P2P 是 OK 且同 NUMA 的卡优先组 TP。
3. 跨 NUMA 或异构的卡组，优先 PP。
4. 最后用真实引擎跑单卡、TP、PP 的端到端对比，用数据确认。

完整的决策树和端到端吞吐对照见 [并行环境.md](并行环境.md)。
