# v4 大模型性能对比（8B / 14B / 4B）

本文是 [02-性能对比.md](02-性能对比.md) 的续篇：把测试对象从 0.6B 小模型扩展到 8B / 14B / 4B 三档，在 v4 引擎与官方 vLLM（0.26.0）上，验证 `torch.compile`（prefill）与 CUDA Graph（decode）在 TP / PP / DP 三种并行下的收益，并回答"并行到底划不划算"以及"v4 重构后与官方差距多大"。

核心结论先行：

- **模型越大，CG 与 compile 的相对收益越小。** 0.6B 上 CG 是 6.6x、compile 是 4.1x；到 8B 只剩 CG 1.5x、compile 1.1x——因为大模型 decode/prefill 都被权重访存与算力主导，不再是 kernel 启动开销主导。
- **显存放得下的模型，单卡 + CG 仍是这台机器的最优解。** 8B（16 GB）能装进 24 GB 的 4090 D，此时 TP=2 / PP=2 都是负收益（无 P2P、跨 NUMA，通信开销压过算力减半收益）。
- **14B 靠不均分 PP 才跑得动。** 12 层放 12 GB 的 4070 SUPER、28 层放 24 GB 的 4090 D（`--pp-layer-counts 12,28`），decode 20~24 tok/s，证明 PP 的价值在于"装下更大的模型"而非"跑得更快"。
- **DP 在这台异构机器上不缩放。** 4B 用 DP=2（4090+4070）反而比单 4090 慢（1146 vs 1433 tok/s），慢卡成为 round-robin 的瓶颈。
- **v4 重构后与官方 vLLM 基本打平。** 8B 单卡 / TP=2 的 eager 与 CG 吞吐互有胜负、差距在个位数百分比。

## 1. 测试环境与方法

### 1.1 硬件与模型

| 项 | 值 |
| --- | --- |
| 机器 | 环境 A，RTX 4090 D（24 GB）+ RTX 4070 SUPER（12 GB），双路 Xeon |
| 拓扑 | 两卡无 P2P（`p2p r` = NS），跨 NUMA，通信绕主机内存 |
| 设备序 | `cuda:0` = 4090 D（快卡），`cuda:1` = 4070 SUPER（慢卡） |
| 精度 | bfloat16 |
| 模型 | Qwen3-8B（≈16 GB）、Qwen3-14B（≈29 GB）、Qwen3-4B（≈7.6 GB） |

权重规模决定可行布局：8B 单卡装得进 24 GB 卡，14B 任何单卡都装不下、只能 PP=2 不均分，4B 能装进两张卡、用于 DP 维度。

### 1.2 测量场景与指标

沿用 02 篇的三组场景（prompt=256、贪心、`ignore_eos`、`max_tokens=128`）：

| 指标 | 含义 | 测法 |
| --- | --- | --- |
| TTFT | 首 token 时间 | 单请求从提交到首个 token 的墙钟 |
| 单请求 decode | 单条解码吞吐 | 128 token 去掉首 token 的 `tok/s` |
| batch=8 吞吐 | 8 路并发聚合吞吐 | 总 token / 墙钟 |

DP 维度单独用 `bench/bench_dp.py`，测 32 条并发请求的聚合吞吐（tok/s）。每个布局跑 4 个开关：eager / CG / compile / CG+compile。

### 1.3 可行矩阵

| 模型 | 布局 | 关键参数 |
| --- | --- | --- |
| Qwen3-8B | 单卡 / TP=2 / PP=2 | 单卡用 `--device-ids 0`（4090） |
| Qwen3-14B | PP=2 | `--pp-layer-counts 12,28`（12→4070，28→4090） |
| Qwen3-4B | DP=1 / DP=2 | DP=1 用 4090，DP=2 用 0,1 |

官方 vLLM（`.venv-vllm`，V1 引擎已移除离线 PP）：仅 8B 单卡与 TP=2 的 eager / CG / compile；14B 单卡装不下、PP 无官方支持，故无 14B 对照。

## 2. v4 大模型矩阵

### 2.1 Qwen3-8B 全量数据

| 布局 | 模式 | TTFT (ms) | decode tok/s | batch=8 tok/s |
| --- | --- | --- | --- | --- |
| 单卡 | eager | 39.99 | 38.4 | 363.0 |
| 单卡 | CG | 40.82 | 57.6 | 400.2 |
| 单卡 | compile | 35.47 | 50.3 | 354.9 |
| 单卡 | CG+compile | 35.47 | 58.0 | 399.5 |
| TP=2 | eager | 47.88 | 31.3 | 229.9 |
| TP=2 | CG | 72.84 | 51.3 | 334.3 |
| TP=2 | compile | 47.33 | 33.7 | 240.1 |
| TP=2 | CG+compile | 62.48 | 51.0 | 333.3 |
| PP=2 | eager | 59.08 | 23.1 | 165.6 |
| PP=2 | CG | 75.63 | 35.2 | 247.3 |
| PP=2 | compile | 超时 | — | — |
| PP=2 | CG+compile | 66.11 | 35.4 | 247.5 |

> PP=2 的 `eager+compile`（`torch.compile` 且不开 CG）在 15 min 超时未完成，属当前实现的已知限制（多卡 + 纯 eager compile 路径），其余三档（含 `CG+compile`）均正常。

### 2.2 CG 的收益：随模型变大而衰减

![CUDA Graph speedup](figures/fig1_cg_speedup.svg)

| 布局 | eager decode | CG decode | 倍率 |
| --- | --- | --- | --- |
| 单卡 | 38.4 | 57.6 | 1.5x |
| TP=2 | 31.3 | 51.3 | 1.6x |
| PP=2 | 23.1 | 35.2 | 1.5x |

对比 0.6B 的单卡 6.6x，8B 的 CG 收益骤降到 1.5x。原因很直接：0.6B 每步 decode 只搬 1.2 GB 权重，Python 调度与 kernel 启动开销占主导，CG 把整条流水线固化后收益巨大；8B 每步要搬 16 GB 权重，时间几乎全花在访存与算力上，启动开销占比可忽略，CG 只能省下那一点固定开销。**CG 对"小而快"的模型是刚需，对"大而重"的模型只是锦上添花。**

### 2.3 compile 的收益：同样衰减

![compile TTFT](figures/fig2_compile_ttft.svg)

| 布局 | eager TTFT | compile TTFT | 倍率 |
| --- | --- | --- | --- |
| 单卡 | 39.99 | 35.47 | 1.13x |
| TP=2 | 47.88 | 47.33 | 1.01x |

0.6B 上 compile 把 TTFT 压到 4.1x，8B 只剩 1.13x。原因与 CG 相同：256 token 的 prefill 在 0.6B 上是"发 28 层小算子"的发射开销主导，`torch.compile` 融合后收益巨大；8B 的 prefill 是实打实的矩阵乘算力，融合省不下多少。TP=2 下 compile 依旧几乎无收益（47.88→47.33），与 02 篇结论一致。

### 2.4 TP / PP 扩展性：显存够就别切

![scaling](figures/fig3_scaling.svg)

以 CG 模式 batch=8 吞吐看相对单卡的扩展（单卡 400.2 tok/s 为 1.0x）：

| 布局 | batch tok/s | 相对单卡 |
| --- | --- | --- |
| 单卡 CG | 400.2 | 1.00x |
| TP=2 CG | 334.3 | 0.84x |
| PP=2 CG | 247.3 | 0.62x |

8B 单卡能装下，于是 TP / PP 全是负收益，且 PP 更差。这正是 [01-硬件互联.md](01-硬件互联.md) 预判的：无 P2P、跨 NUMA，TP 每层 all-reduce、PP 每步 send/recv 都要绕主机内存，通信时间压过算力减半省下的时间；异构卡（4070 慢于 4090）还让慢卡拖累整条流水线。**并行唯一的正当理由是显存不够，而不是速度。**

## 3. Qwen3-14B：PP=2 的不均分方案

14B（≈29 GB）任何单卡都装不下，只能切成 PP=2，并按两卡容量不均分：12 层（≈8.7 GB）放 4070 SUPER，28 层（≈20.3 GB）放 4090 D。

![PP 14B](figures/fig6_pp14b.svg)

| 模式 | TTFT (ms) | decode tok/s | batch=8 tok/s |
| --- | --- | --- | --- |
| eager | 77.26 | 20.2 | 145.8 |
| CG | 76.72 | 24.1 | 171.7 |
| compile | 74.41 | 20.6 | 147.9 |
| CG+compile | 75.21 | 24.0 | 171.2 |

14B 能跑起来（decode 20~24 tok/s），但 CG 只有 1.2x、compile 只有 1.04x，都进一步衰减——14B 每步要搬 29 GB 权重，优化空间更小。这一档的结论很明确：**PP 的价值是让装不下的模型能跑，而不是让能跑的模型更快。** 不均分 `pp_layer_counts` 是 v4 针对异构卡的实用能力（等分 20/20 会让 4070 超显存）。

## 4. Qwen3-4B：DP 不缩放

4B（≈7.6 GB）能装进两张卡，用于验证 DP。DP=1 用单张 4090 作基线，DP=2 用 4090+4070 两副本 round-robin。

![DP throughput](figures/fig5_dp.svg)

| 布局 | eager | compile | CG |
| --- | --- | --- | --- |
| DP=1（4090） | 1432.8 | 1403.6 | 2302.5 |
| DP=2（4090+4070） | 1146.7 | 1100.1 | OOM |

两个结论：

1. **DP=2 比 DP=1 慢（1146.7 vs 1432.8）。** 副本间 round-robin 均分请求，慢卡 4070 成为瓶颈，聚合吞吐被最慢副本卡死；再叠加副本间无共享、每副本都要独立加载模型与 KV。DP 只有在**同构、多副本、显存确实放不下单副本大 batch** 时才划算，这台异构双卡机器上不成立。
2. **DP=2 的 CG 在 12 GB 卡上 OOM。** 4B 模型 + CUDA 上下文在 4070 上已占 ~10.8 GB，eager/compile 用 16 块 KV（0.56 GB）勉强装下，但 CUDA Graph 捕获（默认捕获到 `max_num_seqs` 的 batch 上限）再占一块图内存就超了 12 GB。这是纯硬件约束，不是代码问题。

## 5. v4 vs 官方 vLLM（Qwen3-8B）

![v4 vs vLLM](figures/fig4_vs_vllm.svg)

| 布局 | 模式 | 引擎 | TTFT (ms) | decode tok/s | batch=8 tok/s |
| --- | --- | --- | --- | --- | --- |
| 单卡 | eager | v4 | 39.99 | 38.4 | 363.0 |
| 单卡 | eager | vLLM | 36.36 | 35.3 | 349.3 |
| 单卡 | CG | v4 | 40.82 | 57.6 | 400.2 |
| 单卡 | CG | vLLM | 55.89 | 59.4 | 403.0 |
| TP=2 | eager | v4 | 47.88 | 31.3 | 229.9 |
| TP=2 | eager | vLLM | 51.69 | 32.0 | 263.6 |
| TP=2 | CG | v4 | 72.84 | 51.3 | 334.3 |
| TP=2 | CG | vLLM | 52.05 | 57.7 | 363.8 |

**eager 与 CG 下两者基本打平。** 单卡 eager 的 decode 38.4 vs 35.3（v4 快 9%），CG 57.6 vs 59.4（vLLM 快 3%）；TP=2 下 vLLM 略快（32.0 vs 31.3，57.7 vs 51.3）。这与 0.6B 小模型上"v4 CG 领先 1.9x"形成鲜明对比：**模型一大，两者都被权重访存主导，实现层面的调度/启动差异被摊薄，吞吐收敛到同一水平。** v4 重构后在大模型上与官方 vLLM 达到同一量级，说明控制面/计算面的架构对齐是有效的。

compile 的对照（TTFT）：单卡 v4 35.47 vs vLLM 38.56（v4 略快），TP=2 v4 47.33 vs vLLM 51.36。大模型上 compile 对两边都几乎无收益，差距也不大。

### 5.1 对比边界

- 官方 vLLM 是通用引擎（更多采样、投机解码、多模态等），本对比只覆盖"贪心 decode、单机、8B/4B"窄场景。
- 两者 KV 容量设置方式不同（v4 显式块数，vLLM 按 `gpu_memory_utilization=0.9` 自适应），batch=8 下均未触顶。
- v4 的 compile 只编译 prefill，官方 `VLLM_COMPILE` 是全模型编译，语义不完全对等。
- 均为单次测量，TTFT 有 5%~10% 噪声，decode/吞吐较稳定；结论以 decode 与 batch 吞吐为准。

## 6. 复现方式

在 `vllm-v4/` 下：

```bash
# v4 大模型矩阵 + 官方矩阵（后台跑，timeout 兜底，写 bench/out/*.txt 与 bench.jsonl）
bash bench/run_matrix_large.sh

# 失败配置的补跑（DP=2 用 16 块 KV 适配 12GB 卡；vLLM 用 0.9 显存比）
bash bench/run_matrix_rerun.sh

# 生成 IEEE 风格英文图（SVG+PNG → docs/figures/）
../.venv2/bin/python bench/plot_bench.py
```

单个配置示例：

```bash
# v4：8B 单卡（4090）+ CG
../.venv2/bin/python bench/bench_parallel.py --model ~/shared/models/Qwen3-8B \
    --tp 1 --pp 1 --device-ids 0 --cg --tag 8b-tp1-cg

# v4：14B PP=2 不均分（12→4070，28→4090）
../.venv2/bin/python bench/bench_parallel.py --model ~/shared/models/Qwen3-14B \
    --tp 1 --pp 2 --pp-layer-counts 12,28 --device-ids 1,0 --tag 14b-pp2

# v4：4B DP=2
../.venv2/bin/python bench/bench_dp.py --model ~/huggingface/Qwen3-4B \
    --dp 2 --num-kvcache-blocks 16 --tag 4b-dp2

# 官方 vLLM：8B 单卡 + CG
../.venv-vllm/bin/python bench/bench_vllm_official.py --model ~/shared/models/Qwen3-8B \
    --tp 1 --cuda-devices 0 --cg --tag vllm-8b-tp1-cg
```

## 7. 结论与优化方向

综合 8B/14B/4B 三档，可以得出四条工程结论：

1. **优化开关的收益与模型规模成反比。** CG 从 0.6B 的 6.6x 衰减到 8B 的 1.5x、14B 的 1.2x；compile 从 4.1x 衰减到 1.1x。小模型靠它省发射开销，大模型靠它聊胜于无。
2. **并行策略只解决显存问题，不解决速度问题（在这台无 P2P 异构机上）。** 8B 单卡装得下时，TP/PP 全是负收益；14B 装不下时才用不均分 PP；4B 的 DP 反而更慢。
3. **v4 重构后在大模型上与官方 vLLM 打平。** 架构对齐（控制面 EngineCore/Executor、计算面 ModelRunner、数据面 KV）让 v4 从"小模型 CG 领先"收敛到"大模型同量级"，符合预期。
4. **已知限制待修。** 多卡纯 eager 的 `torch.compile`（8B PP=2）超时；DP=2 的 CG 在 12 GB 卡 OOM（需限制 CG 捕获 batch 上限）。

后续可优先做三件事：

1. **修复多卡纯 eager compile 路径。** 当前对含通信的 forward 做 max-autotune 会反复试探甚至卡死，可改为对 prefill 的"本地计算段"单独编译、通信段保持 eager。
2. **给 CG 加捕获 batch 上限。** 让 CUDA Graph 只捕获到实际调度 batch（而非 `max_num_seqs`），既能省显存、也能让 DP=2 的 4B 在 12 GB 卡上开 CG。
3. **TTFT 多次取中位数。** 当前单发噪声 5%~10%，回归对比时应取多次中位。
