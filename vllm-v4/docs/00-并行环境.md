# 并行计算环境

当我们拿到一台多卡服务器时，我们不仅要学会分析它的拓扑方式，更要确定大模型的并行方案。

在这篇文档中，我们主要学习两个模块：
- [1] 为什么要并行，三类并行策略及其代价。
- [2] 如何根据吞吐来做决策以及入门学习路线。

## 1. 并行计算框架
### 1.1 为什么要并行

大语言模型越来越大，但是单张 GPU 是存在天花板的。影响大模型的主要有两个因素：

- **显存瓶颈**。模型参数要占显存，bf16 下一个参数占 2 字节。Qwen3-14B 有 140 亿参数，权重约 28GB。一张 RTX 4090 只有 24GB 显存，权重放下之后还要给 KV cache 和中间激活留空间，14B 模型单卡就放不下了。
- **算力瓶颈**。就算显存放得下，单卡的矩阵乘算力也是有限的。decode 阶段一次只推一个 token，每次只做很小的矩阵乘，但要求延迟足够低。对于用户来说，单卡的算力总归是有上限的，因此更好的方式是多张卡一起算。

这两个瓶颈就是并行的理由。要么把模型的参数分到多张卡上，要么把计算任务分到多张卡上。

### 1.2 三类并行策略

并行策略可以按切分的对象分类。

**数据并行 DP**。每张卡持有完整的模型副本，输入数据按 batch 切分，每张卡算不同的样本。梯度更新时需要把各卡的梯度同步，通常用一次 all-reduce 完成。数据并行解决的是吞吐问题，一般来说训练更常用。

![数据并行 DP（源自 Megatron-LM 论文与 HF Model Parallelism 文档）](posts/parallelism_dp.png)

**张量并行 TP**。把一层内部的参数按维度切分，每张卡持有一块参数，算一块结果，最后用集合通信拼回。例如把权重矩阵的行切开分给两张卡，各自算部分输出，再用 all-gather 拼起来。这也是 v4 版本 `linear.py` 和 `vocab_parallel.py` 的实现方式。但是 TP 通信发生在每一层，通信非常频繁。

![张量并行 TP（源自 Megatron-LM 论文）](posts/parallelism_tp.png)

**流水线并行 PP**。把模型的层按顺序切段，每张卡负责连续的一段层。每张卡都算若干层，之后把中间张量传给后续的机器。PP 的通信发生在层与层的边界，次数比较少，单次传输的是整个 hidden 向量。

![流水线并行 PP（源自 GPipe 论文）](posts/parallelism_pp.png)

> 三者区别为：DP 切样本，TP 切层内张量，PP 切层。

### 1.3 并行的代价

并行是有代价的。
引入并行之后，单张卡的负担变小了，但是却多了另外一项开销，那就是通信。

以 TP 为例。列并行每层 all-gather 一次，行并行每层 all-reduce 一次。
在 Qwen3 的解码层里，o_proj 和 down_proj 是行并行，每层两次 all-reduce，28 层的模型单个 decode 步就有 56 次集合通信。每次通信的延迟和消息大小成正比，消息大小又和 batch、hidden 成正比。56 次乘起来，总通信开销没有办法被忽视。

对于 PP 来说，通信次数少，每层边界只发一次 hidden 向量，但流水线同样有气泡问题。前段卡算完传给后段卡时，前段卡可能闲着等下一份输入，GPU 利用率不满。

所以判断一个并行方案值不值，核心指标是通信开销和计算时间的比值。如果每层通信的时间远小于每层计算的时间，并行划算。如果通信比计算还贵，并行就是负收益。

## 2. 决策与学习路线
### 2.1 真实数据下的决策

用环境 A （4070s + 4090D）的实测数据展示决策过程。模型是 Qwen3-0.6B，decode 单请求吞吐如下。环境 A 的拓扑与带宽细节见 [服务器测量.md](服务器测量.md)。

| 配置 | 单请求 decode tok/s | batch=8 吞吐 tok/s |
| --- | --- | --- |
| 单卡 + CUDA Graph | 433 | 2735 |
| TP=2 + CUDA Graph | 145 | 995 |
| PP=2 + CUDA Graph | 228 | 1039 |
| 单卡 eager | 58 | 481 |
| TP=2 eager | 35 | 280 |
| PP=2 eager | 66 | 495 |

同一台机器，eager 和 CUDA Graph 两种模式下结论不同。eager 模式被 Python 和 kernel 启动开销主导，PP 把每卡层数减半反而更快。CUDA Graph 把启动开销压掉后，瓶颈回到算力和通信，因为环境A的通信开销特别大， 因此只要开启并行，几乎就是负收益。

从环境 A 我们得出的结论是：对于显存放得下的模型，单卡加 CUDA Graph 优先。TP 只有在 NVLink 环境或模型大到单卡放不下时才考虑。PP 在 eager 模式有一定的优化，但是在 CG 模式下也不如单卡。


### 2.2 入门学习路线
对于模型并行，可以参考以下学习方案：
1. 单卡推理优化（V0-V3已教学）
2. 硬件互联。搞清楚所用的服务器配置
3. 动手测量。用固定流程测试当前服务器的GPU带宽，把纸面参数转换成为真实的延迟曲线。
4. 掌握集合通信。学习 all-reduce、all-gather、reduce-scatter、send/recv 等通信原语。
5. 理解 TP 和 PP。学习如何对linear和词表进行切分；以及如何设计通信原语。
6. 完整的把大模型从单卡修改为多卡。
