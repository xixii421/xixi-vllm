# 多机部署指南

同一套代码要在三台机器上跑，最忌讳的是"手动拷文件、手动配环境"。
本文给出一个标准工作流，让代码同步和环境配置都变成一条命令。

## 核心思路

代码走 git，环境走脚本。二者分开，因为它们的更新频率完全不同。

代码频繁变，走 git 推送拉取，一条 `git pull` 就同步。环境几乎不变，走版本化的脚本，每台机器只在首次配置时跑一次。

## 第一步，代码用 git 同步

仓库已经在 GitHub（`git@github.com:dzyy-team/dzyy-vllm.git`），三台机器各 clone 一份。

```bash
git clone git@github.com:dzyy-team/dzyy-vllm.git
cd dzyy-vllm
```

之后每次代码有改动，在本机提交并推送。

```bash
git add .
git commit -m "描述这次改动"
git push
```

其他机器上拉取最新代码。

```bash
git pull
```

关键是养成习惯，所有代码改动都进 git，绝不手动拷文件。`vllm-v4/.venv` 这类本地环境已经写在 `.gitignore` 里，不会被提交，也不会互相污染。

## 第二步，环境用脚本配置

clone 之后，在 `vllm-v4/` 下跑一次。

```bash
cd vllm-v4
bash setup_env.sh
```

脚本会自动做三件事。

1. 探测本机 CUDA 版本（`nvidia-smi` 头部），自动选择匹配的 torch 安装源，例如 CUDA 13 用 `cu130` 源，CUDA 12.4 用 `cu124` 源，不用手填。
2. 创建 `.venv` 虚拟环境。
3. 安装 torch、flashinfer、flash-attn 和 `requirements.txt` 里的纯 Python 依赖。

不同机器的 CUDA 版本可能不同，脚本按本机探测结果装，三台机器可以各装各的版本，互不冲突。

### 常用参数

```bash
bash setup_env.sh --venv myenv      # 指定虚拟环境目录名，默认 .venv
bash setup_env.sh --cuda 12.4       # 手动指定 CUDA 版本
bash setup_env.sh --skip-cuda       # 只装纯 Python 依赖，跳过 torch 等 CUDA 包
```

flashinfer 或 flash-attn 在个别机器上可能因为网络或编译失败，脚本会给出警告但继续，不影响正确性，只影响推理速度。它们主要做推理加速，可以之后再补装。

## 第三步，日常开发流程

每次在三台机器之间切换，只需两句话。

```bash
git pull                 # 同步代码
source .venv/bin/activate  # 启用环境
```

如果 `requirements.txt` 里新增了依赖，重跑一次 `bash setup_env.sh` 即可，已装好的包会被 pip 跳过，只装新增的。

## 可选的进阶方案

环境脚本已经解决了大多数问题。如果嫌每台机器各自装太慢，还有两个更重的方案。

**共享虚拟环境**。如果几台机器的 GPU 和 CUDA 版本完全一样，可以把装好的 `.venv` 打包传给其他机器。

```bash
tar -czf venv.tar.gz .venv
```

在目标机器上解压到同一路径即可复用。注意虚拟环境里的路径是写死的，必须解压到相同绝对路径才能用。

**容器化**。把环境连同代码一起打包成镜像，任何机器 `docker run` 即可，彻底消除环境差异。

```bash
# 在任意一台有 Docker 的机器构建
docker build -t dzyy-vllm .

# 在任意机器运行
docker run --gpus all dzyy-vllm
```

容器方案适合环境复杂或团队协作的场景，但镜像大、构建慢，教学实验用环境脚本通常更轻量。
