## 1. 文件地图

```
src/moe/
  block.py          SparseMoeBlock：gate → route → experts → shared / AR
  experts.py        3D 权重、expert_map、HF 加载、Experts.forward
  parallel.py       MoEParallelConfig、cutlass / triton 可用性
  fused.py          后端分发；cutlass scratch
  kernels/
    triton.py       grouped GEMM；decode 可跳过 align
    cuda.py         JIT 加载 moe_kernels.cu
    moe_kernels.cu  align / mul_and_silu / moe_sum
```

Worker 建模型时：`resolve_moe_backend` → `MoEParallelConfig.from_engine` → `Qwen3MoeForCausalLM`。某一层判定为 MoE 时构造 `SparseMoeBlock`。

```
Qwen3MoeDecoderLayer
        │
        ▼
 SparseMoeBlock.forward
        │  gate（ReplicatedLinear）
        │  route_experts
        ▼
 Experts.forward          expert_map[topk_ids]
        ▼
 fused_moe_forward        cutlass | triton
        │
        ├─ 可选 all-reduce
        └─ 可选共享专家
```

## 2. SparseMoeBlock

构造时读 config：`num_experts`、`num_experts_per_tok`、`moe_intermediate_size`、`norm_topk_prob`、`shared_expert_intermediate_size`。

前向：hidden 展成 `[T, H]` → gate → `route_experts` → `experts(...)` → 按 TP/EP 决定 AR 与共享的先后 → `view` 回原形状。

共享专家有就建，没有则指针为 `None`。共享路径：merged gate_up（列并行）→ `SiluAndMul`（按 `[gate|up]`）→ down（行并行，`reduce_results=False`）→ 乘 `sigmoid(shared_expert_gate)`。routed 专家走 `[up|gate]` / `mul_and_silu`。EP 时共享三层的 `tp_size` 强制为 1。

```python
if self.use_ep:
    if need_ar:
        out = tensor_model_parallel_all_reduce(out)
    if shared is not None:
        out = out + self._shared_expert(hidden)
else:
    if shared is not None:
        out = out + self._shared_expert(hidden)
    if need_ar:
        out = tensor_model_parallel_all_reduce(out)
```

`need_ar` 看 TP 组大小。开 EP 后 MoE 自己的 `tp_size` 已是 1，但 NCCL 组仍是原来那批 rank，`get_tp_group().size > 1` 仍为真，AR 仍会发生：EP 的 partial sum 靠这个组加齐。

## 3. 权重布局与加载

运行时两张 3D 参数：

| 参数 | 形状 | 含义 |
| --- | --- | --- |
| `w13_weight` | `[n_local, 2 * inter_per_tp, hidden]` | 第一层，`[up \| gate]` |
| `w2_weight` | `[n_local, hidden, inter_per_tp]` | down |

`n_local = num_experts / ep_size`。`inter_per_tp = moe_intermediate_size / tp_size`。

HuggingFace 常见两种存法：每专家三份 2D（`gate_proj` / `up_proj` / `down_proj`），或已叠成 3D 的 `gate_up_proj` / `down_proj`。加载器两条都收。

2D 路径按 `tp_rank` `narrow`：gate/up 切第 0 维，down 切第 1 维。`up_proj` 写入 `w13` 前半，`gate_proj` 写入后半。

3D 路径认 `[E, 2I, H]` 或 `[E, H, 2I]`，再 `_hf_gate_up_to_cutlass` 把 HF 的 `[gate|up]` 换成 `[up|gate]`，按 ep 段和 tp 片拷进参数。

`expert_map` 长度等于全局专家数。本卡持有的写本地下标，其余 `-1`。例：ep=2、8 专家、rank 1 → `[-1,-1,-1,-1,0,1,2,3]`。

加载结束断言：每个本地专家的 gate / up / down 都到齐。漏分片在这里报错。

## 4. Qwen2-MoE 与 Qwen3-MoE

层类型：

```python
if layer_idx in mlp_only_layers:
    稠密 MLP
elif (layer_idx + 1) % decoder_sparse_step == 0:
    SparseMoeBlock
else:
    稠密 MLP
```

`model_type == "qwen2_moe"` 时：qkv 带 bias，无 qk-norm。Qwen3-MoE 有 qk-norm。`e_score_correction_bias` 加载时跳过。

词表：LM Head 未加载而 embed 已加载时，把 embed 第 1 行之后拷到 LM Head（第 0 行是 embedding dummy），与 v4 词表路径相同。

## 5. 并行配置与后端

`MoEParallelConfig`：`tp_size / tp_rank / ep_size / ep_rank / use_ep / fused_backend`。入口只有 `from_engine`。

- `--ep` 且 `tp_size>1`：MoE `tp_size=1`，`ep_size=旧 tp`
- 否则 `ep_size=1`，MoE 跟引擎 tp 切中间维

`auto` 后端：

1. SM ∈ `{89,90,100,103,110,120,121}` 且能 import FlashInfer cutlass → cutlass（SM≥120 还要 nvcc≥12.8）
2. 否则有 Triton → Triton
3. 都没有 → 报错；没有生产用的纯 PyTorch for 循环路径

`--moe-backend cutlass|triton` 跳过 auto，不可用则立刻 `RuntimeError`，不静默降级。

CUDA 扩展：`torch.utils.cpp_extension.load` 编 `kernels/moe_kernels.cu`。`VLLM_MOE_CUDA=0` 关闭。`clear_fused_state()` 清 cutlass / Triton 缓存，测试 fixture 每条调用。

## 6. 引擎约束

MoE 在 `EngineConfig.__post_init__` 里强制 `enforce_eager=True`。动态 routing 与 cutlass workspace 尚未稳定进 CUDA Graph。稠密 Qwen3 不受影响。

`enable_ep` 打在稠密模型上会 `ValueError`。

```bash
python run.py --model ~/huggingface/Qwen1.5-MoE-A2.7B --tp 2 --ep --moe-backend triton
```

两张卡仍是 `tp_size=2`：Attention 切头，MoE 切专家。

## 7. 和官方实现的差异

官方在 `vllm/model_executor/layers/fused_moe/`。本实现面向 Qwen2 / Qwen3-MoE，EP 复用 TP 组 + `expert_map`。

| 维度 | vLLM 官方 | 本实现 |
| --- | --- | --- |
| 覆盖模型 | 多家 MoE | Qwen2-MoE / Qwen3-MoE |
| 专家计算 | Triton + FlashInfer/CUTLASS | 同上两选一，Triton 核在仓库内 |
| EP 通信 | DeepEP / PPLX all-to-all | remote 标 `-1`，出口 all-reduce |
| EP 进程组 | 可独立 EP 组 | 复用 TP 组 |
| 量化 MoE | FP8 / INT4 等 | 无 |
| CUDA Graph | MoE 可进图 | MoE 强制 eager |
| 共享专家 AR | 按模型实现 | EP：先 AR 再加；TP：先加再 AR |
| 权重顺序 | 按后端转换 | 加载时固定 `[up\|gate]` |
| LoRA | 有 | 无 |

专家数到 256、跨节点时，官方 DeepEP 往往更合适。v5 先覆盖单机多卡、与现有 TP 共用 rank，语义短、好调试。token 始终在每卡过一遍 map，路由很偏时空转会比 all-to-all 明显。

## 8. 怎么验

- CPU：`route_experts` 归一化后每行和为 1；`expert_map` 分段；开 EP 后 `from_engine` 的 tp 为 1；MoE 的 EngineConfig 打开 eager。
- 单卡 GPU：Triton fused 对 naive，fp16、`atol=5e-2`；EP map 切开再相加等于全专家一次算完。
- 两卡：同一 prompt greedy，`tp=1` / `tp=2` / `tp=2+ep` 序列相同。

性能与正确性分开。`bench/moe_e2e.py` 测本引擎；`bench/vs_vllm.py --model moe` 对官方。对比时官方也关到 eager，否则比的是 graph。

## 9. 还没做的

## 10. 常考题

**Q：`w13` / `w2` 各是什么？**  
`w13` 是 fused 的第一层 `[up|gate]`，`w2` 是 down。运行时不再 `ModuleList` 循环每个专家。

**Q：`expert_map` 干什么？**  
全局专家号 → 本地下标；remote 为 `-1`，核内跳过。EP 的核心数据结构。

**Q：为什么 MoE 强制 eager？**  
routing 动态，`sorted_ids` 长度随负载变；cutlass workspace 尚未按 CUDA Graph 要求固定。

**Q：cutlass 路径里为什么 `ep_size=1`？**  
EP 已在 `expert_map` 做完，核内不再做第二层专家并行。

**Q：共享专家的激活核和 routed 为什么不同？**  
共享走稠密 `SiluAndMul`（`[gate|up]`）；routed 走 `mul_and_silu`（`[up|gate]`），与 FlashInfer cutlass 约定一致。

**Q：本实现和官方最大的行为差？**  
EP 通信：官方可 all-to-all 搬 token；本实现 token 不动、出口 all-reduce。
