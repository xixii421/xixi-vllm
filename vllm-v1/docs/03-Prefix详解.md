# Prefix 详解
> 源码：[src/kv/prefix/](../src/kv/prefix/) | 上文：[01-KV Cache 代码架构解释](./01-KV%20Cache代码架构解释.md)

上一篇讲完了KV Management。本篇讲前缀复用。

## Prefix 的作用

在推理服务中，KV Cache 的核心作用是避免单次生成过程中的重复计算。Prefill 阶段计算并缓存历史 token 的 Key/Value，供后续 Decode 阶段直接使用。然而，这种缓存机制默认是“请求级”的，即单次生成结束后，占用的缓存页通常会被直接释放。

这就带来了一个性能瓶颈：当多个请求共享相同的长前缀（如相同的系统提示词或公共参考文档）时，每个请求的 Prefill 阶段都必须重新计算这段公共前缀，造成大量的算力浪费。

前缀缓存的目标正是消除这种跨请求的重复 Prefill 计算。其基本工作流程如下：

- **缓存保留与映射**：当第一次请求完成 Prefill 后，系统不再立即释放那些已填满的 K/V 物理页，而是将其保留，并建立“前缀 token 序列”到“物理页”的映射关系。
- **前缀匹配与复用**：当后续请求到来时，系统会检查其前缀 token 是否与已缓存的序列匹配。如果完全命中，新请求将直接复用这些物理页作为自己的 KV Cache，从而跳过公共前缀的 Prefill 计算。
- **增量计算**：Prefill 过程只需从分叉点（即新请求与缓存前缀不同的位置）开始，继续计算后续新增的 token，并将结果写入新的物理页中。

Prefix 节省的是**跨请求的重复 Prefill**。

在系统实现中，“前缀 → 物理页”的映射关系由特定的索引后端来维护。这可以通过配置项 `prefix_backend` 进行指定：
- `none`：关闭前缀复用；
- `hash` 或 `radix`：两种索引后端，都能命中前缀。目标完全一致，只是组织方式不同。


在深入 Hash 和 Radix 的细节之前，先理解索引层对外暴露的三个基本方法。这三个方法是所有后端共用的接口，不管底层是字典还是树，它们的分工不变。

| 接口 | 做什么 | 谁在什么时候调用 |
|------|--------|-----------------|
| `publish` | 请求结束时，把本次请求中已经填满的物理页登记到索引里，并让这些页进入 cached 状态 | KV Manager 在 `finish` 阶段调用 |
| `match` | 新请求分配页表时，从左到右扫描满块，查索引里有没有可以复用的物理页，返回一个物理块号列表 | KV Manager 在 `allocate` 阶段、Prefill 之前调用 |
| `invalidate` | 某个处于 cached 状态的物理页被页池淘汰时，把索引里指向它的条目删掉，防止后续请求查到一块已经无效的物理页 | 页池在淘汰 cached 页时通过回调触发 |

这三个函数在目录管理中各自承担着不同的职责，共同保障数据复用机制的正常运行。当数据块填满时，publish 会将其前缀信息记录到目录中；当有新请求到来时，match 会从目录中查找可复用的块；而当数据块被回收时，invalidate 会及时清理对应的目录条目。简单来说，publish 负责“建索引”，match 负责“查索引”，invalidate 负责“删索引”。


Radix 后端比 Hash 多了两个额外的生命周期方法，`pin_match` 和 `release_seq`，它们用来在树节点上增减引用计数。


## Prefix示例
假设 `block_size = 2`（每个物理块最多存储 2 个 token）。三个请求的序列分块情况如下表所示：

| 请求 | Prompt 序列 | 块 0 | 块 1 | 块 2 (尾块) |
| :--- | :--- | :--- | :--- | :--- |
| **R1** | `[A, B, C, D, E]` | `[A, B]` | `[C, D]` | `[E]` *(未满)* |
| **R2** | `[A, B, C, D, F, G]`| `[A, B]` | `[C, D]` | `[F, G]` |
| **R3** | `[A, B, X, Y, Z]` | `[A, B]` | `[X, Y]` | `[Z]` *(未满)* |

**R1 结束时的物理页状态：**

假设 R1 依次分配了物理页 P0、P1、P2，其最终状态如下：

```text
物理页 P0: [A, B]  <-- 满块，进入 cached 状态 (供 R2/R3 复用)
物理页 P1: [C, D]  <-- 满块，进入 cached 状态 (供 R2 复用)
物理页 P2: [E]     <-- 尾块(未满)，直接释放回内存池
```

*注：前缀缓存机制仅保留满块。因此，当 R2 到来时，可以直接复用 P0 和 P1；而 R3 到来时，只能复用 P0。*

R1 先执行完毕，它留下了两个满块。我们假设它分配到的物理页号分别是 P0 和 P1，P0 里面存了 `[A, B]`，P1 里面存了 `[C, D]`。尾块所在的物理页是 P2，因为不满，不会被发布。

P0 和 P1 在 R1 结束后会进入 cached 状态，等待被后续请求复用。


## 链式哈希：让哈希记住前缀
索引要解决的核心问题，是根据 token 序列定位到对应的物理块。如果直接用完整 token 序列进行匹配，序列通常较长，存储和比较的成本都比较高。因此，可以对每个已满块计算一个哈希值，并让这个哈希值代表该块的内容。

不过，单个块的哈希不能只由本块 token 独立决定。相同内容的块可能出现在不同前缀之后。例如一个请求的前两块是 `[A, B]` 和 `[C, D]`，另一个请求的前两块是 `[X, Y]` 和 `[C, D]`。两个请求中的第二块内容相同，但前面的上下文不同。如果第二块的哈希只由 `[C, D]` 决定，索引就可能命中另一个上下文中的物理块，造成错误复用。

因此可以采用链式哈希。每个块的哈希不仅由本块 token 决定，也由前一个块的哈希决定。这样，一个块的哈希同时携带了本块内容和前缀位置的信息。只要前缀中任何一个块不同，后续块即使内容相同，也会得到不同的哈希。

在具体表示中，首块没有前驱块，前缀可以设为特殊值 -1。块 0 的哈希可以写成 `h0 = hash([A, B], prefix = -1)`。如果块 1 的内容是 `[C, D]`，并且它紧跟在块 0 之后，那么块 1 的哈希为 `h1 = hash([C, D], prefix = h0)`。请求 R1 和 R2 如果共享这两个块，它们得到的 h1 相同。请求 R3 如果在同样的前缀 h0 之后使用不同内容 `[X, Y]`，则会得到 `h1' = hash([X, Y], prefix = h0)`，因此与 R1 和 R2 不同。

这样处理后，每个块的哈希都依赖于它之前的所有块。索引在查找时只有逐块得到相同的哈希，才能确认某个物理块属于当前 token 前缀，可以安全使用。



## Hash 后端：一本扁平的字典

Hash 后端的结构是一个字典。字典里存的是链式哈希到物理块编号的映射。计算块哈希时，每个块都会带上前一块的哈希，所以哈希值本身就包含前缀信息。查找时从第一个块开始，逐块计算哈希，逐块查字典，就能知道请求能命中多少已有块。

```python
class HashPrefixIndex:
    def __init__(self):
        self._hash_to_block_id: dict[int, int] = {}
```
字典里只有哈希和物理块编号。前缀关系由哈希值本身携带。查字典时，只要哈希能对上，就说明这段前缀在系统里已经出现过。

### R1 结束时发布满块

R1 有两个满块。第一块 P0 里是 [A, B]，第二块 P1 里是 [C, D]。请求处理到一定阶段后，KV Manager 调用 publish，把这两个块写进索引。

```python
def publish(self, seq, num_full_blocks, pool):
    h = -1
    for i in range(num_full_blocks):   # i 依次为 0 和 1
        bid = seq.block_table[i]       # 第一个满块是 P0，第二个是 P1
        toks = seq.block_token_ids(i)  # 第一次取 [A, B]，第二次取 [C, D]
        h = compute_block_hash(toks, h)  # 计算链式哈希
        pool.blocks[bid].update(h, toks) # 把哈希和 token 写入物理块元数据
        self._hash_to_block_id[h] = bid  # 在字典里记录 h → bid
```

第一次循环时，h 还是 -1，说明前面没有块。用 [A, B] 和 -1 计算出 h0。P0 的元数据写入 h0 和 token_ids，字典里也记下 h0 对应 P0。

第二次循环时，h 变成 h0。用 [C, D] 和 h0 计算出 h1。P1 的元数据写入 h1 和 token_ids，字典里记下 h1 对应 P1。

publish 结束后，字典内容是

```
h0 → P0
h1 → P1
```

目录里现在有两个条目，分别记录第一块和第二块的物理位置。

### R2 到来时的前缀匹配

R2 进来后，Manager 在 Prefill 前调用 match，看它能复用多少块。match 的做法很直接，从第 0 块开始，一块一块算哈希，一块一块查字典。查到就继续，查不到就停。

```python
def match(self, seq, pool):
    h = -1
    hit = []
    for i in range(seq.num_full_blocks()):   # R2 有三个满块，循环三次
        toks = seq.block_token_ids(i)        # 依次取 [A,B], [C,D], [F,G]
        h = compute_block_hash(toks, h)      # 用同样的方式计算链式哈希
        bid = self._hash_to_block_id.get(h, -1)  # 查字典
        if bid < 0:
            break                            # 找不到就停
        block = pool.blocks[bid]
        if block.token_ids != toks:          # 校验 token 是否完全一致
            break
        if bid not in pool.used_ids and bid not in pool.cached_ids:
            break                            # 物理块必须处于可用状态
        hit.append(bid)
    return hit
```

R2 有三个满块，分别是 [A, B]、[C, D]、[F, G]。

先看第 0 块。token 是 [A, B]，h 从 -1 开始，算出 h0。字典里有 h0，拿到 P0。再看一下 P0 里存的 token_ids，确实是 [A, B]，并且 P0 当前可以被复用，于是把 P0 加进结果。

再看第 1 块。token 是 [C, D]，这时 h 是 h0，算出 h1。字典里有 h1，拿到 P1。P1 里的 token_ids 也是 [C, D]，状态也合适，于是把 P1 加进结果。

到第 2 块时，token 是 [F, G]，这时 h 是 h1，算出新的哈希，比如 h2_new。字典里没有这个键，get 返回 -1，match 停止。

所以 R2 的结果是 [P0, P1]。Manager 会把这两块放进 R2 的页表，并把已缓存 token 数设为 4。后面 Prefill 从 F 开始算，A B C D 不用再算。

### R3 到来时的前缀匹配

R3 同样调用 `match`。

第一步，i=0。`toks` 为 `[A, B]`，算出 `h0`，字典命中 `P0`，校验通过，`hit = [P0]`。

第二步，i=1。`toks` 为 `[X, Y]`，`h` 为 `h0`，算出 `h1'`。这个值不在字典里，`bid` 为 -1，`break`。

循环结束，返回 `[P0]`。R3 只能复用第一块，第二块开始需要新分配物理页。

在整个过程中，Hash 字典的结构没有任何变化。`h1'` 查不到只是因为字典里没有对应的条目，字典本身仍然是那两条记录。

这就是 Hash 后端的特点：通过逐块查字典自然实现最长前缀匹配。


## Radix 后端：一棵压缩前缀树

Radix 后端也根据前缀 token 序列查找可复用的物理块。它把链式哈希序列放进一棵压缩前缀树。树的每条边保存一段哈希序列，同时保存这段哈希对应的物理块编号。查找时，请求的哈希序列从根开始逐段匹配，能匹配多远，就取出对应的物理块。

压缩前缀树的好处是，公共前缀可以共享一段路径。没有分叉时，多个连续哈希可以放在同一条边上。出现分叉时，再把边拆开，让公共部分成为独立节点。

### 树的结构

每个节点保存从父节点到当前节点的一条边。key 是这条边上的哈希序列，value 是对应的物理块序列。key 和 value 的长度相同，位置一一对应。children 的键是孩子边的第一个哈希值。ref_count 记录当前节点被多少活跃请求引用。根节点的引用计数通常设为 1，避免被回收。

```python
class _RadixNode:
    __slots__ = ("children", "parent", "key", "value", "ref_count")
    def __init__(self, *, parent=None, key=(), value=(), ref_count=0):
        self.children = {}   # 子节点，键为子边第一个哈希值
        self.parent = parent
        self.key = key       # 这条边上挂的哈希元组
        self.value = value   # 这条边对应的物理块号元组
        self.ref_count = ref_count
```

### R1 结束时发布满块

在进入 publish 之前，需要先明确一个前提。只有满块才会进入前缀索引。满块指 token 数正好等于 block_size 的块。未满的尾块不参与共享。

这样规定是为了把复用边界固定在整块上。如果未满块也能进入索引，系统就要处理块内部分命中、块内追加 token、不同请求共享同一个半块等问题。页表拼接和物理块回收都会复杂很多。教学实现里直接约定，publish 只处理 num_full_blocks。尾块即使包含有效 KV，也不写入索引。

以 R1 为例。假设 block_size 是 2，R1 的 token 序列是 [A, B, C, D, E]。前两个块 [A, B] 和 [C, D] 是满块，对应 P0 和 P1。第三个块只有 [E]，对应 P2。publish 只登记 P0 和 P1。P2 不会进入 Hash 字典，也不会进入 Radix 树。后续请求即使也以 [A, B, C, D, E] 开头，也只能复用前两个满块，E 所在部分需要重新计算。

```python
def publish(self, seq, num_full_blocks, pool):
    # 先给每个物理块写入 hash 和 token_ids（与 hash 后端相同）
    ...
    key = self._block_hashes(seq, num_full_blocks)    # [h0, h1]
    value = list(seq.block_table[:num_full_blocks])   # [P0, P1]
    last = self._tree.insert(key, value)
    self._tree.inc_ref(last)
    self._seq_node[seq.seq_id] = last
```

插入后树的状态如下，根下面有一条边，它的 key 是 `(h0, h1)`，value 是 `(P0, P1)`。

```
根
 └── 边 (h0, h1) → value (P0, P1)
```
inc_ref 会把该节点的引用计数加一，表示 R1 还在使用这段前缀。_seq_node 记录这个请求对应的节点，方便后续引用或释放。
如果树上已经存在相同路径，insert 会复用已有节点。如果新路径和已有路径部分相同，insert 会在分叉处拆开旧边，再挂上新边。

### R2 到来时的前缀匹配

R2 的满块哈希序列也是 `[h0, h1]`。`match` 方法调用 `match_prefix` 沿树匹配。

```python
def match(self, seq, pool):
    n_full = seq.num_full_blocks()
    key = self._block_hashes(seq, n_full)          # [h0, h1]
    cached_ids, _ = self._tree.match_prefix(key)   # 沿树走，得到 [P0, P1]
    # 再逐块校验 hash 和 token_ids（与 hash 后端类似的校验循环）
    ...
```

match_prefix 从根开始找。它看到根的某个孩子边以 h0 开头，并且这条边的 key (h0, h1) 与请求 key 完全一致，于是返回这条边上的物理块序列 (P0, P1)。

得到候选物理块后，match 还会逐块校验。校验 token_ids 是为了确认物理块里的内容和请求块一致。校验 used_ids 和 cached_ids 是为了确认物理块还没有被回收。校验通过后，R2 命中 P0 和 P1。pin_match 会增加相关节点的引用计数，表示这段前缀正在被活跃请求使用。


### R3 到来时的前缀匹配与边分裂

R3 的哈希序列是 [h0, h1_prime]。h1_prime 和 h1 不同。

match_prefix 从根开始，仍然能找到以 h0 开头的那条边。原来的边 key 是 (h0, h1)，请求 key 是 (h0, h1_prime)。两边只有一个哈希 h0 相同，第二个哈希开始分叉。为了把公共前缀单独表示出来，树会把这条边拆开。

有些实现会让 match 保持只读，把分裂放到 publish 阶段。这里为了说明树结构如何变化，按照教学实现的写法，让 match_prefix 在发现部分匹配时先拆边。

分裂后，第一段边变成 (h0,)，对应物理块 (P0,)。第二段边变成 (h1,)，对应物理块 (P1,)，挂在第一段边下面。

分裂后的树结构如下。

```
根
 └── 边 (h0) → value (P0)
      └── 边 (h1) → value (P1)
```

`match_prefix` 在分裂后停在 `(h0)` 节点，返回 `(P0)`。R3 因此只命中第一块。

如果将来 R3 也发布自己的满块，就会在 `(h0)` 节点下再挂上一条 `(h1')` 的边，形成显式的分叉结构。公共前缀 `h0` 以共享节点的形式存在，分叉的子树挂在不同分支下。
```
根
 └── 边 (h0) → 值 (P0)
      ├── 边 (h1) → 值 (P1)
      └── 边 (h1') → 值 (P4)
```

在 Hash 后端里，`invalidate` 的实现很直接，从字典中删除对应条目即可。但在 Radix 后端中，教学实现里的 `invalidate` 是空操作。

```python
def invalidate(self, block_id: int, pool: BlockPool) -> None:
    # 教学实现：淘汰时不拆树，靠块元数据校验兜底
    return
```

这意味着当某个 cached 物理页被淘汰时，Radix 树不会立刻删除对应的节点或边。那怎么防止后续请求错误命中一块已被回收的物理页呢？答案在 `match` 的校验逻辑里。每次 `match_prefix` 返回候选物理块列表后，Radix 后端的 `match` 方法会逐块检查这些物理块是否还在 `used_ids` 或 `cached_ids` 中。如果某一块已经被淘汰，它就不在这两个集合里，校验会失败，匹配就此中断。

这种设计在教学版本中可以减少树结构频繁修改的复杂度。在生产环境中，如果希望对树节点本身也做生命周期管理，可以结合引用计数，在节点引用降到零且所有关联的物理块都失效时，再对树节点进行回收。





## 两种后端的对比总结

从功能上看，Hash 和 Radix 做的是同一件事：记住满块，让后续请求的前缀能够命中并复用物理页。用同一组 R1、R2、R3 的例子，它们给出的命中结果完全一样，R2 得到 `[P0, P1]`，R3 得到 `[P0]`。对 Prefill 跳跃的 token 数量没有区别。

从结构上看，Hash 是一本扁平字典，每个满块哈希对应一个物理块号，分叉表现为字典里查不到对应的键，字典本身不变。Radix 是一棵压缩前缀树，整条哈希序列作为路径，分叉时边被分裂，公共前缀在树上以共享节点的方式显式呈现，并用引用计数管理前缀的生命周期。


当 `prefix_backend` 设置为 `none` 时，系统使用一个空操作的后端，所有方法都不执行任何实际逻辑。


`match` 永远返回空列表，这意味着每次请求都从零开始分配页表，没有任何前缀可以复用。`publish` 和 `invalidate` 什么都不做，所有满块在请求结束后都会归还 free 池，不留任何 cached 块。

Noop 后端的价值在于保持接口统一。上层的 KV Manager 不需要判断后端是否存在，始终调用 `self.index.match()`，如果配置为 `none`，这个调用什么也不返回，Manager 的后续逻辑自然走全量分配路径。这比在 Manager 里到处写 `if backend is not None` 更干净。


## Radix优点
Radix 树和 Hash 字典都能实现前缀复用，命中结果也完全一致。既然 Hash 字典那么简单直接，为什么还要设计 Radix 呢？我们从四个角度来分析 Radix 带来的额外好处。

**第一，分叉时结构更紧凑，公共部分只存一份**

在 Hash 字典里，每个满块哈希是一个独立的键，对应一个物理块号。假设有三个请求共享同一段长前缀，比如 10 个满块，它们只在最后一块不同。Hash 字典会为每个请求的前缀分别存储 10 条独立的记录，即使前 9 块的哈希和物理块号完全一样。这些重复的键分散在字典里，彼此之间没有关联，字典无法知道它们共享了相同的前缀。

Radix 树的做法不同。它把公共的哈希序列压缩成共享的边和节点。前 9 块对应的哈希序列在树中只存储一次，成为一个公共路径。到第 10 块分叉时，通过边的分裂，在公共路径的末尾挂上不同的后缀分支。这样相同的哈希序列不会被重复存储，结构上自然体现了前缀的共享关系。

**第二，树节点支持引用计数，能精确管理前缀的生命周期**

Hash 字典只建立了哈希值到物理块的映射。它本身不记录有多少个请求正在使用这个映射，也不关心映射对应的前缀是否还有人需要。如果物理页从 cached 池中被淘汰，Hash 字典通过 `invalidate` 被动删除条目。只要页还在，条目就在；页被回收，条目就消失。这是一种比较简单直接的生命周期管理，完全跟随物理页的状态。

Radix 树给每个节点加入了 `ref_count` 引用计数。当请求在 allocate 阶段命中一段前缀时，会调用 `pin_match`，从命中节点到根节点，沿途每个节点的引用计数都加一。当请求结束时，调用 `release_seq`，沿途减一。

这个机制带来了一个 Hash 字典没有的能力。多个请求可以同时使用同一个前缀节点，即使前缀对应的物理页因为某些策略被淘汰，只要还有请求持有该节点的引用，这个树节点就不会被删除，前缀的结构关系仍然保留。这样在多请求并发访问的场景下，前缀索引不会因为某个页被淘汰而立刻断掉，其他还在使用这段前缀的请求依然可以找到自己的路径。

**第三，多次查询时路径匹配更高效**

Hash 字典的匹配方式是逐块计算哈希并查表。对于一段由很多满块组成的前缀，需要依次计算哈希、查字典、校验 token，每次都是独立的键值查找。虽然单次查找开销不大，但块数多的时候需要做很多次字典查询。

Radix 树把连续匹配的哈希合并成一条边。如果一个请求的前缀完全命中一条很长的边，`match_prefix` 可以一次走过整条边，拿到整段对应的物理块列表，不需要逐块查字典。即便中间有分叉，公共部分也只被匹配一次。这种压缩前缀的查找方式在处理长前缀时比逐块查表更直接。

**第四，为并发共享和更复杂的前缀策略留下扩展空间**

Hash 字典天生是一个扁平的全局映射。如果多个请求同时共享前缀，字典只能保证查到同一块，但它没有结构来表示“这些请求正在共享同一个前缀”。当需要实现更复杂的功能，比如统计前缀热度、主动清理不再被引用的前缀子树、或者在内存压力下有选择地驱逐冷前缀时，Hash 字典缺少必要的结构信息。

Radix 树天然是一个带引用计数的树。可以通过遍历树知道哪些前缀被多少请求引用，哪些子树长期没有引用可以回收。这种结构为未来的前缀缓存管理策略，比如 LRU 淘汰前缀节点、限制前缀树的总大小、区分冷热前缀等，提供了很自然的扩展基础。
